## D-03 P3-A4 数据面落点与清库代价

- **问题**：P3-A4 卡绑定“本机 `~/.moshi` 种子库”，要求有边、有裁决、有 feedback、有 query_log；M2 现有 `~/.moshi` 是 60 条直写事实（edge/annotation/adjudication 全 0，episode/session 全空）。`pnpm seed:devdb` 在默认 home 会被 `assertProjectsRootOwned`（jianmu 有 3 个 jsonl）与 `assertOwnedDb`（有 fact 但 episode=0）拒绝；用 `--home` 隔离可以跑通，但偏离卡定义；清库重建会覆盖 40 条 `golden.v1.jsonl` 为 32 条、丢 174 条 `query_log`，并破坏 P1-16 当前 m2 证据。
- **原因**：护栏按 episode 归属判库；旧库不是种子工具产物；seed 的 golden 生成器上限为四类各 8（32 条），无法产出 P1-16 需要的 40 条。
- **解决方向**：先裁定 M2 的 P3-A4 证据落点（隔离 home 是否可接受），再决定是否动 `~/.moshi`；合成数据面只能用于 P3-A4 自身，不得外溢到 P1-19/P1-20。
- **解决思路**：
  - A（隔离 home）：`tsx tools/seed-devdb.ts --home <临时 home>`，eval/doctor 由 seed 以同一 home 在进程内完成；在 §9.3/m2 明确标注“隔离 home · 合成数据面”。不改 `~/.moshi`。
  - B（清库重建）：先备份 `~/.moshi` 与 40 条 golden，再清库、移开 jianmu 会话目录后 seed；需用户明确授权，且要接受 P1-16 m2 证据重建。
  - C（暂不做）：P3-A4 m2 维持未跑。
- **影响范围**：P3-A4 的 m2 状态；P1-16 的 m2 golden；P1-19/P1-20 的数据面解释；`~/.claude/projects` 下真实会话的安全。
- **期望效果**：M2 的数据面来源、路径、可否作验收证据三件事在 §9.3 写清；不再出现“同一台机器两套库混读”。

## D-04 P3-A6 清理有效性的取证口径

- **问题**：M2 `edge=0`，`doctor --fix` 关闭反向 supersedes 0 条；单测 `edges.test.ts` 13/13。M2 既有“关闭 0 条”的读数，但没有“在有反向边的库上关闭 >0 条”的本机读数。注入单边反向边会关 0 条，因为 `closeReversedSupersedes` 要求存在活跃的正向孪生边。
- **原因**：M2 没有 P3-A6 修复前遗留的反向边；卡面没有定义“清理有效性”是否必须在有存量数据的库上正面证明；`--fix` 只接受 `--fix`，路径固定走配置的 `data_dir`。
- **解决方向**：先裁定 M2 的验收口径：是“无存量即通过”，还是必须在本机构造一次正面证明。
- **解决思路**：
  - A（无存量即通过）：以 M2 “0 条存量 + `--fix` 幂等 + I8 通过 + 13/13 单测”为证据，写 `DONE.m2`。
  - B（本地成对注入）：在 M2 临时 `data_dir`/副本库注入成对边（旧→新 + 新→旧）再跑 `--fix`，记录“关闭 N 条、id 保留、edge 总数不变、I8 通过”，并标注“合成副本证据”。
  - C（维持 WIP）：P3-A6 m2 继续 WIP，等待有真实形态数据的库出现。
  - 禁止：只注入反向边期待关闭 N 条；禁止依赖 M1 的库文件。
- **影响范围**：P3-A6 的 m2 状态；I8/doctor 结论；P3-A5 的验收口径。
- **期望效果**：清理逻辑在“有真实形态反向边”的数据上被证明，或在无存量时明确按幂等通过；M2 不因数据缺失而长期挂 WIP。
