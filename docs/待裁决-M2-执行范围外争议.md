## D-01 P1-20 的验收数据面与“四类全过”口径

- **问题**：M2 真实库 `edge=0`，`multi_hop` 恒 0/10；P1-20 卡要求“四类各 ≥8 且全过”。若改在种子库上跑，则是另一套数据面（四类各 8、32/32），与真实库结果不可互换。M2 同一节点存在“真实库 30/40”与“种子库 32/32”两种可能的判定，卡面、决策记录与台账没有统一。
- **原因**：真实库的边从未补齐（P2-22 只在新 harvest 批次抽边，存量事实无 backfill 入口）；多跳题的判定条件要求 `dependency_summary` 非空；种子库被当作补充证据使用，但它的 32 题结果不能代表真实库。
- **解决方向**：先确定 P1-20 在 M2 的唯一数据面与唯一判定线，再决定是补真实边、用真实语料重出题，还是修改“全过”的验收口径。
- **解决思路**：
  - A（真实库闭环）：补真实边——新 harvest 或存量 backfill——再跑四类题；multi_hop 必须由真实 `depends_on` 支撑。
  - B（真实语料重出题）：从 M2 真实会话重新导入，按新库重出四类各 ≥8 的 golden，再跑 P1-20。
  - C（口径降级）：明确接受“真实库多跳恒红”，把 P1-20 改为“非多跳三类全过 + 多跳仅要求判定可用”，记决策并同步 P1-19 的依赖。
  - 禁止：用种子库 32/32 直接写 `DONE.m2`；该结果不能作为真实库验收证据。
- **影响范围**：P1-16、P1-19、P1-20 的 m2 状态；B-1；P2 里程碑口径；P3-A4 的定位。
- **期望效果**：M2 的 P1-20 只有一套可复跑的数据面与判定线；`DONE.m2` 不再依赖“换了哪套库”。

## D-02 P1-19 主题导出与阶段依赖

- **问题**：M2 的 `selectTopics=0`，`export --all` 导出 0 篇；P1-19 的依赖是“全部”P1，P1-16、P1-20 未完成时它不可能完成。§9.3/m2 与 11-06 日志把 `multi_hop 0/10` 记成 P1-19 未过理由，属过度归因。
- **原因**：`topics.ts` 有两条过滤——`fact_count ≥ 8` 与 `chainCompleteness ≥ 0.5 || hasMutex`；M2 真实库 `edge=0`，社区划分退化为 57 个单节点社区，两条同时不满足。只下调 `MIN_FACTS` 不会改变第二条过滤的结果。
- **解决方向**：先解决真实库的边与社区密度，或明确修改主题过滤口径；在此之前 P1-19 在 M2 维持 `WIP`。
- **解决思路**：
  - A（补真实边）：新数据经 harvest 自然抽边，或为存量事实补 `extractEdges` backfill；社区规模与依赖链同时改善。
  - B（放宽口径）：同时下调 `MIN_FACTS` 并放宽/删除 `chainCompleteness || hasMutex` 过滤，记决策；这会削弱主题质量门禁，且仍需解释“无边的主题”是否可接受。
  - C（接受 WIP）：P1-19 继续 WIP，等 P1-20 与 B-2 解决后再收口。
  - 禁止：用隔离 home 的合成种子库结果作为 P1-19 的 m2 验收证据。
- **影响范围**：P1 阶段出口；归档功能；B-2；P1-19 的 m2 状态；P3-A4 的“合成数据面”边界。
- **期望效果**：`moshi export --all` 在真实库稳定导出 ≥1 篇主题文档，且导出内容与主题门槛可解释；P1-19 的未过理由只写“主题导出 0 / 依赖 P1-16、P1-20”，不写 multi_hop。

## D-03 P3-A4 数据面落点与清库代价

- **问题**：P3-A4 卡绑定“本机 `~/.moshi` 种子库”，要求有边、有裁决、有 feedback、有 query_log；M2 现有 `~/.moshi` 是 60 条直写事实（edge/annotation/adjudication 全 0，episode/session 全空）。`pnpm seed:devdb` 在默认 home 会被 `assertProjectsRootOwned`（jianmu 有 3 个 jsonl）与 `assertOwnedDb`（有 fact 但 episode=0）拒绝；用 `--home` 隔离可以跑通，但偏离卡定义；清库重建会覆盖 40 条 `golden.v1.jsonl` 为 32 条、丢 174 条 `query_log`，并破坏 P1-16 当前 m2 证据。
- **原因**：护栏按 episode 归属判库；旧库不是种子工具产物；seed 的 golden 生成器上限为四类各 8（32 条），无法产出 P1-16 需要的 40 条。
- **解决方向**：先裁定 M2 的 P3-A4 证据落点（隔离 home 是否可接受），再决定是否动 `~/.moshi`；合成数据面只能用于 P3-A4 自身，不得外溢到 P1-19/P1-20。
- **解决思路**：
  - A（隔离 home）：`tsx tools/seed-devdb.ts --home <临时 home>`，eval/doctor 由 seed 以同一 home 在进程内完成；在 §9.3/m2 明确标注“隔离 home · 合成数据面”。不改 `~/.moshi`。
  - B（清库重建）：先备份 `~/.moshi` 与 40 条 golden，再清库、移开 jianmu 会话目录后 seed；需用户明确授权，且要接受 P1-16 m2 证据重建。
  - C（暂不做）：P3-A4 m2 维持未跑。
- **影响范围**：P3-A4 的 m2 状态；P1-16 的 m2 golden；P1-19/P1-20 的数据面解释；`~/.claude/projects` 下真实会话的安全。
- **期望效果**：M2 的数据面来源、路径、可否作验收证据三件事在 §9.3 写清；不再出现“同一台机器两套库混读”。

## D-04 P3-A6 清理有效性的取证口径

- **问题**：M2 `edge=0`，`doctor --fix` 关闭反向 supersedes 0 条；单测 `edges.test.ts` 13/13。M2 既有“关闭 0 条”的读数，但没有“在有反向边的库上关闭 >0 条”的本机读数。注入单边反向边会关 0 条，因为 `closeReversedSupersedes` 要求存在活跃的正向孪生边。
- **原因**：M2 没有 P3-A6 修复前遗留的反向边；卡面没有定义“清理有效性”是否必须在有存量数据的库上正面证明；`--fix` 只接受 `--fix`，路径固定走配置的 `data_dir`。
- **解决方向**：先裁定 M2 的验收口径：是“无存量即通过”，还是必须在本机构造一次正面证明。
- **解决思路**：
  - A（无存量即通过）：以 M2 “0 条存量 + `--fix` 幂等 + I8 通过 + 13/13 单测”为证据，写 `DONE.m2`。
  - B（本地成对注入）：在 M2 临时 `data_dir`/副本库注入成对边（旧→新 + 新→旧）再跑 `--fix`，记录“关闭 N 条、id 保留、edge 总数不变、I8 通过”，并标注“合成副本证据”。
  - C（维持 WIP）：P3-A6 m2 继续 WIP，等待有真实形态数据的库出现。
  - 禁止：只注入反向边期待关闭 N 条；禁止依赖 M1 的库文件。
- **影响范围**：P3-A6 的 m2 状态；I8/doctor 结论；P3-A5 的验收口径。
- **期望效果**：清理逻辑在“有真实形态反向边”的数据上被证明，或在无存量时明确按幂等通过；M2 不因数据缺失而长期挂 WIP。

## D-06 M2 现有 60 事实库的来源与可用性

- **问题**：M2 的 `~/.moshi/moshi.db` 有 60 条事实，但 `episode=0`、`session=0`、`source_episode/session_id/turn/batch_id` 全空、`origin` 全 NULL，60 条 `created_at` 集中在 24ms 内，呈批量直写特征，不是 import/harvest 链路的形态。它是 M2 现有 golden、eval、bench 的全部数据基础。
- **原因**：旧库由早期脚本直接写入；P1-16 卡要求“题目基于真实导入数据”，台账 §9.2 又允许 seed 生成 golden；两种口径并存，导致“直写库是否可作验收数据面”没有结论。
- **解决方向**：明确该库的定位：保留为“旧直写库”并标注，或从真实会话重新 import 生成新库并重建 golden。
- **解决思路**：
  - A（保留并标注）：在 §9.3/m2 写清“旧直写库，非 import 链路”，后续读数都带此标注；P1-16 的 m2 只在台账口径下成立。
  - B（重新导入）：从 M2 的真实 Claude 会话 `~/.claude/projects`（jianmu 3 个 jsonl）走 `moshi import` 生成新库，重建 golden 后再跑 P1-16/P1-19/P1-20。
  - C（隔离合成）：只在隔离 home 用 seed 生成 P3-A4 专用库，不触碰 `~/.moshi`。
- **影响范围**：所有以 M2 库为数据面的读数（P1-16/P1-19/P1-20/P3-A4/P3-A6）；golden 的有效性。
- **期望效果**：M2 每个验收结论都能追溯到“哪份库、哪条链路产生”；不再把直写库当作真实导入库使用。

## D-08 阶段验收口径：任务卡完成 vs 真实数据面闭环

- **问题**：P2 收口验收（5k 图、导出二次一致性、两遍扫描计数不变）全部在种子库完成，真实库 `edge=0`、`export=0`、多跳 0/10，但 Phase 2 仍记“完成”。P3 目前又在用同一方式推进 P1-20/P1-19。P2 审查报告 Z-11 已把这种情况定义为“任务卡层完成，不是里程碑层完成”。
- **原因**：台账同时存在“任务卡 DONE”和“里程碑出口”两种口径，§1 快照只体现前者；种子库读数被当成数据面闭环的证据。
- **解决方向**：把阶段状态拆成“代码/任务卡完成”与“真实数据面闭环”两个口径，并在 Phase 3 收口前明确真实库闭环是否为硬前置。
- **解决思路**：
  - A（拆口径）：§1 快照与阶段表增加“数据面闭环”列；种子库证据只能填“代码完成”，不能填“闭环完成”。

- **影响范围**：Phase 2/3 的状态与出口；用户对进度的判断；P1-19/P1-20/P3-A4 的验收方式。
- **期望效果**：台账不再出现“种子库全绿 = 阶段完成”的误读；真实库闭环的缺口在 §1 一眼可见。
