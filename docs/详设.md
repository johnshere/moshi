### 0.3 约定用语

| 词 | 含义 |
| --- | --- |

| **SHOULD / 应当** | 默认这么做，偏离要在此处写明理由 |

**数值精度约定**：`confidence` / `strength` / `importance` / `weight` 一律存 `REAL`，**写入前四舍五入到 4 位小数**（`Math.round(x*1e4)/1e4`）。浮点比较一律用 `Math.abs(a-b) < 1e-4`，禁止 `===`。

### 0.4 本版新增决策登记

以下是概设未定、由本版拍板的实现决策。**改动其中任何一条都会波及多个章节**，改之前先在任务台账里记一条决策记录。

| # | 决策 | 理由 | 波及 |
| --- | --- | --- | --- |
| **D1** | 时间一律存 **UTC ISO-8601 毫秒**（`2026-11-01T02:36:07.123Z`），展示层转本地 | 跨时区/夏令时不可比；字符串排序即时间排序 | §1.2 全部 |
| **D2** | ID = 前缀 + **ULID 小写**（`f_01j9z3k2m4n5p6q7r8s9t0`） | 可按时间排序、无中心分配、可读 | §1.1 |
| **D3** | `attrs` 拆 `frozen` / `ext` 两区，**用触发器守 frozen 不可变** | 不守则"append-only"承诺落空（原 §1.1 待修 #1） | §2.2 / §2.5 |
| **D4** | `edge` 用**活跃唯一索引** `UNIQUE(src,dst,etype) WHERE valid_to IS NULL`；`degree` 用**触发器**维护 + 视图校验 | 重复 harvest 不再写出重复边 | §2.2 / §2.5 |
| **D5** | `canonical_key` **禁止 NULL**：消解失败也给 provisional entity（`etype='unknown'`） | 否则幂等索引对未消解事实完全失效（待修 #3） | §5.5 |
| **D6** | `entity.merged_into` + **合并事务**（重算 key → 撞幂等 → 合并或 supersede） | 只写 alias 不会改变 `canonical_key`，合并无效（待修 #4） | §2.9 |
| **D7** | 新增 7 张表：`query_log` / `evidence_log` / `adjudication` / `training_sample` / `meta` / `session` / `ontology` | `[M#]` 回填、A/B 分组、成长曲线、GAT 标签全无处落地（待修 #5） | §2.2 |
| **D8** | `epistemic_status` 增 **`disputed`** | 概设 §4.3 第 2 条要求"落败者标记 disputed 但仍返回"，原枚举装不下 | §2.2 / §6.6 |
| **D9** | 谓词基数性**默认 `set`（不建互斥）**，只有白名单谓词默认 `single-valued` | 默认单值会让观测序列型谓词互斥爆炸（概设 §2.6 的 H1 风险） | §5.7 |
| **D10** | RRF 分数**先归一化到 [0,1] 再加两个信号** | 原始 RRF 分约 0.02–0.05，直接 +0.25 会让信号完全主导 | §6.4 |
| **D11** | FTS5 用**预分词**列：标识符切分 + CJK 二元组 | `unicode61` 对中文整段成一个 token，BM25 实际不可用 | §6.3 |
| **D12** | 装箱预算**单向借**：保底池未用满可借给效用池，反向不可 | 防高频事实挤掉关键约束（概设 §14.1 的下限意图） | §6.7 |
| **D13** | δ 应用后**必须重跑符号裁决**，结果翻转则丢弃 δ | K3：符号硬约束可覆盖神经高分 | §7.5 |
| **D14** | 社区 id 稳定性：新旧划分 **Jaccard ≥ 0.5 继承旧 id** | 否则归档 slug 每次重算都变，链接全断 | §8.3 |
| **D15** | sidecar 走 **unix domain socket / Windows 命名管道**，不走 TCP | 概设 §11.3 已定；避免端口占用与本地嗅探 | §4.6 |
| **D16** | 布局在**后台 worker 线程**算，前端只渲染 | 概设 §8.9 纪律 1：前端不做图计算 | §10.4 |

## 1 全局约定

### 1.1 标识符

```
<prefix>_<26 位 ULID 小写>
```

| 前缀 | 对象 | 生成位置 | 例 |
| --- | --- | --- | --- |
| `f_` | fact | `core/write/harvest` | `f_01j9z3k2m4n5p6q7r8s9t0ab` |
| `x_` | edge | 同上 | `x_01j9z3k2m4n5p6q7r8s9t0ac` |
| `en_` | entity | `core/write/resolve` | `en_01j9z3k2m4n5p6q7r8s9t0ad` |
| `ep_` | episode | `core/write/ingest` | `ep_01j9z3k2m4n5p6q7r8s9t0ae` |
| `ss_` | session | `core/write/session` | `ss_01j9z3k2m4n5p6q7r8s9t0af` |
| `q_` | query | `core/read/query` | `q_01j9z3k2m4n5p6q7r8s9t0ag` |
| `an_` | annotation | `core/write/ingest` | `an_01j9z3k2m4n5p6q7r8s9t0ah` |
| `au_` | audit | `infra/sqlite/audit` | `au_01j9z3k2m4n5p6q7r8s9t0ai` |
| `aj_` | adjudication | `core/write/conflict` | `aj_01j9z3k2m4n5p6q7r8s9t0aj` |
| `t_` | archive topic | `core/archive/topic` | `t_01j9z3k2m4n5p6q7r8s9t0ak` |

**ULID 实现**：`ulid` npm 包（`ulid()` 返回 26 位 Crockford Base32），统一 `monotonicFactory()` 单例，保证同毫秒内单调递增。

**不得使用**：自增整数（备份合并会撞）、UUIDv4（不可排序、索引局部性差）、内容哈希（内容变了 id 就变，破坏引用）。

### 1.2 时间

| 项 | 规则 |
| --- | --- |
| 存储格式 | `YYYY-MM-DDTHH:mm:ss.SSSZ`，**恒为 UTC**（`Z` 结尾），长度恒为 24 |
| 生成 | `new Date().toISOString()`（原生即此格式） |
| 比较 | 字符串比较即时间比较（同格式同长度），SQL 里直接用 `<` `>` |
| 展示 | 前端与归档用 `Intl.DateTimeFormat` 转本地时区，带 `+08:00` 偏移 |
| 解析 | `core/time.ts` 唯一入口 `parseTs(s): number`，非法输入抛 `E_TS_INVALID` |
| 禁止 | `datetime('now')`（SQLite 返回 UTC 但无毫秒、无 `Z`）、本地时区字符串入参 |

三个时间语义必须分清（概设 §2.2）：

| 字段 | 含义 | 来源 |
| --- | --- | --- |
| `valid_at` | 事实**在世界上**开始成立 | 工具调用时间戳；无则取 episode 时间 |
| `valid_to` | 事实**在世界上**结束成立 | 新观测的 `valid_at`（追加式失效） |
| `recorded_at` | **写入系统**的时间 | `now()` |

### 1.3 哈希与规范化 JSON

```ts
// domain/hash.ts
export function canonicalJson(v: unknown): string   // 键按 UTF-16 码点升序，无空格，不转义非 ASCII
export function sha256Hex(s: string): string        // 64 位小写 hex
export function shortHash(s: string, n = 32): string // 取前 n 位
```

**canonicalJson 规则**（MUST，因为触发器靠字符串相等判断 `frozen` 是否被改）：

1. 对象键排序：`Object.keys(v).sort()`（默认 UTF-16 序）；
2. 无多余空白：`{"a":1,"b":[1,2]}`；
3. 数字：整数不带 `.0`，浮点用 `Number.prototype.toString()`，禁止 `-0`（归一为 `0`）；
4. 字符串：只转义 `"` `\` 与控制字符，中文原样输出；
5. `undefined` / 函数 / Symbol：**抛错**，不静默丢弃（静默丢弃会让两个不同对象哈希相同）。

**身份键**（概设 §3.6.2 的落地）：

```
canonical_key = "ck1:" + shortHash(scope + "\u001f" + entity_id + "\u001f" + predicate, 32)
value_hash    = "vh1:" + shortHash(canonicalJson(value), 32)
```

- 前缀 `ck1:` / `vh1:` 是**格式版本**，将来改构成时换 `ck2:`，新旧可共存；
- 分隔符用 `\u001f`（Unit Separator），不会出现在正常文本里，避免拼接歧义；
- `predicate` 用**规范化后**的谓词（§5.4），不是原文。

### 1.5 错误码

统一 `MoshiError`，`code` 是稳定字符串，`httpStatus` 与 MCP 错误码由此映射。

```ts
export class MoshiError extends Error {
  constructor(
    readonly code: ErrorCode,
    message: string,
    readonly detail?: Record<string, unknown>,
    readonly retryAfterMs?: number,
  ) { super(message); }
}
```

| code | 触发 | HTTP | MCP | Agent 应如何理解 |
| --- | --- | --- | --- | --- |
| `E_INPUT` | 入参校验失败 | 400 | -32602 | 调用方写错了，不要重试 |
| `E_NOT_FOUND` | fact / topic 不存在 | 404 | -32602 | id 无效 |
| `E_IMMUTABLE` | 试图改 `content` / `attrs.frozen` | 409 | -32603 | 违反 append-only，改用新事实 |
| `E_CONFLICT_IDENTITY` | 幂等键冲突且无法自动合并 | 409 | -32603 | 需人工裁决，见 §2.9 |
| `E_BUSY` | 写队列满 / SQLITE_BUSY | 503 | -32603 | 可重试，带 `retry_after` |
| `E_DB` | 其他数据库错误 | 500 | -32603 | 服务端故障 |
| `E_SIDECAR` | sidecar 不可用 | 200（降级） | — | 走纯符号模式，`degraded:["no_sidecar"]` |
| `E_TIMEOUT` | 阶段超预算 | 200（降级） | — | 见 §6.10 |
| `E_SCHEMA` | `attrs` 违反已登记类型 | 422 | -32602 | 字段不合法，可能是调用方版本旧 |
| `E_QUARANTINED` | 写入被隔离 | 202 | — | 已接收但未入图，见 `quarantine` |
| `E_OP_EXPIRED` | 批量撤销窗口已过 / op 已作废 | 410 | -32602 | 不可重试；重新预览并确认即可，原操作已落盘（§10.6） |
| `E_CONFIG` | 配置非法 | 500（启动失败） | — | 进程不启动，写日志退出 |

**铁律**：MCP 层**只在"无法返回可用结果"时**抛错。任何能降级的情况都必须返回 `status:"ok"` + `degraded:[...]`（概设 §4.7）。

### 1.6 脱敏规则

写入前对所有入库文本（`content` / `attrs` / `episode.summary`）执行，**默认开启**，规则可配。

| 类型 | 正则（JS） | 替换 |
| --- | --- | --- |
| OpenAI 风格 key | `/\bsk-[A-Za-z0-9_-]{20,}\b/g` | `<REDACTED:API_KEY>` |
| GitHub token | `/\b(gh[pousr]_[A-Za-z0-9]{20,})\b/g` | `<REDACTED:GITHUB_TOKEN>` |
| AWS key | `/\bAKIA[0-9A-Z]{16}\b/g` | `<REDACTED:AWS_KEY>` |
| 私钥块 | `/-----BEGIN [A-Z ]*PRIVATE KEY-----[\s\S]*?-----END [A-Z ]*PRIVATE KEY-----/g` | `<REDACTED:PRIVATE_KEY>` |
| 通用赋值 | `/\b(password\|passwd\|pwd\|secret\|token\|api[_-]?key)\s*[:=]\s*("[^"]*"\|'[^']*'\|[^\s,;]+)/gi` | `$1=<REDACTED>` |
| Bearer | `/\bBearer\s+[A-Za-z0-9._-]{16,}/g` | `Bearer <REDACTED>` |
| 带用户名的绝对路径 | `/(\/Users\/\|\/home\/\|[A-Z]:\\Users\\)([^\/\\\s"']+)/g` | `$1<USER>` |
| 内网 IP（可选，默认关） | `/\b(10\.\d{1,3}\|192\.168\.\d{1,3}\|172\.(1[6-9]\|2\d\|3[01])\.\d{1,3})\.\d{1,3}\b/g` | `<REDACTED:PRIVATE_IP>` |

**顺序**：先私钥块（跨行，最贪婪），再具体 token，最后通用赋值——反过来会把私钥的头部吃掉，导致块匹配失败。

**脱敏后长度变化不影响 `value_hash`**：哈希在脱敏**之后**算，保证"同一个秘密两次观测得到同一个 key"，不会因原文微差产生两条事实。

### 1.7 单例与并发

- Node 单线程 + `better-sqlite3` 同步 API → **实际只有单写者**，不需要锁；
- 但同步调用会阻塞事件循环，因此**长任务必须分片**：每片 ≤ 15ms、≤ 200 行，片间 `await new Promise(r => setImmediate(r))`；
- `PRAGMA busy_timeout = 5000`；写事务用 `BEGIN IMMEDIATE`（避免升级锁死锁）。

## 2 数据模型（定稿）

### 2.1 关系

```
entity 1─n alias
entity 1─n fact ──(canonical_key)──> 同一身份的多条取值（互斥候选）
fact 1─n edge (src) ; fact 1─n edge (dst)
fact n─1 episode
episode n─1 session
fact n─1 community_summary (community_id, scope)
query_log 1─n evidence_log
query_log 1─n adjudication
fact 1─n audit (tbl='fact', row_id)
fact 1─1 layout
community_summary 1─1 archive_meta (topic_id = 稳定社区 id)
```

**没有物理外键的三处**（SQLite 外键不跨虚表，且删除成本高）：

- `fact_vec.fact_id` → `fact.id`：靠应用层在同一事务内维护；
- `fact_fts.fact_id` → `fact.id`：同上；
- `query_log.id` → `evidence_log.query_id`：**有**外键（普通表，保留）。

### 2.2 DDL v1

> 与旧版（概设 v0.4 附录 C）的差异全部来自 §0.4 的 D1–D9。**旧 DDL 已作废，不得再参照。**

```sql
-- ============ 0. 连接级 PRAGMA（每次打开连接都要设，不写进 DDL 文件） ============
-- journal_mode=WAL / synchronous=NORMAL / foreign_keys=ON / busy_timeout=5000
-- user_version 由迁移器维护，见 §2.7

-- ============ 1. 元信息 ============
CREATE TABLE meta (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
-- 约定键：schema_rev（单调递增，任何写入 +1）、layout_version、last_harvest_at、
--         last_export_at、last_infer_at、sidecar_model_version、embed_model

-- ============ 2. 实体与别名 ============
CREATE TABLE entity (
  id             TEXT PRIMARY KEY,
  canonical_name TEXT NOT NULL,
  etype          TEXT NOT NULL
                 CHECK (etype IN ('pkg','process','port','path','version',
                                  'service','concept','unknown')),
  scope          TEXT NOT NULL DEFAULT 'global',
  alias_count    INTEGER NOT NULL DEFAULT 0,
  first_seen_at  TEXT NOT NULL,
  merged_into    TEXT REFERENCES entity(id),
  UNIQUE (canonical_name, etype, scope)
);
CREATE INDEX idx_entity_merged ON entity(merged_into) WHERE merged_into IS NOT NULL;

CREATE TABLE alias (
  alias      TEXT NOT NULL,
  entity_id  TEXT NOT NULL REFERENCES entity(id),
  source     TEXT NOT NULL CHECK (source IN ('rule','vector','human')),
  confidence REAL NOT NULL DEFAULT 1.0 CHECK (confidence BETWEEN 0 AND 1),
  created_at TEXT NOT NULL,
  PRIMARY KEY (alias, entity_id)
);
CREATE INDEX idx_alias_alias  ON alias(alias);
CREATE INDEX idx_alias_entity ON alias(entity_id);

-- ============ 3. 轨迹与会话 ============
CREATE TABLE episode (
  id         TEXT PRIMARY KEY,
  session    TEXT,
  ts         TEXT NOT NULL,
  raw_hash   TEXT NOT NULL,
  raw_path   TEXT,
  summary    TEXT,
  agent      TEXT,
  cwd        TEXT
);
CREATE INDEX idx_episode_ts      ON episode(ts);
CREATE INDEX idx_episode_session ON episode(session);

CREATE TABLE session (
  id              TEXT PRIMARY KEY,
  agent           TEXT,
  cwd             TEXT,
  started_at      TEXT NOT NULL,
  ended_at        TEXT,
  turn_count      INTEGER NOT NULL DEFAULT 0,
  tool_histogram  TEXT,           -- JSON: {"Bash":42,"Read":18}
  summary         TEXT,           -- 确定性模板生成，非 LLM（§8.2）
  source_episodes TEXT,           -- JSON 数组
  summarized_at   TEXT
);
CREATE INDEX idx_session_cwd_time ON session(cwd, started_at);
CREATE INDEX idx_session_open     ON session(ended_at) WHERE ended_at IS NULL;

-- ============ 4. 事实（L0 主表） ============
CREATE TABLE fact (
  id                TEXT PRIMARY KEY,
  content           TEXT NOT NULL,
  ftype             TEXT NOT NULL CHECK (ftype IN ('semantic','episodic','conditional')),

  -- 置信侧：可重估、可覆盖，每次变更必须留 source + audit（概设 §3.6.3）
  confidence        REAL NOT NULL DEFAULT 0.5 CHECK (confidence BETWEEN 0 AND 1),
  confidence_source TEXT NOT NULL DEFAULT 'llm_claim'
                    CHECK (confidence_source IN ('llm_claim','tool_obs','user_confirm',
                                                 'gat_delta','human','derived','procedure')),
  strength          REAL NOT NULL DEFAULT 0.5 CHECK (strength BETWEEN 0 AND 1),
  importance        REAL NOT NULL DEFAULT 0.5 CHECK (importance BETWEEN 0 AND 1),
  pool              TEXT NOT NULL DEFAULT 'utility'
                    CHECK (pool IN ('utility','value_floor')),
  epistemic_status  TEXT NOT NULL DEFAULT 'active'
                    CHECK (epistemic_status IN ('active','archived','invalidated',
                                                'pruned','disputed')),
```

### 2.3 字段字典（只列非自明字段）

**`fact`**

| 字段 | 空 | 写入方 | 可变 | 说明 |
| --- | --- | --- | --- | --- |
| `content` | 否 | harvest | **永不** | 给人看的一句话要点；触发器阻断 UPDATE |
| `attrs` | 否 | harvest | 仅 `ext` | `{"frozen":{...},"ext":{...}}`，见下 |
| `confidence` | 否 | confidence.ts | 可（带 audit） | 必须同时写 `confidence_source` |
| `strength` | 否 | lifecycle/strength | 可（**只经** `factRepo.applyStrength`） | 生命周期字段，禁止入特征 |
| `pool` | 否 | packing 前由规则算 | 可 | `importance ≥ 0.7` 或谓词在白名单 → `value_floor` |
| `canonical_key` | 否 | identity.ts | 仅合并事务 | 变更只能由 §2.9 的合并流程触发 |
| `degree` | 否 | 触发器 | 自动 | 只读，校验用 `v_fact_degree` |
| `last_decay_at` | 否 | 每次读写 | 自动 | 惰性衰减基准点 |
| `community_id` | 是 | 巩固任务 | 可 | 未分区时为 NULL |

**`attrs` 结构（D3）**

```json
{
  "frozen": {
    "subject":   {"entity_id": "en_...", "name": "port:8080"},
    "predicate": "occupied_by",
    "value":     {"process": "node", "pid": 48213}
  },
  "ext": {
    "tool": "lsof",
    "argv": ["lsof", "-i:8080"],
    "raw_excerpt": "<REDACTED>",
    "steps": [ ... ]
  }
}
```

- `frozen` **只允许三个键**（`subject` / `predicate` / `value`），多一个都算结构错误；
- `ext` 自由扩展，`schema validate` 只校验**已登记**的键（§8.5）；
- `frozen` 必须能被 `canonicalJson` 稳定序列化——**写入前统一走 `serializeFrozen()`**，不直接 `JSON.stringify`。

**`edge`**

| 字段 | 说明 |
| --- | --- |
| `weight` | 结构权重，默认 1.0；`co_occur` 用共现次数归一，`mutually_exclusive` 恒 1.0 |
| `valid_at` | 关系成立的时刻（通常取较晚的一条事实的 `valid_at`） |
| `valid_to` | 关系失效时刻；**不删行** |

**`adjudication`**

| 字段 | 说明 |
| --- | --- |
| `decided_by` | `规则名@版本`，如 `mutex_by_confidence@1`。**这是算"哪条规则不可靠"的唯一分组键** |
| `outcome` | `NULL` = 尚未被检验；`upheld` = 后续观测支持；`overturned` = 被推翻（**这是 GAT 的正样本**） |
| `outcome_evidence` | 推翻它的新事实 id，用于人工复核 |

**`ontology`**

| 字段 | 说明 |
| --- | --- |
| `single_ratio` | 同一 `canonical_key` 下"只有 1 个不同取值"的 key 占比。**≥0.9 → single-valued**（§8.5 判据） |
| `distinct_values` | 该谓词全库不同取值数；> 50 且 `single_ratio < 0.3` → `series` |
| `promoted` | 1 = 已晋升为结构列（本版全部为 0，晋升在 v1.1） |

### 2.4 不变量（可断言）

以下每条都要有对应的单测或 `moshi doctor` 检查项：

| # | 不变量 | 检查方式 |
| --- | --- | --- |
| I1 | `fact.content` 从不变更 | 触发器 + `audit` 中不存在 `tbl='fact' AND field='content'` |
| I2 | `attrs.frozen` 从不变更 | 触发器 |
| I3 | 同一 `(canonical_key, scope, value_hash)` 只有一行 | 唯一索引 |
| I4 | 同一 `(src,dst,etype)` 只有一条活跃边 | 部分唯一索引 |
| I5 | `valid_to IS NULL` 的事实，其 `epistemic_status ∈ {active, disputed}` | `doctor` 查询 |
| I6 | `epistemic_status='invalidated'` 的事实必有 `valid_to` | 同上 |
| I7 | `degree` 等于活跃边计数 | `v_fact_degree` 对账 |
| I8 | 每条**活跃**（`valid_to IS NULL`）`supersedes` 边的 `dst.valid_at >= src.valid_to`（已关闭的边是历史记录，例如 `doctor --fix` 关掉的反向重复边，不参与判定）（有效期是半开区间 `[valid_at, valid_to)`，写入侧取代时 `旧.valid_to = 新.valid_at`，相等即首尾相接） | 查询断言 |
| I9 | `fact_fts` 行数等于 `fact` 行数；`fact_vec` 行数等于 `fact` 行数，或标记为降级（`vector_disabled`，或 `fact_vec` 存在但 0 行 = 从未编码，doctor 退出码 4） | `doctor` |
| I10 | 任何 `confidence` 变更在 `audit` 里都有对应行 | 抽样对账 |

### 2.5 触发器

```sql
-- I1：content 不可变
CREATE TRIGGER trg_fact_content_immutable
BEFORE UPDATE OF content ON fact
WHEN NEW.content IS NOT OLD.content
BEGIN SELECT RAISE(ABORT, 'E_IMMUTABLE: fact.content is append-only'); END;

-- I2：attrs.frozen 不可变（D3）
-- 依赖 canonicalJson 的稳定序列化；比较的是 JSON 文本
CREATE TRIGGER trg_fact_frozen_immutable
BEFORE UPDATE OF attrs ON fact
WHEN json_extract(NEW.attrs,'$.frozen') IS NOT json_extract(OLD.attrs,'$.frozen')
BEGIN SELECT RAISE(ABORT, 'E_IMMUTABLE: fact.attrs.frozen is immutable'); END;

-- I4 的兜底：边一旦关闭就不再复活（复活要新建行）
CREATE TRIGGER trg_edge_no_reopen
BEFORE UPDATE OF valid_to ON edge
WHEN OLD.valid_to IS NOT NULL AND NEW.valid_to IS NULL
BEGIN SELECT RAISE(ABORT, 'E_IMMUTABLE: closed edge cannot be reopened'); END;

-- degree 维护（D4）
CREATE TRIGGER trg_degree_ins AFTER INSERT ON edge
WHEN NEW.valid_to IS NULL
BEGIN
  UPDATE fact SET degree = degree + 1 WHERE id = NEW.src;
  UPDATE fact SET degree = degree + 1 WHERE id = NEW.dst;
END;

CREATE TRIGGER trg_degree_close AFTER UPDATE OF valid_to ON edge
WHEN OLD.valid_to IS NULL AND NEW.valid_to IS NOT NULL
BEGIN
  UPDATE fact SET degree = degree - 1 WHERE id IN (OLD.src, OLD.dst);
END;

CREATE TRIGGER trg_degree_del AFTER DELETE ON edge
WHEN OLD.valid_to IS NULL
BEGIN
  UPDATE fact SET degree = degree - 1 WHERE id IN (OLD.src, OLD.dst);
END;

-- 任何写入都推高 schema_rev（派生投影的新鲜度判据）
CREATE TRIGGER trg_rev_fact_ins AFTER INSERT ON fact
BEGIN
  UPDATE meta SET value = CAST(CAST(value AS INTEGER) + 1 AS TEXT) WHERE key = 'schema_rev';
END;
```

**触发器不是万能的**：`degree` 的增减依赖"边插入时 `valid_to` 为 NULL"。如果某条边以 `valid_to` 非空插入（补历史），触发器不计数——这是**故意**的，历史边不该计入当前度数。`doctor` 用 `v_fact_degree` 对账，不一致就重建。

### 2.6 视图与查询计划

```sql
CREATE VIEW v_fact_degree AS
SELECT f.id AS fact_id,
       (SELECT COUNT(*) FROM edge e
         WHERE e.valid_to IS NULL AND (e.src = f.id OR e.dst = f.id)) AS degree
FROM fact f;

CREATE VIEW v_active_fact AS
SELECT * FROM fact
WHERE epistemic_status IN ('active','disputed')
  AND (valid_to IS NULL OR valid_to > strftime('%Y-%m-%dT%H:%M:%fZ','now'));

CREATE VIEW v_orphan_ratio AS
SELECT CAST(SUM(CASE WHEN degree = 0 THEN 1 ELSE 0 END) AS REAL) / COUNT(*) AS ratio,
       COUNT(*) AS total
FROM fact WHERE epistemic_status IN ('active','disputed');
```

**索引选择说明**（避免实现时乱加索引）：

| 查询 | 走的索引 | 说明 |
| --- | --- | --- |
| 1 跳邻域 | `idx_edge_src` / `idx_edge_dst` | 双向各查一次，`UNION` 后过滤 `valid_to IS NULL` |
| 身份定位 | `idx_fact_key` | 一次查出一个 `canonical_key` 的全部取值 |
| 幂等写入 | `idx_fact_identity` | 唯一索引，`INSERT ... ON CONFLICT DO UPDATE` |
| 时态过滤 | `idx_fact_valid_range` | 范围扫描 |
| 列表分页 | `idx_fact_status_strength` | 按状态过滤 + 强度排序 |

**不要加**：`fact(content)` 索引（无前缀查询）、`edge(valid_to)` 单列索引（选择性太差）、`fact(created_at)`（时间过滤都走 `valid_at`）。

### 2.7 迁移

- 版本存 `PRAGMA user_version`；当前 `1`。
- 文件：`migrations/001_init.sql`、`002_xxx.sql`，**只增不改**——已发布的迁移文件改一个字都会导致线上库版本与文件不一致。
- 执行器 `infra/sqlite/migrate.ts`：

```
1. 读 user_version = v
2. 若 v == target → 返回
3. 若 v > target → 抛 E_CONFIG（不允许降级，概设 §2.3）
4. 若 v < target：
   a. VACUUM INTO backups/pre-migrate-<v>.db
   b. 依次执行 migrations/<v+1..target>.sql，每个文件包在一个事务里
   c. 每步后校验 user_version，不符即回滚并抛错
5. 完成后跑 doctor 的 I1–I10 检查
```

**迁移脚本三条纪律**：

1. 不写 `DROP TABLE`——要废弃的表改名 `_deprecated_<name>_<ver>`；
2. 加列必须有默认值或可空（SQLite 的 `ADD COLUMN` 不支持非常量默认）；
3. 数据迁移与结构迁移分开文件，便于回滚重跑。

### 2.8 幂等矩阵

写入时的四种情形，必须严格按此处理（概设 §3.3 第 2 步的落地）：

| 情形 | 判定 | 动作 | 返回 |
| --- | --- | --- | --- |
| **A. 全新** | `(canonical_key, scope, value_hash)` 无行 | 插入新 fact，`valid_to = NULL` | `created` |
| **B. 完全重复** | 有行且 `valid_to IS NULL` | **不新建**：刷新 `recorded_at`、`access_count+1`、按 §5.8 抬升 `confidence`（若来源更强）、写 `audit` | `refreshed` |
| **C. 复活** | 有行但 `valid_to` 非空 | 不复活旧行（触发器禁止），**插入新行** + 建 `supersedes` 边 | `recreated` |
| **D. 不同取值** | 同 `canonical_key` 有行，`value_hash` 不同 | 按基数性处理：`single-valued` → 旧行收口 + 新行 + `supersedes`；`series`/`set` → 直接新行，不建 mutex | `superseded` / `coexist` |

**"来源更强"的判定**（情形 B 用）：

```
rank: user_confirm(4) > tool_obs(3) > derived/procedure(2) > llm_claim(1) > gat_delta(0)
若 新来源 rank > 旧来源 rank → confidence = max(旧值, 新先验)，source 更新
若 相等 → confidence = min(0.99, 旧值 + 0.03)（重复观测的微弱加成）
若 更弱 → 不动 confidence，只记 access_count
```

### 2.9 实体合并事务（D6）

> **这是本系统唯一不可逆的操作**，必须整段在一个事务里，且写 `audit`。

输入：`winner_id`、`loser_id`、`operator`（`human` 或 `rule`）。

```
BEGIN IMMEDIATE
1. 校验：两者都存在、merged_into 均为 NULL、etype 相同（不同 etype 禁止合并）
2. 记 audit(tbl='entity', row_id=loser, before={merged_into:null}, after={merged_into:winner})
3. UPDATE entity SET merged_into = winner WHERE id = loser
4. 迁移别名：INSERT OR IGNORE INTO alias(alias, entity_id, source, confidence, created_at)
   SELECT alias, winner, 'human', confidence, now FROM alias WHERE entity_id = loser
5. 重算 loser 名下所有 fact 的 canonical_key：
   FOR EACH fact f WHERE attrs.frozen.subject.entity_id = loser:
     new_key = ck1(scope ‖ winner ‖ predicate)
     若 (new_key, scope, value_hash) 已存在 → 走"合并分支"
     否则 UPDATE fact SET canonical_key = new_key WHERE id = f.id
6. 合并分支（撞幂等键）：
   a. 保留 created_at 更早的那条为 survivor
   b. 另一条：valid_to = now, epistemic_status='invalidated', superseded_by = survivor
   c. 建边 loser_fact --supersedes--> survivor_fact
   d. survivor.confidence = max(两者)，写 audit
   e. 合并 ext：survivor.attrs.ext 以 survivor 为准，缺的键从 loser 补
      （注意：这一步会改 attrs，触发器只守 frozen，ext 可改，合法）
7. 重跑冲突检测：对受影响的 canonical_key 重新计算互斥对（§5.7）
8. UPDATE entity SET alias_count = (SELECT COUNT(*) FROM alias WHERE entity_id = winner) WHERE id = winner
9. UPDATE meta SET value = value+1 WHERE key='schema_rev'
COMMIT
```

**失败处理**：任一步抛错 → 整体回滚，返回 `E_CONFLICT_IDENTITY`，UI 显示"该合并会与 N 条既有事实冲突，需逐条确认"。

**拆分（回退）**：只允许回退到"未合并"状态——`UPDATE entity SET merged_into = NULL WHERE id = loser`，但**已重算的 `canonical_key` 不自动回滚**（因为可能已产生新事实）。UI 必须提示："回退只恢复实体，不恢复事实归属；如需完全回退请用备份。"这是刻意的保守设计：宁可让人多一步，也不要静默产生不一致。

### 2.10 图质量 SQL（概设 §10.2.1 六项）

```sql
-- 1 孤立节点比
SELECT CAST(SUM(degree=0) AS REAL)/COUNT(*) FROM fact WHERE epistemic_status IN ('active','disputed');

-- 2 社区模块度（需应用层算，见 §8.3；SQL 只给社区规模分布）
SELECT community_id, COUNT(*) c FROM fact WHERE community_id IS NOT NULL GROUP BY 1 ORDER BY c DESC;

-- 3 stale 依赖链：依赖的前置已失效、自身仍 active
SELECT COUNT(DISTINCT e.src) FROM edge e
JOIN fact s ON s.id = e.src JOIN fact d ON d.id = e.dst
WHERE e.etype='depends_on' AND e.valid_to IS NULL
  AND s.epistemic_status IN ('active','disputed')
  AND d.epistemic_status IN ('invalidated','pruned');

-- 4 近似重复比（需向量：同 canonical_key 下相似度 > 0.95 的不同 value_hash 对）
-- 走 fact_vec KNN，应用层统计，见 §11.3

-- 5 关键实体覆盖率（top50 高频实体中至少 1 条 active 事实的比例）
WITH top AS (
  SELECT json_extract(attrs,'$.frozen.subject.entity_id') eid, COUNT(*) n
  FROM fact WHERE epistemic_status IN ('active','disputed')
  GROUP BY 1 ORDER BY n DESC LIMIT 50)
SELECT CAST(SUM(CASE WHEN EXISTS(
         SELECT 1 FROM fact f2
         WHERE json_extract(f2.attrs,'$.frozen.subject.entity_id') = top.eid
           AND f2.epistemic_status IN ('active','disputed')) THEN 1 ELSE 0 END) AS REAL)
       / COUNT(*) FROM top;

-- 6 跨 scope 泄漏（v1.1 启用后才有意义）
SELECT COUNT(*) FROM query_log q JOIN evidence_log e ON e.query_id=q.id
JOIN fact f ON f.id=e.fact_id
WHERE q.flags_json LIKE '%"scope":"global"%' AND f.scope LIKE 'project:%';
```

### 3.5 并发与事务

| 场景 | 做法 |
| --- | --- |
| 单条写入（`memory_annotate`） | 一个事务，≤ 2ms |
| harvest 一批 | 每 200 条一个事务，片间 `setImmediate` 让出（≤15ms/片） |
| 查询 | 只读，**不开事务**（WAL 下读到一致快照） |
| 导出 | 先读快照（`schema_rev` 记下来），再在快照上渲染，避免边读边写 |
| 布局计算 | worker 线程，只读 DB 副本（`db.serialize()` 拿 buffer 后在 worker 里开新连接） |

**写队列**：`core/write` 内部一个 `p-queue`（并发 1），`memory_annotate` 入队即返回 `202` + `annotation_id`，不等待入图。这是概设 §3.3 的"只写缓冲"。

> 为什么是"被动观测为主、LLM 抽取为辅"，见 **概设 §3.0 / §3.1**；为什么内容不可改写、置信可重估，见 **概设 §3.6.3**。本节只写实现。

### 5.1 三条采集路径的落点

| 路径 | 入口 | 落到哪 | 延迟 |
| --- | --- | --- | --- |
| S1 协议埋点 | 扫描器解析会话里的 `moshi` 块（`core/collect/protocol.ts`） | `annotation`（`channel='harvest'`，`origin='agent_format@v1'`） | 分钟～小时 |

### 5.2 会话记录适配层

```ts
// core/adapters/session-source.ts
export interface SessionSource {
  readonly name: string;                 // 'claude-code' | 'generic-jsonl'
  detect(): Promise<{ found: boolean; root: string }>;
  listSessions(since: string): AsyncIterable<SessionRef>;

export interface RawTurn {
  ts: string;              // ISO8601
  sessionId: string;
  cwd?: string;
  role: 'user' | 'assistant' | 'tool';
  text?: string;           // 文本内容
  tool?: { name: string; input: unknown; output?: string; exitCode?: number };
```

#### 5.2.1 Claude Code 适配器

| 项 | 值 |
| --- | --- |
| 根目录 | `~/.claude/projects/` |
| 目录名 | cwd 的转义形式（`/` → `-`）。**不反解目录名**，从 JSONL 内部的 `cwd` 字段取 |
| 文件 | `<session-id>.jsonl`，一行一个事件 |
| 关键字段 | `timestamp`、`sessionId`、`cwd`、`type`、`message.content[]` |
| 内容块 | `{type:"text",text}` / `{type:"tool_use",name,input,id}` / `{type:"tool_result",tool_use_id,content}` |
| 工具结果配对 | 按 `tool_use.id` ↔ `tool_result.tool_use_id` 配对，**跨行配对需要一个小缓冲**（最多保留 50 个未配对 id） |

**防御式解析**（这是刻意的）：适配器 MUST 容忍未知字段与未知 `type`——平台会改版，硬编码字段名会在某次升级后静默失效。规则：

1. 只读上表列出的字段，其余忽略；
2. `type` 不认识 → 跳过该行，计数 `unknown_lines`；
3. `content` 不是数组 → 当作文本处理；
4. 任何字段缺失 → 用默认值（`ts` 缺失则用文件 mtime，`cwd` 缺失则 `null`）；
5. 解析失败率 > 20% → 写 `warn` 日志并在 `/api/diag` 显示"适配器可能已过期"。

`moshi doctor --probe-source` 会 dump 前 3 行的字段形状，供升级后快速核对。

#### 5.2.2 通用 JSONL 适配器

给其他 Agent 用：接受 `{ts, role, text, tool:{name,input,output,exit_code}, session_id, cwd}` 的最小约定。**字段名可配置**（`[ingest] field_map`），默认按上表。

#### 5.2.3 游标

`~/.moshi/cursors.json`：

```json
{ "claude-code": { "/Users/x/.claude/projects/-Users-x-proj/abc.jsonl":
  { "offset": 1048576, "last_ts": "2026-10-31T02:11:07.412Z",
    "size": 1048576, "inode": 12345 } } }
```

**三个必须处理的边界**：

| 情况 | 判定 | 处理 |
| --- | --- | --- |
| 文件被截断/轮转 | `size < 记录的 size` 或 `inode` 变化 | `offset = 0` 重读；靠 `episode.raw_hash` 去重 |
| 读到半行 | 最后一行无 `\n` | **不消费**，`offset` 停在该行开头 |
| 文件被删 | `stat` 失败 | 游标条目删除，不报错 |

**断点续读**：每次 `readEpisode` 返回的 turn 都先落 `episode`（带 `raw_hash = sha256(rawLine)`），再进解析。**episode 写入成功后才推进游标**——顺序反了会在崩溃时丢数据。

**`content` 生成规则**（统一模板，保证可读 + 可检索）：

```
"{subject.name} 的 {谓词中文标签} 为 {value 的简短形式}"      → 优先
"{subject.name} {谓词} {value}"                              → 兜底
```

`content` 上限 2 KB（`max_fact_bytes`），超了截断并只保留前两句 + `…`，同时 `importance` 不因截断变化（截断只影响可读性，不影响事实本身）。

**多事实拆分**（对应概设遗留问题）：一条命令输出里出现多个独立主体（如 `pip install` 装了 5 个包）→ **拆成 5 条事实**，共享同一个 `source_episode` 与 `valid_at`。同一主体多个属性（`node -v` 同时给出 major/minor/patch）→ **一条事实**，`value` 是对象。

### 5.4 规范化（`core/parse/normalizers.ts`）

| 函数 | 输入 → 输出 | 规则 |
| --- | --- | --- |
| `normalizePort` | `"8080"` / `":8080"` → `"port:8080"` | 去冒号，`1..65535` 校验，非法返回 `null` |
| `normalizePath` | `~/a//b/../c/` → `"~/a/c"` | 展开 `~`；`\`→`/`；折叠 `//`；纯词法消解 `.`/`..`（**不碰文件系统**）；去尾斜杠；win32 只把盘符小写 |
| `normalizePkg` | `Node.js` / `nodejs` / `node` → `"pkg:node"` | 小写；去 `@` 作用域分隔变体；别名表 `node.js/nodejs/node → node`、`py/python/python3 → python` |
| `normalizeVersion` | `v22.9.0` / `22.9` → `"22.9.0"` / `"22.9"` | `v?(\d+)\.(\d+)(?:\.(\d+))?(?:[-+].*)?`，缺 patch 就只保留两段 |
| `normalizeProcess` | `/usr/bin/Node` → `"node"` | 取 basename；去 `.exe`；win32 小写 |
| `normalizePredicate` | `"Installed Version"` → `"installed_version"` | 小写、空白→`_`、去非 `[a-z0-9_]`、连续 `_` 折叠 |

**别名表**（`normalizers.ts` 顶部常量，v1.1 移到 `ontology`）：

```ts
const PKG_ALIASES = { 'node.js':'node', 'nodejs':'node', 'node':'node',
                      'py':'python', 'python3':'python',
                      'golang':'go', 'postgres':'postgresql' };
```

**规范化失败不阻断**：`normalizePort("abc")` 返回 `null` → 该事实走 provisional 路径（§5.5），不丢弃。

### 5.5 实体消解（三级）

> 三级顺序与"向量级只建 alias 不合并"的理由见 **概设 §3.6.1**。

```
resolve(subject, type, scope):
  1. 规则级：
     name = normalize<Type>(subject)
     若 name 为 null → 走 3（provisional）
     entity = SELECT * FROM entity WHERE canonical_name = name AND etype = type AND scope = scope
       且 merged_into IS NULL
     命中 → 返回 entity，并 INSERT OR IGNORE alias(subject, entity.id, 'rule', 1.0)
     未命中 → 建新 entity（etype=type），alias(source='rule')
  2. 向量级（仅当规则级新建了实体时）：
     取 subject 的 embedding，KNN 查同 etype 的实体名向量 top-3
     相似度 ≥ 0.92 → INSERT alias(subject, 命中实体, 'vector', sim)   // 只建 alias，不合并
     0.60 ≤ sim < 0.92 → 写 pending_resolve（进 UI 队列，§8.3）
     sim < 0.60 → 什么都不做
  3. provisional：
     建 entity(canonical_name = rawSubject, etype='unknown')
     alias(source='rule', confidence=0.5)
     fact 的 identity 标记 identity='unresolved'（证据包里体现）
```

**为什么规则级失败也要建实体**（D5）：`canonical_key` 里含 `entity_id`，没有实体就没有 key，没有 key 就绕开幂等索引——每次 harvest 都新建一行。provisional 实体让 key 恒存在，消解完成时**只改 alias，不动 fact**。

**`entity.alias_count`** 在 alias 插入后重算（不是 `+1`，避免回滚后漂移）。

### 5.6 身份键

见 §1.3。三个实现约束：

1. `predicate` 用 `normalizePredicate` 后的值，**不是原文**——否则 `Installed Version` 与 `installed_version` 会算出两个 key；
2. `value` 用**脱敏后**的对象，且必须过 `canonicalJson`（不可序列化就抛 `E_INPUT`，不要静默降级成字符串）；
3. `scope` 进 key，Phase 0 恒为 `"global"`，**不允许**在 Phase 0 写别的值（写入时断言）。

### 5.7 冲突检测

#### 5.7.1 基数性判定（D9）

```ts
// core/write/conflict.ts
const DEFAULT_SINGLE_VALUED = new Set([
  'installed_version', 'runtime_version', 'package_manager', 'occupied_by',
  'git_branch', 'git_head', 'env_var', 'build_result', 'test_result',
]);
// 其余谓词默认 'set'（不建互斥），等 schema infer 晋升
function cardinalityOf(predicate: string, ontology?: OntologyRow): Cardinality {
  if (ontology?.cardinality) return ontology.cardinality;
  return DEFAULT_SINGLE_VALUED.has(predicate) ? 'single-valued' : 'set';
}
```

**这条默认值是刻意的**：默认 `single-valued` 会让"磁盘用量""构建次数"这类观测序列型谓词每两条就成互斥对，互斥边爆炸，且 §6.6 的裁决会把大量正常事实标成 `disputed`。默认 `set` 的代价是"漏报真冲突"，但漏报只会让 Agent 看到两条并存的事实（可自行判断），误报则会让它看到"已被裁决"的错误结论——**两者不对称，选漏报**。

#### 5.7.2 检测流程

```
detect(newFact):
  card = cardinalityOf(predicate)
  if card == 'set' → 不检测，直接插入
  siblings = SELECT * FROM fact
             WHERE canonical_key = newFact.canonical_key AND valid_to IS NULL AND id != newFact.id
  if card == 'single-valued':
     for s in siblings:
        if s.value_hash == newFact.value_hash → 跳过（幂等，§2.8 情形 B）
        else → 触发追加式失效：
          1. UPDATE s SET valid_to = newFact.valid_at,
                          epistemic_status = 'invalidated',
                          superseded_by = newFact.id, updated_at = now
          2. INSERT edge(s.id, newFact.id, 'supersedes', valid_at = newFact.valid_at)
          3. INSERT adjudication(kind='temporal_invalidate', fact_ids=[s.id,newFact.id],
                                 decided_by='single_valued_supersede@1')
          4. INSERT edge(s.id, newFact.id, 'mutually_exclusive', valid_at = ...)  // 保留冲突证据
  if card == 'series':
     // 新旧并存，只建 co_occur 边表示"同一主体的连续观测"
     INSERT edge(s.id, newFact.id, 'co_occur', weight = 0.5) ON CONFLICT DO NOTHING
```

**`mutually_exclusive` 边保留**：即使已裁决，冲突本身是信息（归档的「冲突与裁决」小节直接读它）。

#### 5.7.3 裁决（读取时，不在写入时）

写入只**记录**冲突与裁决快照；**裁决的"胜出者"在读取时按当前数据算**（§6.6）。原因：置信会变，写时算出的胜者会过期。

### 5.8 置信

#### 5.8.1 先验表

| 来源 | 内容类型 | 初值 | 说明 |
| --- | --- | --- | --- |
| `tool_obs` | 结构化直接观测（`exitCode===0` + 正则命中） | **0.95** | `lsof`、`node -v`、`test -f` |
| `tool_obs` | 从非结构化输出推断（`ps`、`ls`） | **0.85** | 有解析歧义空间 |
| `user_confirm` | 用户明确确认 | **0.98** | 金标签 |
| `llm_claim` | 模型陈述，无命令佐证 | **0.55** | 系统性过度自信，必须压 |
| `llm_claim` | 模型陈述且引用了命令/文件 | **0.65** | |
| `derived` | 巩固提炼 | `min(mean(源), 0.90)` | 不高于源均值 |
| `procedure` | 序列模式提炼 | **0.70** | 3 次重复才产出 |

**为什么 LLM 陈述只有 0.55**：概设 §3.6.3 已说明——初始置信是模型自评，没有共同标尺。0.55 让它进得了证据包（阈值 0.5），但排不到前面。

#### 5.8.2 重复观测的加成

```
第 k 次独立观测（同一 value_hash，不同 episode）：
  confidence = min(0.99, confidence + validate_bump)      // 默认 +0.05
  当 k ≥ 3 且来源均为 tool_obs → epistemic 可视为 validated，
  并触发 strength 的 floor 保底（§8.1）
```

"独立"的判定：`source_episode` 不同且 `|valid_at 差| > 60s`——同一秒内的两次输出是同一次观测。

#### 5.8.3 变更留痕

每次 `confidence` 变化 MUST 写 `audit`：

```json
{ "tbl":"fact", "row_id":"f_...", "field":"confidence",
  "before_json":"0.55", "after_json":"0.60",
  "source":"reobserve", "reason":"2nd independent tool_obs", "ts":"..." }
```

`confidence_source` 变化同样写 audit。UI 检查器的"上次是谁改的"直接读这张表。

### 5.9 隔离区

| 触发 | reason | 处理 |
| --- | --- | --- |
| `confidence < 0.25` | `low_confidence` | 写 `quarantine`，不入图 |
| `content` 超 2 KB 且截断后仍超 | `too_long` | 同上 |
| 控制字符占比 > 5% | `binary_like` | 同上 |
| `value` 不可 `canonicalJson` | `unserializable` | 同上 |
| 同一 `canonical_key` 24h 内出现 > 50 条不同取值 | `mutex_storm` | 同上 + 告警（消解或基数性出问题） |

隔离条目在 UI 里可见可批（`/api/queues/lowconf` 之外单开一栏），批量接受时按原 payload 重新入图。

### 5.10 harvest 事务

```
harvest(batchSize = 200):
  1. rows = SELECT * FROM annotation WHERE harvested_at IS NULL ORDER BY received_at LIMIT batchSize
  2. 对每行：
     a. 脱敏（幂等，重复脱敏无副作用）
     b. 解析 → ExtractedFact[]
     c. 逐条：resolve() → identity() → detect() → upsert()
     d. UPDATE annotation SET harvested_at = now WHERE id = ?
  3. 每 200 条一个事务，提交后 setImmediate 让出
  4. 结束时：
     - 更新 meta.schema_rev（触发器已做，逐行 +1）
     - 给受影响 canonical_key 的社区打 dirty（§9.5）
     - 写日志 {event:'harvest.done', scanned, created, refreshed, superseded, quarantined, ms}
```

**幂等**：重复跑同一批 annotation 不会产生新事实（`harvested_at` 已非空 + 幂等键）。中途崩溃 → 未提交的批次整体回滚，`harvested_at` 未推进，下次重跑。

**`upsert` 的 SQL 形态**：

```sql
INSERT INTO fact (...) VALUES (...)
ON CONFLICT (canonical_key, scope, value_hash) DO UPDATE SET
  recorded_at = excluded.recorded_at,
  access_count = fact.access_count + 1,
  confidence = MAX(fact.confidence, excluded.confidence),
  updated_at = excluded.updated_at
RETURNING id, (SELECT changes()) AS touched;
```

`RETURNING` 无法区分"插入"与"更新"，因此在 upsert 前先 `SELECT id FROM fact WHERE ...` 判断走哪条分支（§2.8 的四种情形），再做对应动作。**不要依赖 `changes()`**——它在 `DO UPDATE` 时也返回 1。

### 5.11 `moshi import`（开发者自用，不是产品入口）

> 产品不提供"人工整理后导入"的路径（概设 §3.1.2）。`import` 只保留给开发者做历史回填与联调，不进对外流程，也不写进客户接入文档。

```
1. 读 config 的 sources，逐个 detect()
2. 对每个 source：listSessions(since = --since 或 "1970-01-01")
3. 游标**从 0 开始**（不是从当前 offset）——这是与日常 harvest 唯一的差别
4. 分批：每批 500 turns，先落 episode，再解析入图
5. 每批结束打印进度：`imported 1200/8400 turns, 340 facts, 12 quarantined`
6. 全程限速：每秒 ≤ 20 条事实（避免首次导入把 UI 卡死）
7. 结束：重建 FTS、向量索引、degree；跑一次 infer
```

**断点**：import 用独立的游标文件 `cursors.import.json`，与日常游标分开——否则一次 import 会把日常游标推到文件尾，丢掉中间的增量。

**退出条件**（概设 §12 Phase 0）：`import` 后事实数 ≥ 100 且 `node`/`nodejs` 归到同一实体。

### 5.12 采集协议与两阶段扫描

#### 5.12.1 埋点块格式（`ann-v1`）

会话里的一等公民是**块**：以 ` ```moshi ` 开头、` ``` ` 结尾，块内是 JSON（单行或格式化均可），同一 turn 允许多块。

```moshi
{"v":1,
 "facts":[{"subject":"daemon","predicate":"port","value":"53000",
           "content":"daemon 监听端口 = 53000","confidence":0.95,"source":"tool_obs"}],
 "edges":[{"from":"k:daemon.port","to":"k:proxy.noproxy","etype":"depends_on",
           "note":"curl 走代理导致回环请求失败"}]}
```

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| `v` | 是 | 版本号；**未知版本整块跳过**，不猜语义 |
| `facts[].subject/predicate/value` | 是 | 与 `memory_annotate` 同义；`content` 可省，省则用模板拼 |
| `facts[].confidence/source/ftype/valid_at` | 否 | 缺省 0.9 / `llm_claim`（`source` 取值见 §1.4） |
| `edges[].from/to` | 是 | 事实引用：`f:<fact_id>` 或 `k:<canonical_key>` |
| `edges[].etype` | 是 | 仅 `depends_on` / `co_occur` / `derived_from`（其余由生命周期层产生） |
| 单块上限 | — | facts ≤ 20、edges ≤ 20；超限截断并计数 |

解析顺序：定位块 → JSON 解析 → 字段校验 → 引用解析 → 归一（复用 §5.4）→ 写 `annotation`。**引用解析不到不丢边**，整条边进候选（`status='pending'`），等对应事实入库后再提升为活跃边。

#### 5.12.2 两阶段扫描

| 阶段 | 输入 | 做什么 | 产出 |
| --- | --- | --- | --- |
| **阶段 1（确定性）** | 每个 turn 的文本 | 找块、解析、归一 | `annotation`（`origin='agent_format@v1'`，置信取块内或 0.9） |
| **阶段 2（LLM 兜底）** | **没有块**的 turn，按 session 批量（≤ 40 turns） | 让模型按同一结构输出事实与边 | `annotation`（`origin='llm_scan@v1'`，置信 ≤ 0.6，全部 `status='pending'`） |

**顺序不可颠倒**：阶段 1 跑完才知道哪些 turn"没有块"。阶段 2 的成本闸——每 session 每天最多 1 次调用、日 token 预算可配、超预算即停（阶段 1 照跑）。

**为什么不把阶段 2 做成主力**：它把"当时知道为什么"的信息交给事后猜测，精度低且成本高；它存在的意义只有一个——客户 Agent 不遵守协议时，仍有数据进来。

#### 5.12.3 幂等键（重复扫描必须零副作用）

| 对象 | 键 | 冲突时 |
| --- | --- | --- |
| annotation（埋点） | `(session_id, block_hash)`，`block_hash = sha256(规范化块 JSON)` | 跳过，`dedup += 1` |
| annotation（归纳） | `(session_id, turn_start, turn_end, prompt_ver)` | 同上 |
| annotation（直写） | 现有 `dedup_key`（§2.8） | 同上 |
| fact | `(canonical_key, scope, value_hash)` 唯一索引 | 刷新置信与观测时间，不建行 |
| edge | `(src,dst,etype) WHERE valid_to IS NULL` 唯一索引 | 提升 `weight`，不建行 |

#### 5.12.4 游标

复用 §5.2.3 的文件游标；新增**块游标** `~/.moshi/cursors.blocks.json`：每个 session 记 `{turn_index, block_index, block_hash}`。**先写 `episode`，再推进游标**——顺序反了崩溃时会丢数据。

#### 5.12.5 失败语义

| 失败 | 降级码 | 处理 |
| --- | --- | --- |
| 块 JSON 畸形 | `ann_malformed` | 整块进 `quarantine`，计数 |
| 未知 `v` | `ann_version_unknown` | 跳过并计数，每天告警一次 |
| 引用解析不到 | `ann_ref_unresolved` | 边进候选 pending，不丢弃 |
| LLM 超时 / 限流 | `llm_scan_unavailable` | 该 session 本轮跳过，下轮重试 |
| 预算耗尽 | `llm_scan_budget_exhausted` | 阶段 2 停，阶段 1 照跑 |

#### 5.12.6 边抽取的最小规则集

与扫描同批执行，全部写 `edge.provenance`（迁移 `003_edges.sql` 新增该列）：

| 规则 | 判定 | 产出 | 置信 |
| --- | --- | --- | --- |
| 工具序列 | 同 session、同 cwd、相邻 `tool_use`（间隔 ≤ 5 min） | `depends_on` | 0.7 |
| 过程步骤 | 同一条 `procedure` 的 `attrs.steps[]` 相邻项 | `depends_on` | 0.85 |
| 同实体共现 | 同 subject 实体、时间差 ≤ 1h | `co_occur` | 0.5 |
| 时间序取代 | 同 entity+predicate，后者 `valid_at` 更晚且前者已失效 | `supersedes`（旧 → 新，与 §5.7.2 同向；已存在则跳过） | 0.9 |

**配额**：每个新事实最多 7 条边（5 `co_occur` + 2 `depends_on`），按 weight 截断；`supersedes` 不受配额限制（真值维护，不能省）。

> 三路召回与全局分流的理由见 **概设 §4.5**；两个重排信号的来源见 **概设 §4.5.1**；预算装箱的取舍见 **概设 §4.6**；失败语义见 **概设 §4.7**。本节给算法与参数。

### 6.1 总编排

```ts
async function query(q: QueryInput, ctx: Ctx): Promise<EvidencePack> {
  const t0 = now();
  const flags = ctx.flags.snapshot();          // {gat, self_attn, cross_attn, vector, bm25, ppr}
  const route = routeIntent(q.query);          // §6.2
  const queryId = `q_${ulid()}`;

  if (route === 'global') return globalPath(q, queryId, flags, t0);

  const ents   = recognizeEntities(q.query);                       // §6.3
  const cands  = await recall(q, ents, flags);                     // §6.4 三路
  const fused  = fuse(cands, q, ents);                             // §6.5 RRF + 两信号
  const sub    = buildSubgraph(fused, ctx.cfg.subgraph);           // §6.6
  const scored = flags.gat !== 'off'
    ? await scoreWithGat(sub, q, flags) : null;                    // §7.5
  const adj    = adjudicate(sub, scored);                          // §6.7 符号兜底
  const packed = pack(adj, ctx.cfg.packing);                       // §6.8
  const pack   = assemble(packed, adj, sub, queryId, t0);          // §6.9
  await logQuery(queryId, q, cands, fused, packed, pack, t0);      // §6.12
  return pack;
}
```

**阶段计时**：每步用 `performance.now()` 记到 `stage_ms_json`，用于 SLO 断言与回归分析。

### 6.2 意图分流

规则优先，命中不了默认 `local`（概设 §4.2：3ms 预算）。

| 判定 | 条件 | 结果 |
| --- | --- | --- |
| 全局 | 命中全局词 **且** 未识别到实体 | `global` |
| 局部 | 识别到 ≥ 1 个实体 | `local` |
| 局部 | 含具体标识符（端口号 / 路径 / 包名 / 错误码） | `local` |
| 默认 | 以上都不满足 | `local` |

```ts
const GLOBAL_WORDS = ['有哪些','哪些','整体','概况','总结','概览','风险','全貌',
                      'overview','summarize','summary','all','risks','landscape'];
const LOCAL_HINTS  = /(:\d{2,5}\b|\/[\w.-]+\/|\b[A-Z]{2,}_[A-Z_]+\b|\bE[A-Z]{3,}\b)/;
```

**"且未识别到实体"是关键**："8080 有哪些风险"含全局词但也含实体，走局部——因为实体存在时局部路径的召回质量更高，全局摘要反而丢细节。

### 6.3 实体识别

```
recognizeEntities(text, limit = 8):
  1. 抽取候选片段：
     - 端口：/\b:?(\d{2,5})\b/ → normalizePort
     - 路径：/(?:~|\.{1,2})?\/[\w./-]+/ → normalizePath
     - 标识符：/\b[A-Za-z][\w.-]{2,}\b/ → 原样 + normalizePkg 两种形态
     - 错误码：/\bE[A-Z]{3,}\b/
  2. 每个候选查 alias：SELECT entity_id, confidence FROM alias WHERE alias = ? ORDER BY confidence DESC
  3. 同一片段命中多个实体 → 按 alias.confidence 取前 2（不同 etype 的都要）
  4. 去重后截断到 limit
  5. 返回 [{entity_id, name, etype, matched_text, span}]
```

**最长匹配优先**：`pnpm-lock.yaml` 先整体匹配，再匹配 `pnpm`——否则会识别出两个实体，实体信号被稀释。

### 6.4 三路召回

三路**并行发起、各自超时、超时即丢弃**（概设 §4.2 末条）。

| 路 | 实现 | top-k | 预算 |
| --- | --- | --- | --- |
| 向量 | `sqlite-vec` KNN | 20 | 7ms |
| BM25 | FTS5 `bm25()` | 20 | 4ms |
| PPR | 内存图扩散（种子 = 向量 top-3） | 20 | 7ms |

#### 6.4.1 向量

```sql
SELECT fact_id, distance
FROM fact_vec
WHERE embedding MATCH ?
ORDER BY distance
LIMIT 20;
```

`?` 是 `Float32Array` 的 512 维（`EMBED_DIM`）查询向量（已 L2 归一化）。`distance` 是 L2 距离，转相似度 `sim = 1 - distance/2`（归一化向量的 L2 ∈ [0,2]）。

**降级**：`meta.vector_disabled = "1"` 或 sidecar 不可用 → `degraded:["no_vector"]`，只走 BM25 + PPR（PPR 种子退化为 BM25 top-3）。

#### 6.4.2 BM25（D11）

`tokenizeForFts(text)` 是**预分词**，写入与查询必须用**同一个函数**：

```
tokenizeForFts(text):
  1. 小写
  2. 标识符切分：按 [.\/_\-\s] 切，保留原串与各段
     "pnpm-lock.yaml" → "pnpm-lock.yaml pnpm lock yaml"
  3. camelCase 切分：EADDRINUSE → "eaddrinuse eaddr inuse"
  4. CJK：连续汉字串生成**二元组**（"本机开发环境" → "本机 机开 开发 发环 环境"）
     单字串原样保留
  5. 去停用词（"的","了","是","在","the","a","of"）
  6. 用空格连接
```

```sql
SELECT fact_id, bm25(fact_fts) AS score
FROM fact_fts
WHERE tokens MATCH ?
ORDER BY score
LIMIT 20;
```

查询串同样走 `tokenizeForFts`，多 token 用 `OR` 连接（`a OR b OR c`）——用 `AND` 会让长查询零命中。

**FTS 同步**：`fact` 插入/更新 `content` 后，在同一事务里 `DELETE FROM fact_fts WHERE fact_id=?; INSERT INTO fact_fts(fact_id,tokens) VALUES(?,?)`。

#### 6.4.3 PPR

只在**候选子图内**跑（概设 §4.5 硬约束），不碰全图。

```
ppr(seeds: fact_id[3], opts):
  1. 从 seeds 出发 BFS 2 跳，收集节点（上限 ppr_max_nodes=400）
     边只走 active（valid_to IS NULL），边类型权重：
       depends_on 1.0 / mutually_exclusive 1.0 / logic 0.8 / supersedes 0.6 / co_occur 0.4
  2. 构造稀疏邻接：A[i][j] = weight（双向）
  3. 初始化 p = 均匀分布，seed 权重 3 倍后归一化
  4. 迭代 iters 次（默认 20）或 ||p_new - p||₁ < 1e-4：
       p_new = (1-d)/N + d * (A_norm^T · p)
     d = 0.85
  5. 返回 p 的 top-20（排除 seeds）
```

**性能**：400 节点、平均度 6 → 2400 条边，20 次迭代约 3ms（Node 上）。超 7ms 直接返回当前结果并 `degraded:["no_ppr"]`。

### 6.5 融合（D10）

```ts
function fuse(cands, q, ents) {
  // 1) RRF
  const rrf = new Map<string, number>();
  for (const list of [cands.vector, cands.bm25, cands.ppr])
    list.forEach((id, i) => rrf.set(id, (rrf.get(id) ?? 0) + 1 / (60 + i + 1)));

  // 2) 归一化到 [0,1] —— 关键，否则下面的加成会完全主导
  const max = Math.max(...rrf.values());
  for (const [id, v] of rrf) rrf.set(id, v / max);

  // 3) 实体信号
  const entIds = new Set(ents.map(e => e.entity_id));
  // 4) 时序信号
  const temporal = parseTemporalIntent(q.query);   // {kind:'now'|'past'|'range', at?, from?, to?}

  for (const [id, base] of rrf) {
    const f = factById(id);
    let s = base;
    if (entIds.has(f.subjectEntityId)) s += 0.25 * f.entityAliasConfidence;
    s += 0.20 * recencyScore(f, temporal);
    rrf.set(id, clamp(s, 0, 1.5));
  }
  return [...rrf].sort((a, b) => b[1] - a[1]);
}
```

**`recencyScore`**：

| 意图 | 打分 |
| --- | --- |
| `now`（"现在"/"当前"/"今天"） | `valid_to === null ? 1.0 : 0.15`——**失效事实降权而非排除**（概设 §4.5.1 约束 2） |
| `past`（"以前"/"上次"/"之前"） | `valid_to !== null ? 1.0 : 0.4` |
| `range`（具体日期区间） | `区间重叠度`：`overlap / union` |
| 无时间词 | 0（不加成） |

**时间词表**：`现在|当前|目前|今天|now|current` → now；`以前|之前|上次|曾经|原来|past|before|previous` → past；`\d{4}-\d{2}(-\d{2})?` → range。

**为什么不归一化三路原始分**：概设 §4.5 已定——分数量纲不可比，归一化是伪科学。RRF 只用排名，天然免疫量纲问题。

### 6.6 子图构建

```
buildSubgraph(fused, cfg):
  1. seeds = fused 前 8 个
  2. BFS 2 跳，节点上限 64
     邻居扩展优先级（边类型）：mutually_exclusive > depends_on > supersedes
                                > logic > co_occur > derived_from
     同优先级按 edge.confidence 降序
  3. 边上限 192：先保留两端都在集合内的边，再按优先级 + confidence 截断
  4. 节点排序：seeds 按 fused 顺序在前，其余按 degree 降序
     —— 顺序稳定，否则 Python 侧下标每次不同，无法复现
  5. 返回 {nodes: Fact[], edges: Edge[]}
```

**排序稳定性是硬要求**：子图节点顺序进 GAT 的输入矩阵，顺序变了同一份数据会得到不同分数（浮点累加顺序），shadow 模式的对照就失去意义。**排序键必须是全序**：`(isSeed desc, fusedRank asc, degree desc, id asc)`。

### 6.7 符号兜底（五步，硬顺序）

> 顺序来自概设 §4.3，不可调换。

```
adjudicate(sub, scored):
  for each fact f in sub.nodes:
    // 1 时态失效
    if f.valid_to !== null && f.valid_to <= now:
        if !includeHistory → 排除
        else → flag 'historical'
    // 2 互斥冲突（只在同 canonical_key 内）
    group = groupBy(canonical_key) 中 f 所在的组
    if group.size > 1 && cardinality === 'single-valued':
        winner = argmax(confidence * strength)         // 见下
        if f !== winner → f.status = 'disputed', flag 'disputed'
        else → 记录 conflicts 条目 {a,b,resolved:winner.id,rule:'mutex_by_confidence@1'}
        // 写 adjudication（每对一次，去重）
    // 3 置信阈值
    if f.confidence < threshold(0.5) → 不进包，计数 low_confidence_dropped
    // 4 依赖链断裂
    if any(depends_on 前置).epistemic_status in ('invalidated','pruned')
        → flag 'stale_dependency'
    // 5 身份未定
    if f.entityType === 'unknown' → flag 'identity_unresolved'
  return sortedBy(finalScore)
```

**`finalScore` 的构成**（这是"GAT 与符号"的汇合点）：

```
base       = fusedScore(f)                       // §6.5 的融合分
neural     = scored ? (f.confidence + δ_f) : f.confidence
lifecycle  = 0.15 * f.strength                   // 生命周期在此生效，且只在此生效
finalScore = 0.55 * base + 0.30 * neural + lifecycle
```

**注意**：`strength` 只出现在 `finalScore` 的**最后一步**，且**从不进入子图特征**。这条在代码上由 `FEATURE_FIELDS` 白名单保证（§3.3）——`buildSubgraph` 输出的对象里根本没有 `strength` 字段。

**阈值取值**：`confidence < 0.5` 不进包。这个阈值与先验表的 0.55（LLM 陈述）配合——纯 LLM 陈述刚好能进，但排在后面。

### 6.8 装箱（D12）

```
pack(candidates, cfg):
  B        = 1500                      // token 总预算
  utilB    = B * 0.70 = 1050
  floorB   = B * 0.30 = 450
  perItem  = min(estimateTokens(content), 80)

  floorPool = candidates.filter(f => f.pool === 'value_floor')
  utilPool  = candidates.filter(f => f.pool === 'utility')

  // 1) 保底池先满足下限
  take floorPool 前 floor_min=2 条
  // 2) 保底池按 score*1.15 贪心填到 floorB
  // 3) 效用池按 score*1.0 贪心填到 utilB
  // 4) 单向借：floorPool 未用满 → 余额给 utilPool；反之不可
  // 5) 总量不得超 B；超则停止
```

**`estimateTokens`**：

```ts
const estimateTokens = (s: string) => {
  let cjk = 0, ascii = 0;
  for (const ch of s) (ch.charCodeAt(0) > 0x2e80) ? cjk++ : ascii++;
  return Math.ceil(cjk * 1.0 + ascii / 3.2);
};
```

中文 1 字 ≈ 1 token，英文 3.2 字符 ≈ 1 token——比 tiktoken 略保守，宁可少放一条也不超预算。

**单条超 80 token**：截断到 80 token，保留首句（到第一个 `。` 或 `. `），末尾加 `…`。**截断不改 `content` 本体**，只改入包副本。

**为什么不用背包 DP**：1500/80 ≈ 19 条上限，贪心的解与最优解差距 < 5%，而 DP 的复杂度与调试成本高一个量级（概设 §4.6.1 已定）。

### 6.9 证据包组装

```
assemble(packed, adj, sub, queryId, t0):
  1. m_id 按 packed 顺序从 1 连续分配
  2. evidence[] 逐条映射（§4.4 字段）
  3. conflicts 只保留"两端都在 evidence 里"的
  4. dependency_summary 取子图内 depends_on 边，最多 10 条
  5. topic_hint：取 evidence 中出现最多的 community_id，读 community_summary
     无摘要 → null + coverage:'partial'
  6. numbered_list：
       `[M{i}] ({confidence}, {valid_at 本地日期}{valid_to ? ' 至 '+date : ' 起'}) {content}`
       disputed 的加 `（存疑）` 后缀
  7. confidence_summary：
       max(confidence) ≥ 0.85 → 'high'
       ≥ 0.6 → 'medium'
       > 0 → 'low'
       空 → 'none' + advice:'无可靠记忆，请勿臆断'
  8. status：degraded.length ? 'degraded' : 'ok'
```

**`advice` 的措辞纪律**：只能说"无可靠记忆"，不能说"没有"或"不存在"——前者是记录边界，后者是事实断言（概设 §8.4 同一条纪律）。

### 6.10 全局路径

```
globalPath(q, queryId, flags, t0):
  1. SELECT * FROM community_summary WHERE scope = ? ORDER BY fact_count DESC LIMIT 5
  2. 无摘要 或 derived_at 早于 source_rev 对应版本 → coverage:'partial', degraded:['no_summary']
  3. 拼 topic_hint 数组（不是单条），每条带 moshi://topic/{slug}
  4. evidence = []（全局路径不返回单条事实）
  5. advice = '以下是主题概览；具体细节请按 topic 下钻'
  6. 预算 30ms（不跑 GAT、不跑召回）
```

**为什么不返回事实**：概设 §4.1——摘要只做入口。全局问题返回 5 条主题 + 下钻指针，让 Agent 自己决定看哪片。

### 6.11 会话内缓存

| 项 | 值 |
| --- | --- |
| key | `sha256(tokenizeForFts(normalizedQuery) + scope + JSON.stringify(flags))` |
| 命中条件 | key 相同 **或** 与缓存条目的查询向量余弦 ≥ 0.95 |
| TTL | 5 分钟 |
| 失效 | 该 scope 下任何 fact 写入/失效（`schema_rev` 变化）→ 全清 |
| 返回 | 原证据包 + `cached:true`，`query_id` **新生成**（否则 feedback 会串） |

**`query_id` 必须新生成**：缓存的证据包被复用时，`[M#]` 编号可能不同，用旧 `query_id` 回填会写错 `evidence_log`。

### 6.12 埋点（`query_log`）

每次查询（含缓存命中）写一行：

| 字段 | 内容 |
| --- | --- |
| `candidates_json` | `{vector:[ids], bm25:[ids], ppr:[ids]}`——**三路各自贡献**，A/B 分析的基础 |
| `fused_json` | `[{fact_id, rrf, entity_bonus, temporal_bonus}]` |

## 7 推理支路（Phase 3）

> 内核裁决见 **综述 §15.2**（`GAT → 交叉注意力 → FFN → Readout`）；启用双门槛见 **概设 §12 Phase 3**；正交化红线见 **概设 §5.2**；训练标签的循环性问题见 **综述 §16.2**。本节只写实现。

### 7.1 sidecar 生命周期

```
状态机：STOPPED → STARTING → READY ⇄ UNLOADED → STOPPED
                    ↘ FAILED（1h 内 3 次后停在 FAILED，mode 降为 off）
```

| 事件 | 动作 |
| --- | --- |
| daemon 启动 | 不拉起（冷启动 < 1s 靠这条） |
| 首次需要 embedding | 异步 `ensureStarted()`，本次查询降级返回 |
| 就绪 | 写 `~/.moshi/sidecar.ready`（`{pid, socket, embed_model, model_version, started_at}`） |
| 空闲 5min | `POST /unload` → 权重置 None + `gc.collect()`，进程保留 |
| 空闲 30min | `POST /terminate` → 进程退出 |
| 崩溃 | 重启计数 +1；≥3/h → FAILED + 告警日志（**不弹窗**，概设 §1.5 纪律 2） |

**Python 侧最小实现**：

```python
# sidecar/moshi_sidecar/server.py
import json, socketserver, gc, os
from .encode import Encoder
from .model import Scorer

class Handler(socketserver.StreamRequestHandler):
    def handle(self):
        req = json.loads(self.rfile.readline())
        try:
            if req["path"] == "/health":
                return self._ok(state.health())
            if req["path"] == "/encode":
                return self._ok({"vectors": state.encoder.encode(req["body"]["texts"]).tolist(),
                                 "dim": 512})   # = EMBED_DIM
            if req["path"] == "/score":
                return self._ok(state.scorer.score(req["body"]))
            if req["path"] == "/unload":
                state.unload(); return self._ok({"ok": True})
            if req["path"] == "/shutdown":
                state.unload(); return self._ok({"ok": True})
            if req["path"] == "/terminate":
                state.unload(); state.stopping = True; return self._ok({"ok": True})
        except Exception as e:
            return self._err(type(e).__name__, str(e))
```

**用 `socketserver` + 行分隔 JSON，不引 FastAPI**：sidecar 只有 6 个端点，引 Web 框架会多 40MB 常驻内存，直接顶破 §11.5 的"推理空闲 < 220MB"。

**推理运行时：一套 torch（D-143）**：`Encoder` 用 sentence-transformers 加载 BAAI 原版 `bge-small-zh-v1.5`（CLS pooling，Python 侧 L2 归一），`Scorer` 用 PyTorch + PyG，同进程共用一份 torch（概设 §11.2「避免第二套推理栈」）。**不用 ONNX Runtime**：ORT 自 1.20 起停发训练包、不能加载 `.pt`、消融变体要逐个导出，撑不住 §7.3–§7.4 与 P4-02；ONNX 是 v2 收敛目标（概设 §11.4）。P1-28 曾按 D-61 用 ONNX Runtime 实现嵌入，属于实现偏离，由 P3-A3 改回。

### 7.2 特征

见 §4.5 的 522 维定义（`EMBED_DIM + 10`）。实现约束：

| 项 | 规则 |
| --- | --- |
| embedding | `F.normalize(tensor, p=2, dim=-1)`，**必须**在 Python 侧重做一次——Node 侧可能有浮点误差 |
| `degree` 归一化 | `log1p(d) / log1p(64)`，`d > 64` 截断到 1.0 |
| one-hot | 顺序固定，**从 `moshi_sidecar/features.py` 的常量读**，与 TS 侧 `domain/enums.ts` 对齐 |
| padding | 节点数补到 64（`max_nodes`），`mask[i]=0` 表示 padding；边补到 192，`edge_mask` 同理 |
| 缺 embedding | 用零向量 + `has_embedding=0` 标记（**不加维度**，用 confidence 折半代替） |

**契约测试（必须有）**：Node 侧构造一个 3 节点 2 边的子图，断言 Python 侧读出的 `x.shape == (1, 64, 522)`、`mask.sum() == 3`、`edge_index.shape == (2, 192)`、`edge_mask.sum() == 2`，并断言 Python 侧 `NODE_FEAT_DIM` 与 TS 侧相等。这条测试挂了，说明两侧已经对不上。

### 7.3 模型

```python
# sidecar/moshi_sidecar/model.py
import torch, torch.nn as nn
from torch_geometric.nn import GATConv

class MoshiScorer(nn.Module):
    def __init__(self, in_dim=522, q_dim=512, hidden=128, heads=4, edge_dim=16, delta_cap=0.15):
        # in_dim = NODE_FEAT_DIM、q_dim = EMBED_DIM，均从 features.py 常量传入，不写死
        super().__init__()
        self.delta_cap = delta_cap
        self.inp  = nn.Linear(in_dim, hidden)
        self.gat1 = GATConv(hidden, hidden // heads, heads=heads, edge_dim=edge_dim, concat=True)
        self.gat2 = GATConv(hidden, hidden, heads=1, edge_dim=edge_dim, concat=False)
        self.ln1, self.ln2 = nn.LayerNorm(hidden), nn.LayerNorm(hidden)
        self.q_proj = nn.Linear(q_dim, hidden)
        self.xattn  = nn.MultiheadAttention(hidden, num_heads=4, batch_first=True)
        self.ln3    = nn.LayerNorm(hidden)
        self.ffn    = nn.Sequential(nn.Linear(hidden, hidden*2), nn.GELU(),
                                    nn.Dropout(0.1), nn.Linear(hidden*2, hidden))
        self.ln4    = nn.LayerNorm(hidden)
        self.head   = nn.Sequential(nn.Linear(hidden, 64), nn.GELU(), nn.Linear(64, 2))

    def forward(self, x, edge_index, edge_attr, edge_mask, node_mask, query_vec, self_attn=False):
        h = self.inp(x)
        h = self.ln1(h + self.gat1(h, edge_index, edge_attr))       # 残差 + LN
        h = self.ln2(h + self.gat2(h, edge_index, edge_attr))
        if self_attn:                                                # 默认关（综述 §15.2）
            h = self.ln3(h + self.xattn(h, h, h, key_padding_mask=~node_mask)[0])
        if query_vec is not None:                                    # 查询交叉注意力
            q = self.q_proj(query_vec).unsqueeze(1)
            h = self.ln3(h + self.xattn(q, h, h, key_padding_mask=~node_mask)[0])
        h = self.ln4(h + self.ffn(h))
        out = self.head(h).squeeze(0)                                # (N, 2)
        delta = torch.tanh(out[:, 0]) * self.delta_cap
        return delta, out[:, 1]                                      # (delta, overturn_logit)
```

**参数规模**：约 **26 万**。概设 §5.1 的 1–6M 只作**上限参考**，首版取小是有意的——1M 以上在这个数据量上必然过拟合。

**两个输出头**（对应综述 §16.2 的语义修正）：

| 头 | 语义 | 标签来源 | 用途 |
| --- | --- | --- | --- |
| `delta` | 置信修正 | `feedback` 的 pairwise | `gat_mode='on'` 时改排序 |
| `overturn_logit` | 符号裁决被推翻的概率 | `adjudication.outcome` | 两个用途：① 训练主信号；② `on` 时若 > 0.5 则**不下调**该事实的置信（保守） |

**为什么必须两个头**：综述 §16.2 已证——`delta` 的标签是循环的（Agent 的 verdict 训 GAT，GAT 再修 Agent），上限是复现。`overturn_logit` 的标签由世界产生，是唯一非循环信号。两个头共用躯干，但**只有 `overturn` 头能在冷启动期训练**。

### 7.5 门控与 δ 应用（D13）

```
applyDelta(fact, delta, overturnProb):
  1. 若 |delta| > delta_cap → clamp
  2. cand = clamp(fact.confidence + delta, 0, 1)
  3. 若 overturnProb > 0.5 且 delta < 0 → 丢弃（不确定就别下调）
  4. 用 cand 重跑符号裁决（只针对该 fact 所在的互斥组）
  5. 若裁决结果翻转（原来的胜者变成落败）→ 丢弃 δ，保留原值
  6. 否则：confidence = cand，confidence_source = 'gat_delta'
     写 audit {field:'confidence', source:'gat_delta', before, after, reason:'model:<ver>'}
```

**第 5 步是 K3 的代码化**：符号硬约束可以覆盖神经高分。这条不做，GAT 训练几轮后会把互斥裁决全推翻，而它没有能力做这件事。

### 8.1 强度（惰性衰减）

```ts
// core/lifecycle/strength.ts
const HALF_LIFE_MS = { default: 14 * 864e5, procedure: 60 * 864e5 };

export function applyStrength(f: Fact, event: StrengthEvent, now: number): number {
  let s = f.strength;
  // 1) 先补衰减（惰性，读时算）
  const h = HALF_LIFE_MS[isProcedure(f) ? 'procedure' : 'default'];
  const dt = Math.max(0, now - Date.parse(f.lastDecayAt));
  s = s * Math.exp(-Math.LN2 * dt / h);
  // 2) 再按事件调整
  switch (event.kind) {
    case 'adopt':     s = s + 0.15 * (1 - s); break;      // 饱和增量
    case 'reject':    s = s * 0.70; break;                // 乘性惩罚
    case 'validate':  s = Math.max(s, 0.60); break;       // 独立验证设下限
    case 'none':      break;
  }
  return clamp(s, 0, 1);
}
```

**三个实现约束**（概设 §5.5.1 的三条细节）：

1. **惰性**：不在后台扫全表。查询返回前、写入后各算一次，`last_decay_at = now` 只在值变化超过 `1e-3` 时写回——否则每次读都写库，WAL 会爆。同一条阈值也约束**事件路径**（P2-08 收口补注，D-106）：`adopt` 在 `s ≥ 0.9933` 时增益小于 `1e-3` 会静默不落库（`changed = false`，返回库内旧值），`validate` 在 `s > 0.6` 时同理——这是惰性写回的既定语义，不是丢事件。另外，读路径的「算一次」口径是**候选集**：被 `includeHistory=false` 过滤掉的失效行、以及不在候选并集内的子图邻居，其 `strength` 允许滞后（邻居陈旧值仍以 0.15 权重进入裁决分），边界见台账 I-22。
2. **失效事实衰减到 0**：`valid_to !== null` 时 `s = 0`，但行保留。
3. **淘汰是软删**：`epistemic_status='pruned'`，物理删除只能由用户显式触发（`/api/privacy/purge`），且写 `audit`。

**批量重算**（`moshi db rebuild-strength`）：一次遍历全表，纯计算不写库，最后按 200 行一批写回。

#### 8.3.1 情景 → 语义提炼

产出：

```

```

幂等：`ext.derived_from` 相同 → 不重复产出。同时建 `derived_from` 边指向每条源事实（只读溯源）。

**红线**：不改源事实、不删源事实、不把源事实标 `archived`（除非用户在 UI 里批）。

> **P2-09 实现补注（D-107 ~ D-112）**：
> - 分组 SQL 实建时**显式带上 `scope`**（`GROUP BY canonical_key, scope`）：`canonical_key` 虽已把 scope 混进哈希（§1.1），分组行里保留 scope 可以让后续 `invalidate` / 建边不用反解哈希。
> - 产出模板的 `{value}` 位实现为**取值集合**：`attrs.frozen.value = { consolidated: true, observations: n, values: [...] }`（`values` 按 `canonicalJson` 排序；去重不必做，见下句），`value_hash = valueHash(聚合结构)`。原因：同值重复观测会被 harvest 的幂等情形折叠成一行，所以「同 key ≥3 条活跃 episodic」的组内**取值必然互不相同**；照字面取某一条源值会与活跃源行撞 `idx_fact_identity(canonical_key, scope, value_hash) WHERE valid_to IS NULL`。
> - 要点行用 `confidence_source = 'derived'` 标记「这是归纳不是观测」（不额外加 ext 标记）；`strength/importance/pool` 沿用 `draftToFact` 默认值，`source_episode = NULL`。
> - 幂等与重算：`ext.derived_from = sha256(sorted(ids).join('\n'))`（与 id 顺序无关）。**源集合变化时重算**——新要点插入，同 key 下已存在的活跃派生要点 `invalidate(..., supersededBy: 新要点)` 收口；源事实一条不动（红线）。
> - 只取 `active` 源：`disputed` 不是已验证观测（概设风险表 §5.5.2），不参与提炼；正文的 `n` 是**不同取值数**（同值观测已被 harvest 折叠，I-25）。
> - 撤回语义：同 key + 同指纹的派生点被**人工否决**过 → 不再重建（墓碑）；源撤回导致活跃源 < 阈值 → 反向对账收口，并写 `rule:consolidate_reconcile` audit（不算人工否决，源恢复后仍可重新产出）。失效入口（批量 / PATCH / memory_correct）会定向触发一次对账，每轮巩固开头也扫一遍。
> - `content` 遵守 2 KB 上限：先按 §5.3 的「前两句 + …」截断，单句超长时按 UTF-8 字节安全硬截；`attrs.frozen.value` 保留全量聚合取值。
> - 限速落在**组之间**（每秒 20 组），`--rate 0` 关闭；巩固在 `startHarvestRunner` 每轮 harvest 之后串行执行，默认开启，异常只记日志不冒泡（写入闭环是主线）。

### 8.4 社区划分（Louvain + 稳定性，D14）

```ts
// core/lifecycle/community.ts
export function recomputeCommunities(db: Db): void {
  const g = buildGraphology(db);            // 只取 active/disputed 事实与活跃边
  const raw = louvain(g, { resolution: 1.0, randomWalk: false });

  // 稳定性映射：新社区 ↔ 旧社区按 Jaccard 匹配
  const oldMap = loadOldAssignment(db);     // fact_id → community_id
  const mapping = new Map<number, number>();
  const overlaps = jaccardMatrix(raw, oldMap);
  for (const [newId, [oldId, j]] of overlaps) {
    if (j >= 0.5 && !mapping.has(oldId)) mapping.set(newId, oldId);
  }
  const nextId = () => Math.max(0, ...oldMap.values()) + 1 + (counter++);
  for (const newId of new Set(Object.values(raw))) {
    if (!mapping.has(newId)) mapping.set(newId, nextId());
  }

  // 写回（分批）
  for (const [factId, newId] of Object.entries(raw)) {
    db.prepare('UPDATE fact SET community_id = ? WHERE id = ?').run(mapping.get(newId)!, factId);
  }
  bumpMeta(db, 'community_rev');
}
```

**Jaccard ≥ 0.5 继承旧 id**：这是归档 `slug` 稳定的前提。不继承的话，每次重算社区 id 都变，`archive_meta.topic_id` 失效，所有文档路径全断——这是"归档文件反复改名"风险的直接来源（概设 §13）。

**触发**：每周一次，或用户点"重建"。全量 10k 事实目标 < 60s（概设 §1.7）。

```ts
  { name:'layout',      after:'export',    priority:50, run: runLayout },
  { name:'backup',      cron:'0 3 * * *',  priority:5,  run: runBackup },
];
```

| 规则 | 值 |
| --- | --- |
| 并发 | 1（单写者，串行） |
| 限速 | 每任务 20 条/秒 |
| 抢占 | **不抢占**——查询永远优先，任务在片间 `setImmediate` 让出 |
| 错过 | 进程未运行则跳过，不补跑（harvest 有游标，下次自然补齐） |
| 超时 | 单任务 10 分钟硬超时，超时写 `warn` 并跳过 |

**`meta.last_harvest_at` 必须更新**，`/api/diag` 与首次引导页都读它。

## 9 归档

> 为什么导出单元是主题、为什么保留「已失效」、为什么人工修改优先，见 **概设 §9.1 / §9.2 / §9.4 / §9.5**。本节给渲染与台账实现。

### 9.1 主题选取

```
selectTopics():
  1. 候选 = 所有 community_id 非空的社区
  2. 过滤：fact_count >= 8（min_facts）
     且（依赖链完整度 >= 0.5 或 存在 mutually_exclusive 边）
  3. 依赖链完整度 = 有 depends_on 入边或出边的事实数 / 总事实数
  4. 排序：fact_count desc
```

**低价值主题不导出**（概设 §9.2）——归档一旦什么都收就没人读。

### 9.2 slug

```
slug = sanitize(label)          // 去 / \ : * ? " < > |，空白→-，截断 40 字符
       若冲突 → slug + '-' + shortHash(topic_id, 6)
```

**slug 由 `topic_id` 派生，不随标题变**（概设 §9.2）。`label` 变了只更新 frontmatter 的 `topic`，**不改路径**。

### 9.3 渲染（分节 → 数据来源）

| 小节 | 数据来源 | 条数上限 |
| --- | --- | --- |
| 一句话结论 | 社区内 `confidence × importance` 最高的一条 | 1 |
| 关键事实 | 按 `finalScore` 排序，带置信与起始日期 | 15 |
| 依赖链 | `depends_on` 边，`A → B → C` 文本化 | 10 |
| 冲突与裁决 | `mutually_exclusive` 边 + 对应 `adjudication` | 10 |
| 时间线 | 按 `valid_at` 排序的变更（新增/失效/置信变化） | 20 |
| 已失效 | `valid_to` 非空的事实 | 20 |
| 未解决/待验证 | `identity_unresolved` 或 `stale_dependency` | 10 |
| 本次更新 | 与上次导出的 diff（新增 N / 失效 M / 置信变化 K） | — |
| 溯源索引 | `episode_id + span` 列表，**不含原文** | 20 |

**`content_hash`**：

```
content_hash = sha256( 渲染后的正文（不含 frontmatter 的 derived_at / revision / content_hash） )
```

只对正文算，否则每次导出 `derived_at` 都变，hash 永远不同，"内容未变则不写盘"就失效了。

### 9.4 增量与人工保护

```
exportTopic(topic):
  1. target = archive_dir/topics/<slug>/<slug>.md
  2. 若 target 存在：
       diskHash = sha256(readFile(target) 的正文)
       若 diskHash !== archive_meta.content_hash → 人工改过
           → 写 <slug>.proposed.md，human_edited=1，不覆盖
           → 日志 warn 'archive.human_edited'
           返回
  3. 渲染新正文，算 newHash
  4. 若 newHash === archive_meta.content_hash → **不写盘**（保留 mtime）
  5. 写盘：先写 .tmp 再 rename（原子）
  6. revision += 1；若 revision % 5 === 0 → 复制到 _history/<slug>@<date>.md
  7. 更新 archive_meta
```

**`.proposed.md` 三选一**（`POST /api/archive/proposed/:slug`）：

| action | 行为 |
| --- | --- |
| `accept_auto` | 用自动版覆盖，清 `human_edited`，revision+1 |
| `keep_human` | 把人工版 hash 记为基线，**此后该主题不再自动导出**（`human_edited=2` 表示"永久人工"） |
| `promote_human` | 人工版转正为基线并继续受保护（`human_edited=1`，`content_hash=人工版 hash`）；后续自动更新只刷新 `.proposed.md`，需再次三选一才会覆盖人工正文 |

**`human_edited` 三态**：`0` 正常、`1` 人工正文受保护且有待处理的 `.proposed.md`、`2` 永久人工。`promote_human` 不把状态清成 0，避免后续自动渲染与人工基线 hash 不同而整篇覆盖；自动提案与人工正文始终分开，接受自动版是唯一自动覆盖入口。

### 9.5 主题分裂与合并

| 情况 | 处理 |
| --- | --- |
| 合并（两个旧社区并成一个） | `slug` 取存活时间更长的；另一个写一份"已并入 X"的跳转文档，`status='merged'`，**不删文件** |
| 分裂（一个旧社区拆成两个） | 新主题新建 slug；原主题文档保留，`status='split'`，正文顶部加"已拆分为 A / B" |

**"存活时间更长"** = `archive_meta.last_exported_at` 更早的那个（存在更久）。

### 9.6 台账 `.moshi-archive.json`

```json
{ "schema": "moshi-archive-ledger/1",
  "generated_at": "2026-10-31T04:00:12.000Z",
  "topics": [ { "topic_id":"t_...", "slug":"本机开发环境",
                "path":"topics/本机开发环境/本机开发环境.md",
                "revision":4, "content_hash":"sha256:...", "status":"active" } ] }
```

这份台账与 DB 的 `archive_meta` **互为校验**：`moshi doctor` 比对两者，不一致以 DB 为准并提示重建。

### 9.7 反模式检查（CI）

`tools/check-archive.ts` 静态扫描 `core/archive/*`，断言：

- 不存在 `readFile` 读取 `archive_dir` 下 `.md` 并写回 DB 的路径（禁止回灌，概设 §9.8）；
- 不存在写 `content` 全文到 MD 的路径（原文不出境）；
- 不存在 `rm` / `unlink` 归档文件的调用（合并/分裂只标记不删）。

### 10.3 3D 渲染管线

| 元素 | 实现 | 关键参数 |
| --- | --- | --- |
| 节点 | `InstancedMesh(SphereGeometry(1, 8, 6), MeshBasicMaterial, N)` | 每实例 `matrix`（position + scale）+ `instanceColor`；半径 3–12px 映射 `importance` |
| 边 | `LineSegments` + 自定义 `ShaderMaterial` | 顶点属性 `aType`（边类型）驱动色相；流动点用 `uv.x += t` 偏移，**不加几何体** |
| 光晕 | 面向相机的 `Sprite` + 径向渐变贴图 | **不用 postprocessing bloom**（概设 §8.5.4 硬约束） |
| 社区包络 | `IcosahedronGeometry(1, 1)` + 菲涅尔 `ShaderMaterial` | 每社区一个，`scale` 随簇半径；透明度 0.06 |
| 参考平面 | `GridHelper` ×4（四层）+ 渐隐 | 解决 Y 轴在透视下不可比（概设 §8.5.3 加固点 2） |
| 标签 | `CSS2DRenderer`，只对活跃层 + 距离 < 120 的节点 | 避免糊屏 |

**渲染循环**：`requestAnimationFrame`，`renderer.info.render.calls` 目标 ≤ 12（节点 1 + 边 1 + 光晕 1 + 包络 C + 网格 4 + 标签 0）。

**视觉编码**（概设附录 A 的落地，参数即实现值）：

| 维度 | 通道 | 映射 |
| --- | --- | --- |
| `strength` | Y 轴 | 四层：`≥0.7 → y=+60`、`0.3–0.7 → y=0`、`<0.3 → y=-60`、失效 → `y=-100`（层内再线性微调 ±20） |
| `strength` | 不透明度 | `0.35 + 0.65 × s`（与 Y 冗余，故意的） |
| `community` | XZ | 社区质心 + 布局坐标 |
| `importance` | 半径 | `3 + 9 × imp` px |
| `ftype` | 色相 | semantic `#22d3ee` / episodic `#a78bfa` / conditional `#f59e0b` |
| `etype` | 边色 | depends_on `#8b5cf6` / logic `#06b6d4` / mutex `#f59e0b` / co_occur `#6b7280` / supersedes `#ef4444` / derived `#475569` |
| `edge.confidence` | 边宽 | `0.5 + 1.5 × c` px |
| 访问活跃度 | 流动速度 | `fact.access_count` 按本页最大归一化（`normalizeActivity`）→ `flowSpeedForActivity`，0 即静止；**目标态**改为：亮度 = PPR 边质量、速度 = hop 分档，见 §10.3.2 |
| 查询命中 | 脉冲 | 命中后 `scale *= 1.0 + 0.6*sin(t*8)*exp(-t/2)`，2s 衰减 |

**下沉动画**：`strength` 跨层时 `y` 用 2–3s `easeOutCubic` 过渡（概设 §8.5.3 加固点 3），**不瞬移**。

**实现注脚（2026-11-02，P2-02；对应台账 D-74~D-86）**：

- **工程形态**：`src/ui` 是独立 Vite 工程（React 18 + three），产物落 `src/app/ui/dist` 由 `http/static.ts` 托管在 `/ui/graph`（SPA fallback）；数据只来自 `GET /api/graph`（`?limit=` 默认 **1000** / 上限 5000、cursor 翻页、边只取本页两端节点；首屏不拉全量，全量走页面上的「加载全量」按钮或 `?limit=`），**前端不算力导向**（概设 §8.9 纪律 1）。
- **渲染代价**：集显（UHD 630）上 1080p 的 MSAA 是最大固定开销，`WebGLRenderer({antialias:false})`；包络用 `FrontSide` + 廉价菲涅尔（`pow(x,2)` 换乘法、去掉逐像素 `normalize`）；光晕半径取节点半径的 2.2×、`opacity 0.2`。实测 5000 节点 + 15000 边 = **≈45–50fps**（1920×949，默认取景）/ draw call 8（包络按四层算半径后填充面积变大，比只算 xz 时略降；拉到最近约 24fps，属填充率见底）。
- **两处参数替代**：① `access_count_24h` 列不存在，流动速度改用 `fact.access_count` / 本页最大值归一化（**2026-11-04 起流动速度改由 `edge_mass` 驱动，见 §10.3.2；此处仅保留历史口径**）；② `edge.confidence → 0.5+1.5c px` 是**不换图元的取舍**——`LineSegments` 的线宽不可编程、顶点偏移也改不了宽度，要真做得换每边 6 顶点的 quad（15000 边 30000→90000 顶点、仍 1 draw call、约半天），本次不做，confidence 落到亮度与流动点密度上（`0.5+1.5c` 保留为纯函数与图例口径，待办记台账 I-12）。
- **包络层高**：包络球心按**渲染层高**算（`renderY(node)` = `layerY(strength, isInvalidated(node))`，四层 ±60 / 0 / −60 / −100），不是布局 Y（布局 Y 恒为 0），否则球会飘在 y=0 平面、与四层上的簇错位；`layerY` 与失效判定必须成对使用（`renderY` 把它们绑成一个函数），漏传 `invalidated` 会让失效成员画在 −100 而球心算在 −80、球罩不住成员（P2-02 复审 H-1）。
- **像素意图**：布局坐标量级随数据增长（5k 节点约 ±700），`3+9×imp` 必须按像素换算——首屏 `frameAll()` 取景后 `pxScale = 取景距离/focal`，球的世界半径 = 像素半径 × `pxScale`；标签可见距离取 `max(120, 数据包围球半径)`，语义仍是「只标活跃层 + 近处」。
- **分页口径**：`hasMore` 看「最后一行之后还有没有行」而不是「本页是否装满」，否则总数正好是 limit 整数倍时最后一满页会假报 `truncated`。

#### 10.3.1 双态视觉规范：默认沉默，被调用才活跃（2026-11-02，台账 D-88 / D-89）

> 依据：概设 §8.5.1（3 秒内看出"哪些主题在活跃、哪些在衰退、Agent 刚才用了哪块记忆"）、§8.5.2（脉冲高亮 = 当前查询命中的子图）、§8.5.3（只有活跃层"高亮、有光晕、显示标签"）。
> 一句话：**画布默认是沉默的，只有"被调用"的那一小块亮起来**。全量高亮等于没有高亮——没有读者能同时吸收 5000 个点和 15000 条线。
> **2026-11-04 改判**：流动语义改为表达「检索证据链」（见 §10.3.2）。本节是 2026-11-02 的双态规范，**已按该规范落地**（P2-03，D-88~D-93）；改判后新增的流动语义尚未实现，落点见台账 P2-24 / P2-25 / P2-26。
> **2026-11-04 视觉深化（P2-19-B / D-133、D-138、D-139）**：颜色改为 14 个语义 token（`src/ui/styles/app.css` 的 `@theme`，图谱侧经 `src/ui/graph/pure/palette.ts` 读取并带 fallback）；新增背景渐变/网格雾、边彗星流光、2D 方向箭头层、节点圆环内芯、选中扫描环、玻璃外壳与 HUD 动效——**全部不新增 WebGL draw call**（实测沉默 7、活跃/选中 8，预算 ≤12），禁 bloom，`prefers-reduced-motion` 下动画全停。

**两种状态**

| 状态 | 语义 | 视觉立场 |
| --- | --- | --- |
| **沉默（dormant）** | 库里的存量：结构、体量、归属 | 提供"这里有多少东西、怎么聚的"，不争抢注意力 |
| **活跃（active）** | 此刻被调用 / 被命中的那一小块 | 唯一允许使用高饱和 + 光晕 + 动效的地方 |
| **次级（1-hop）** | 命中节点的直接邻居 | 介于两者之间：可辨认，但不发光、不流动 |

**参数表**（实现值；活跃态是在沉默态上**叠加**，不是切换整张图）

| 通道 | 沉默（默认） | 次级（1-hop） | 活跃 |
| --- | --- | --- | --- |
| 节点色相 | 同 `ftype` 但去饱和至 20%、明度 ×0.45 | 去饱和至 50% | 原色（见上方编码表） |
| 节点不透明度 | `0.10 + 0.12 × s` | `0.35 + 0.35 × s` | `0.85 + 0.15 × s` |
| 节点光晕 | **关**（`halos.count = 0`） | 关 | 开，`opacity 0.2 → 0.35`，随衰减回落 |
| 节点尺寸 | `×0.85` | `×1.0` | `×1.0`，再叠命中脉冲 |
| 边不透明度 | `0.05`（不随 `confidence` 放大） | `0.25` | `0.55 + 0.35 × c` |
| 边流动 | **静止**（`aFlow = 0`） | 不流动 | 流动 + 方向（`src → dst`）；目标态改由 hop 递进决定，见 §10.3.2 |
| 社区包络 | `0.015`（只给"有边界"的暗示） | 不变 | 所属社区 `0.06` |
| 标签 | 0 | 0 | ≤ 48 个，仅活跃层 + 近处 |
| 参考网格 | 保留 | 保留 | 保留（唯一常开元素） |

> 沉默态把光晕关掉后 draw call 从 8 降到 7，是**省**的；活跃态只在局部打开，峰值不高于现状。

**事件与衰减**

- **事件源**（本阶段只用前端可得的两种，不新增接口、不写库）：① `useSelection.focusId`（点选）；② `fact.access_count` 的上升沿——`main.tsx` 在每次取数后比较上一份与这一份的计数（`pickAccessRise`：增量最大者，并列取 importance 高者），命中即调一次 `useActivity.hit()`，**与①一样进入活跃集**（不再只是 `Graph3D` 里的尺寸脉冲）；`pulseAt` 的脉冲保留，表达"这一帧刚发生"，活跃集表达 4–6s 的窗口，两者叠加。首屏没有"上一份"，不触发。
- 一次事件 → 活跃集 = 命中节点 + 其 **1-hop** 邻居（邻居记次级）；活跃态 TTL **4–6s**，按 `exp(-t/2)` 指数回落，回落过程中光晕与边流动同步衰减，**不硬切**。
- **并发上限**：活跃节点 ≤ 64、活跃边 ≤ 256，超出按 `importance` 截断——避免一次大查询把整屏点亮。
- 同一节点在衰减期内再次命中 → 计时重置，不叠加。
- "跳跃"的观感：路径上按 ~180ms 间隔依次触发节点脉冲，信号一跳一跳传过去；**不改 shader 几何**。

**实现落点（2026-11-02 已落地，P2-03 收尾；台账 D-90~D-93）**

4. `src/ui/main.tsx`：信息条「最近调用：命中 N 条（1 跳）+ M 条边 · X 秒前」，沉默时写「当前无活跃调用」。
5. `window.__moshiGraph` 发布 `halos` / `activeNodes` / `activeEdges` / `focusId`，`window.__moshiGraph2d` 发布 `activeNodes` / `activeEdges`——验收脚本据此读数，不靠肉眼。

**2D 侧的口径差异（D-92 / D-93 / D-94）**：上表的 alpha 是给 3D 那条**渲染管线**写的（节点 `MeshBasicMaterial` 走 over 合成、边/光晕/包络走加法混合），而 sigma 只有一种合成方式、也是 over（alpha 直接盖底色），照抄只会得到一张近乎全黑的图。2D 因此保留"三档相对关系"，另做两档重映射：节点 `to2DAlphaNode(a) = clamp01(0.38 + 0.62a)`、边 `to2DAlphaEdge(a) = clamp01(0.06 + 0.94a)`；沉默色也不上 3D 的"去饱和 20% / 明度 ×0.45"，改用 `dimHex(色, 0.55, 0.72)`（节点）与 `dimHex(色, 0.35, 0.55)`（边）——2D 的职责是"看清拓扑 + 精确点选"，太暗等于没有 2D。取舍理由与实测数据在台账 §4 P2-03。

**2D 的标签差异（D-94）**：上表「标签：沉默 0 / 次级 0」只对 3D 生效。2D 没有景深、没有光晕、没有层级，标签是**唯一**的辨认手段——全关会让 2D 变成一屏纯毛球。因此 2D 允许沉默/次级节点出**稀疏标签**：`labelVisibility: 'auto'` + `labelDensity: 0.5` + `labelGridCellSize: 180` + `labelRenderedSizeThreshold: 7`，抽样上限 ≈ `ceil(视口/180)² × 0.5`（1600×900 约 9×5 格 → **≤22 条**），且只有 `size ≥ 7px` 的节点参与；活跃/选中节点仍走强制标签（`labelVisibility: 'visible'`，不受抽样与地板限制）。这是"可辨"与"沉默"的折中，不是漏实现。

**边界**：本规范只改渲染参数与前端事件调度，**不改** `/api/graph` 契约、不改库表、不改检索排序与 `strength` 衰减（那是 `core/read` 与 `core/write` 的职责）；活跃与否纯属展示推导。

**风险与保底**

- 沉默态若过暗，首页会像坏页 → 保留四层网格 + 极淡包络，并由信息条明确写「当前无活跃调用」；
- 活跃态若缺因果，会显得随机 → 文案必须带命中条数与时间戳；
- 2D 视图复用同一张参数表，**先定规范再动手**，避免两处各写一套双态参数。

#### 10.3.2 流动的语义：证据强度驱动

> **状态：目标态**（2026-11-04 定稿）。落点 P2-26；当前 `encoding.ts` 只有 `flowSpeedForActivity`，尚无 hop 分档与 `aMass`。

**流动的语义（2026-11-04 修订，取代「访问活跃度驱动流动」）**

| 顶点属性 | 含义 | 取值范围 |
| --- | --- | --- |
| `aFlow` | hop 分档流速：hop1 快、hop2 更慢、hop0（直击）静止 | hop0 = 0 / hop1 = 0.6 / hop2 = 0.3 |
| `aMass` | PPR 沿边扩散份额，驱动亮度 | 0–1 |
| `aHop` | 跳数，驱动相位偏移（hop 越大相位越滞后，形成从种子流出的观感） | 0 / 1 / 2 |

- 方向：**由 hop 递进决定**（种子 → 1 跳 → 2 跳），不使用 etype 的语义方向（`co_occur` 是对称边）；
- `hop=0` 直击命中：只亮节点，不画入射流动，图例标注「直接命中」；
- 数据源：`moshi-trace/1`（§4.7），模型未生效时同样可用；
- 约束：**不加几何体、不增 draw call、不改 `/api/graph` 契约**。
- **`aHop` 是原始跳数**（0/1/2），渲染侧不做归一化；模型侧特征 `hop` 的归一化（1 跳 → 0.5、2 跳 → 1.0、非路径边 → 0）见 §4.5，两者不要混用。
- **`aFlow` 的 `0.6` 沿用既有系数**：`src/ui/graph/pure/encoding.ts` 的 `flowSpeedForActivity(activity) = 0.6 * clamp01(activity)` 即"满速"档；`hop1` 取 `0.6`，`hop2` 取 `0.3`（半速，表达"更远、证据更弱、更慢"且相位更滞后），`hop0` 取 `0` 表示静止。

### 10.4 布局计算（后台 worker，D16）

```
layout.job:
  1. 输入：所有 active/disputed 事实 + 活跃边
  2. 初始位置（D-73）：
     - 全量重算 = 冷启动：无旧坐标可用，所有事实从原点 + 半径 5 的抖动起步（种子 = hash(fact_id)）；
       此时没有坐标可算质心，社区锚定等价于"全体拉向原点"，社区分离只能靠 link/charge 力在 tick 中长出来
     - 增量：已有 layout 的事实沿用旧坐标（增量稳定，概设 §13 风险 1）
     - 增量·新事实 → 所属社区质心 + 半径 5 的抖动（质心由该社区已有坐标算出，种子 = hash(fact_id)）；
       community_id 为 NULL 或该社区无既有坐标 → 全局质心；全局也无坐标（空库首跑）→ 原点
  3. 力导向：d3-force-3d，numDimensions = 3，固定种子
     linkStrength 0.3 / linkDistance 30 / chargeStrength -30 / centerStrength 0.02
     社区锚定力：向社区质心 k=0.15
     ticks：全量 300，增量 60
  4. 归一化到 [-100, 100]³
  5. 平均位移 > 15 → 全量重算（否则只更新新增）
  6. 写 layout 表，layout_version += 1
```

**冷启动不保证初值有社区分离**（有意）：首轮所有节点都在原点附近均匀抖动，两簇社区均值分离度实测只有 0.22（增量时因为老坐标还在、新节点锚到各自质心，可达 1.09）。冷启动时无坐标可算质心，社区锚定等价于"全体拉向原点"，分离只能靠 link/charge 力在 tick 中长出来；要首帧就分离，得先有社区划分与历史坐标，不属本步。

**为什么全量必须冷启动**：warm start 出来的 `avg` 位移并不为 0——以第一遍结果为起点再跑 300 tick，实测平均位移 9.73、单点最大 32.37，第三遍仍漂 4.85，永不收敛。若 `--full` 从旧坐标起跑，同一个库跑两次就会得到两套坐标，"同一份数据两次计算一致"这条根本不可能成立。所以「沿用旧坐标」只属于增量：增量复用旧位置是为了空间稳定（概设 §13 风险 1），而全量的语义是"从头算一遍"。

**固定种子**：`d3-force-3d` 的初始抖动用 `hash(fact_id)` 而非 `Math.random()`——否则每次重算布局都不同，用户的空间记忆被摧毁（概设 §8.5.1 反目标 2）。

**只在后台算**：前端不做任何力导向（概设 §8.9 纪律 1）。

### 10.6 队列与批量

三个队列的 SQL：

```sql
-- 消解确认：向量级候选（0.60–0.92）
SELECT a.alias, a.entity_id, e.canonical_name, a.confidence
FROM alias a JOIN entity e ON e.id = a.entity_id
WHERE a.source = 'vector' AND a.confidence BETWEEN 0.60 AND 0.92
ORDER BY a.confidence DESC LIMIT ?;

-- 低置信裁决
SELECT id, content, confidence, importance FROM fact
WHERE epistemic_status IN ('active','disputed') AND confidence < 0.45
ORDER BY importance DESC LIMIT ?;

-- 淘汰候选
SELECT id, content, strength, last_access_at FROM fact
WHERE epistemic_status IN ('active','disputed') AND strength < 0.15
ORDER BY strength ASC LIMIT ?;
```

**影响面预览**（`POST /api/facts/batch/preview`）返回：

```json
{ "facts": 42, "edges": 67, "topics": 3, "invalidated_by_cascade": 5,
  "preview_sample": [{ "id": "f_...", "content": "…" }] }
```

`invalidated_by_cascade` 是**必须算的**：批量失效一批事实会连带让依赖它们的事实变成 `stale`。不显示这个数字，等于让人盲签（概设 §8.3）。

**撤销**：`POST /api/facts/batch` 返回 `op_id`，30 秒内可 `undo`（清 `valid_to`，并还原 `epistemic_status` / `superseded_by`）。**批量失效不建也不删任何边**：本路径不产生 `supersedes` 边，且 `edge` 的 `trg_edge_no_reopen` 使已关闭的边不可重开（见台账 D-104）。30 秒后 op 记录过期，undo 返回 410 `E_OP_EXPIRED`；同一 `op_id` 二次撤销返回 404（op 已作废，见台账 D-105）。

三队列接口的 `limit`：默认 50、上限 200（超出夹取），非数字或 `<1` 返回 400 `E_INPUT`。
