## 1 系统全景与运行形态

### 1.1 进程拓扑

```
Agent（Claude Code / Dsh / 其他）
  ├─ MCP client（C2/C3）──────────┐
  ├─ 会话记录 / 工具调用流（C1 被动观测，只读尾随）
  └─ 工作区文件（C4 归档 MD，只写普通文件）
                                  │  HTTP 127.0.0.1:<port>
                                  ▼
                     ┌──────────────────────────┐
                     │      moshi daemon         │
                     │  单实例 / 常驻 / 回环      │
                     ├──────────────────────────┤
                     │ /mcp        MCP endpoint  │
                     │ /api/*      REST          │
                     │ /ui         静态前端       │
                     │ 写入队列（harvest/annot）  │
                     │ 导出任务（低优先级）        │
                     └───────────┬──────────────┘
                                 │ SQLite (WAL)
                     ┌───────────▼──────────────┐
                     │  infer worker（可选子进程）│
                     │  Python + PyTorch Geom.   │
                     │  懒启动 / 空闲卸载 / 可缺席 │
                     └──────────────────────────┘
```

> **注意拓扑里没有的东西（外置原则）**：没有"全局提示词注入"这条线——v0.1 图里的 `全局提示词（标注指令）` 已按综述 §17 删除，改由 C1 被动观测承担写入主通路。**daemon 对 Agent 只有"读"和"被调用"两种关系，没有"写"关系**（除用户显式指定的工作区普通文件）。

**三个形态决策及理由：**

1. **daemon 同时托管 UI**：不另起前端服务，避免双端口、CORS、跨进程状态同步。前端是 daemon 静态目录下的 SPA，`http://127.0.0.1:<port>/ui`。
2. **推理支路独立子进程**：PyTorch 与主进程语言不同；更重要的是**崩溃隔离**——模型 OOM 或 torch 段错误不能拖死记忆服务。子进程不在时自动降级为纯符号模式。
3. **单实例靠文件锁**：`~/.moshi/daemon.lock` 内写 `{pid, port, started_at, version}`。第二个实例启动时探测锁文件并尝试连接，成功则直接退出并提示已运行；失败（陈旧锁）则接管。

### 1.2 数据目录

```
~/.moshi/
  moshi.db              # SQLite（WAL 模式）
  moshi.db-wal / -shm
  config.toml           # 用户配置
  models/               # GAT 权重、embedding 模型
  cache/layout/         # 布局快照（可重建）
  archive/              # 归档输出（路径可配置到任意目录）
  logs/                 # JSONL，滚动 7 天
  backups/              # 每日 VACUUM INTO 快照，保留 7 份
  daemon.lock
```

`archive/` **必须支持配置到别处**（例如 `~/Documents/默识归档`、git 仓库、同步盘），因为它要脱离 moshi 独立存在。

### 1.3 生命周期

| 场景 | 行为 |
| --- | --- |
| 安装 | 注册为登录项（macOS LaunchAgent / Windows 计划任务 / Linux `systemd --user`） |
| 冷启动 | **< 1s**：daemon 不加载模型、**不拉起推理 sidecar**；推理侧懒启动，见 §11.5 |
| 空闲内存 | **纯符号模式 < 150MB**；推理就绪 < 400MB；无请求 5 分钟卸载权重后 < 220MB（10k 事实规模）。三档定义见 §11.5 |
| 崩溃 | 由系统守护重启；写入走 WAL + 幂等 upsert，重启不丢不重 |
| 退出 | 收到 SIGTERM 先 flush 写入队列，再 checkpoint WAL |

### 1.4 端口与鉴权

- 默认绑定 `127.0.0.1`，端口从 53000 起探测空闲；实际端口写入 `daemon.lock`，UI 从锁文件读。
- 仅回环，不做账号鉴权（单机场景）。但**加一层 CSRF 防护**：UI 首次加载由 daemon 下发一次性 token，后续 `/api/*` 写操作必须带 `X-Moshi-Token`。防止任意网页通过浏览器对 localhost 发起写请求。

### 1.5 外置原则的工程落地（v0.2 新增）

> 综述 §17 定的产品边界，在概设里必须变成**可验收的工程约束**，否则一定会被"顺手优化"破坏。

| 约束 | 落地方式 | 验收方式 |
| --- | --- | --- |
| **不写提示词** | 代码中不存在任何写系统提示词 / 改写 `CLAUDE.md` / `AGENTS.md` 的路径；写盘白名单只含 `~/.moshi/` 与用户配置的 `archive/` | 目录写操作统一走 `safe_write()`，白名单外直接抛错；单测断言 |
| **不改内核** | 只暴露 MCP + REST + 文件三种面；不提供补丁、不依赖任何 Agent 私有钩子 | **unplug-safe 测试**：停掉 daemon，Agent 行为完全不变、无报错 |
| **工具自述不夹带指令** | 所有 tool description 集中在 `mcp/descriptions.ts`，单条 ≤ 200 token，只写功能与入参 | 构建期 lint：祈使句禁词表（`you should` / `必须先调用` / `ignore` / `always call`）+ token 上限检查，**不过则构建失败** |
| **用协议注解，不用话术（v0.6）** | 四个 MCP 工具全部标注 `readOnlyHint` / `destructiveHint` / `idempotentHint` / `openWorldHint`——这是 **MCP 标准元数据**，不是指令话术，不违反 N3 | 单测断言四注解齐全；`memory_correct` 必须 `destructiveHint=true` |
| **零调用可用** | 三个 MCP tool 全部可缺席；harvest 与解析器完全独立于工具调用 | 关闭 MCP 后仅靠被动观测仍能产出事实（CI 集成测试） |
| **调用率可观测** | 记录 Agent 自发调用 query/annotate 的次数、场景、空调用率 | `/ui/diagnostics` 展示；作为一级产品指标 |

**三条实现纪律：**

1. **description 是接口，不是广告位。** 想让 Agent 多调用，只能靠"把功能描述写清楚"，不能靠"命令它调用"。
2. **降级必须是静默的。** Agent 不调用记忆，系统不报错、不提示、不重试——外置系统没有资格打扰宿主。
3. **写盘白名单是硬编码的。** 哪怕未来加"导出到工作区"功能，也只能写**用户显式指定的普通文件**，永远不写平台槽位文件。

### 1.6 模块划分与依赖方向

原则：**依赖单向，越往下越纯**。上层可调下层，下层不得反向 import；跨层只走接口，不走全局单例。

```
app/            组装层：读 config、拉起 daemon、注册路由与任务
 ├─ mcp/         MCP 面（tools / resources / descriptions）
 ├─ http/        REST 面（仅 UI 用）
 ├─ jobs/        调度：harvest / 巩固 / 导出 / 布局（低优先级队列）
 └─ ui/          静态前端产物（构建产物，不参与 Node 编译）

core/           领域层：只依赖 domain + infra，不含 HTTP / MCP 概念
 ├─ write/       解析 → 消解 → 幂等 → 冲突 → 落库
 ├─ read/        意图分流 → 三路召回 → 子图 → 排序 → 装箱
 ├─ lifecycle/   强度方程、巩固、社区摘要
 └─ archive/     主题导出、增量更新、人工编辑保护

domain/         类型层：fact / edge / entity / evidence 的纯类型与不变量断言
infra/          适配层：sqlite（含 vec 扩展）、sidecar client、fs、log
```

**四条硬规矩**：

1. `core/*` **不得** import `mcp/` / `http/` / `app/`——领域逻辑必须能被单测直接调用；
2. `domain/` **不得** import 任何 `infra/`（纯类型 + 纯函数），schema 变更因此只影响一处；
3. **生命周期字段的读写只能经 `infra/sqlite` 的专用方法**，业务代码拿不到裸 SQL——`assert_no_lifecycle_features()` 挂在这一层；
4. `core/read` 与 `core/write` **不得互相 import**，共享的东西下沉到 `domain/`。

> **为什么现在就要写这个**：`read` 与 `write` 的边界一旦被"顺手调用"打破，K2 的正交化就从**代码层面**失守了——那比文档层面失守更难发现，因为代码不会自我声明违规。

| 类别 | 指标 | 目标 | 出处 | 验收方式 |

## 2 存储层设计

### 2.1 表清单

| 表 | 职责 | 关键字段 |
| --- | --- | --- |
| `fact` | 事实节点（L0 主表） | id, content, ftype, **confidence, confidence_source**, strength, importance, pool, epistemic_status, canonical_key, **scope（预留）**, valid_at, valid_to, superseded_by, **attrs（JSON 扩展槽）**, recorded_at, community_id, degree, access_count, last_access_at, source_episode, span_start, span_end |
| `edge` | 类型化有向边 | id, src, dst, etype, weight, confidence, valid_at, **valid_to**, recorded_at |
| `entity` | **实体（v0.3 新增）**：事实的规范化主体 | id, canonical_name, etype, scope, alias_count, first_seen_at |
| `alias` | **别名（v0.3 新增）**：同一实体的各种写法 | alias, entity_id, source(rule/vector/human), confidence |
| `community_summary` | **社区摘要（v0.3 新增）**：全局问题的检索入口 | community_id, scope, summary, fact_count, derived_at, source_rev |
| `episode` | 原始轨迹（会话/工具调用片段） | id, session, ts, raw_hash, raw_path, summary |
| `session` | **会话（v0.6 新增）**：一段连续交互的聚合视图 | id, agent, cwd, started_at, ended_at, turn_count, tool_histogram, summary, source_episodes |
| `ontology` | **结构登记（v0.6 新增）**：`attrs` 键 / 实体类型 / 谓词的注册表 | kind, name, value_type, cardinality, registered_at, sample_count |
| `annotation` | 标注缓冲（harvest 前） | id, dedup_key, payload_json, channel, received_at, harvested_at |
| `feedback` | 使用结果回填（自监督样本） | id, fact_id, verdict(adopt/correct/reject), ts, source |
| `layout` | 3D 坐标缓存 | fact_id, x, y, z, layout_version, computed_at |
| `archive_meta` | 归档主题台账 | topic_id, slug, path, content_hash, revision, last_exported_at, dirty, human_edited |
| `audit` | 变更审计（对应综述 §14.7） | id, table, row_id, before_json, after_json, source, ts |
| `quarantine` | 隔离区 | id, payload_json, reason, ts |

**结构列 vs 语义列（v0.4 新增，因为字段尚未确定）**：

| 类型 | 放哪 | 判据 | 例 |
| --- | --- | --- | --- |
| **结构列** | 独立列 + 索引 | 要参与**索引 / join / 计算 / 排序** | id、时间、`confidence`、`strength`、`canonical_key`、`scope`、`community_id` |
| **语义列** | `attrs` JSON | LLM 提议的、词表未定的、尚在演化的 | 主体、谓词、取值、以及任何还没想清楚的扩展键 |

**字段晋升机制**：`attrs` 里某个键出现率超过阈值、且被查询频繁引用 → 提议晋升为结构列（写迁移脚本 + 回填）。**词表从数据里长出来，不预先设计**。

> **为什么这样分**：详设还没定字段，一次定死 30 个列，字段一变就全盘返工。`attrs` 让"还没想清楚的"先能存下来，等它被真实数据证明重要，再提升为列。

字段级 DDL 见**详设 §1.2**（本文只定"有哪几张表、各自职责"，字段归详设）。

### 2.2 双时态与索引

- `valid_at` / `valid_to`：事实**在世界上**有效的**区间**；`recorded_at`：**写入系统**的时间。三者分离，才能同时回答"当时系统认为是什么"和"当时世界上是什么"。
- **`valid_to` 是必填语义（v0.3 修正）**：v0.1 只有 `valid_at` 起点，导致 §4.3 第 1 条"时态失效判定"根本无法实现。现在**失效 = 写 `valid_to`，不删行**——这与"只增不改"不冲突：改的是"这条事实何时结束"，不是"这条事实曾经写过什么"。
- **`scope` 是标签不是分区（v0.3）**：`global` / `project:<id>` / `session:<id>`，全表同一张图（守 K5）。查询时按"项目优先、全局兜底"继承。
- 必要索引：
  - `fact(epistemic_status, strength)` — 分层渲染与查询过滤
  - `fact(canonical_key, scope)` — **身份定位与幂等写入（v0.3 新增，唯一索引的一部分）**
  - `fact(scope, community_id)` — 作用域内主题聚合
  - `fact(valid_at, valid_to)` — 时间切片与失效判定
  - `edge(src)` / `edge(dst)` / `edge(src, etype)` — 邻接遍历
  - `alias(alias)` — **实体消解反查（v0.3 新增）**
- 1 跳邻域查询目标 **< 1ms**（覆盖索引，不做 JOIN 回表）。

### 2.3 schema 迁移

- 版本号存 `PRAGMA user_version`。
- 迁移脚本**单向升级**，不提供降级；升级前自动 `VACUUM INTO backups/pre-migrate-<ver>.db`。
- 迁移过程包在单事务里，失败整体回滚。

### 2.4 备份

- 每日 `VACUUM INTO` 生成一致性快照（比文件拷贝安全，WAL 下不会拷到半写状态）。
- **归档导出前额外做一次快照**，保证归档内容与某个确定时刻一致。

### 2.5 版本与兼容矩阵

系统里有**五个**独立演进的版本，必须显式绑定关系，否则第一次升级就会炸。

| 版本 | 载体 | 谁读它 | 兼容规则 |
| --- | --- | --- | --- |
| **DB schema** | `PRAGMA user_version` | daemon | 单向升级、不降级；升级前自动快照（§2.3） |
| **证据包 schema** | 证据包 JSON 的 `schema` 字段（如 `moshi-evidence/1`） | Agent / 下游脚本 | **只增字段、不删字段**；删字段必须升大版本 |
| **归档 schema** | MD frontmatter 的 `schema`（如 `moshi-archive/1`） | 人 / 其他工具 | 同上 |
| **MCP 协议** | `@modelcontextprotocol/sdk` 版本 | 宿主 | 跟随 SDK，**不做自定义扩展字段** |
| **模型** | 权重目录名（`model_version`） | sidecar | 与 DB schema 无强绑定；但**换 embedding 模型必须全库重嵌入**（§11.2） |

**三条规则**：

1. **证据包与归档的 schema 版本号写在产物里，不写在配置里**——这两个产物要能脱离 moshi 独立存在并被识别；
2. **DB schema 与模型版本解耦**：允许"旧库 + 新模型"，**不允许"新库 + 旧 daemon"**（单向升级的直接推论）；
3. **模型版本进 `layout` 与 `community_summary` 的失效判断**——模型变了，派生投影必须重算，否则 UI 与摘要会新旧混排。

### 2.6 结构演进：`schema` 三命令（v0.6 新增）

> **为什么必须有这一节**：§2.1 定了策略——"字段从数据里长出来，不预先设计"，靠 `attrs` 先接住、出现率高了再晋升为列。但**没有任何工具能回答"现在数据里长出了什么结构"**。策略写得再漂亮，没有执行机构就是口号。
>
> **借鉴与边界**：Basic Memory 的 `bm_schema`（`infer` / `validate` / `diff` 三命令）是目前唯一把"结构演进"做成工具的开源项目。我们借这个**功能形态**，但不借它的"文件即实体"存储。

三个命令，全部是**确定性统计**，不跑 LLM：

| 命令 | 输入 | 输出 | 解决什么 |
| --- | --- | --- | --- |
| **`schema infer`** | 全库 `attrs` 扫描 | 每个键的：出现率、取值类型分布、**基数性**（single-valued / series / set）、样本值 top-5 | ① 回答"该晋升哪个键"；② **直接产出谓词基数性**——这是互斥检测的前提 |
| **`schema validate`** | 写入时的 `attrs` + `ontology` 登记 | 通过 / 违反（类型不符、基数性不符） | 已登记的键受约束，未登记的键**放行但计入"待晋升"** |
| **`schema diff`** | 晋升前后两个 schema 快照 | 差异清单 + 迁移脚本草稿 | 字段晋升时不用手写迁移 |

**关键设计：`infer` 的输出就是基数性判定的依据。**

谓词基数性缺失（同一 `canonical_key` 下所有不同取值被当成互斥对）会让观测序列型谓词（磁盘用量、构建次数）**互斥爆炸**。判定规则很直接：

| 观测特征 | 判定 | 互斥行为 |
| --- | --- | --- |
| 同一 key 下 90% 只有 1 个取值，且取值长期不变 | `single-valued` | 新值 → 旧值失效（`supersedes`） |
| 同一 key 下取值随时间单调增长 / 频繁变化 | `series` | 新观测**不互斥**旧观测，按时间线并存 |
| 同一 key 下同时存在多个取值且无排他性 | `set` | 走成员关系，不建 mutex |

**落地**：`infer` 作为后台任务（与巩固同队列），输出写 `ontology` 表 + `/ui/diagnostics` 的"待晋升清单"。Phase 1 只做 `infer`，`validate` / `diff` 到 Phase 2。

> **这条不是"别人都有所以要有"**——开源里只有 Basic Memory 一家这么做。它是**我们自己策略的强制配套**：不补，`attrs` 就永远是黑盒，字段晋升只能靠人肉翻库。

## 3 写入通路

### 3.0 单一来源原则（v0.4 新增，第一性前提）

> **一切初始数据只有一个来源：客户 Agent 与大模型对话过程中产生的数据。**
>
> moshi 自身**不产生任何基础数据**——它没有探针、没有采集器、没有独立知识库，也不假设自己能"凭空知道"这台机器上发生了什么。它能做的只有一件事：**把对话里已经存在的东西，加工成结构化记忆**。

这条前提推出四层必须分开的东西，混在一起就会得出错误结论：

| 层 | 内容 | 何时确定 | 现状 |
| --- | --- | --- | --- |
| **来源** | **唯一**：Agent ↔ LLM 对话产生的数据 | **现在已定，不再讨论** | 唯一 |
| **投递通道** | 实时接口录入 / 定时扫会话记录 / 会话日志尾随 | 现在定，可并存、可增减 | 见 §3.1 |
| **字段** | 到底记哪些元数据（主体、谓词、取值、时间、…） | **详设阶段定，本文不定** | 用 `attrs` 扩展槽承载（§2.1） |
| **置信与确定性** | 每个字段怎么给初值、怎么校准 | **字段定完之后才定** | 本文只定机制，不定数值（§3.6.3） |

**三个由此产生的判断：**

1. **"确定性工具观测"不是独立数据源**。工具调用与返回**本身就是对话数据的一部分**，只是其中客观性较高的一种**内容类型**。把它当成"另一个来源"是范畴错误。
2. **实时录入与定时扫描只是投递方式不同**，不构成数据质量分级。同一句话，实时接口交过来和扫日志捞出来，是同一份数据。
3. **字段与置信必须等详设**。字段没定就先验表、就特征集，等于在沙子上盖楼——字段一变，全部返工。

**一句话**：moshi 是**对话数据的加工厂**，不是数据采集器。

### 3.1 采集路径（v0.7 重写：协议埋点为主、归纳兜底、直写留闸门）

> 三条路径投递的是**同一来源**的数据，区别只在"由谁完成结构化、什么时候到手、可信到什么程度"。三条**共用同一张 `annotation` 表与同一套幂等键**——不存在第二条入图路径。

| 路径 | 谁做结构化 | 延迟 | 覆盖率 | 默认 |
| --- | --- | --- | --- | --- |
| **S1 协议埋点**（主） | MCP 下发格式约定，Agent 在输出里埋 `moshi` 块；扫描器**确定性解析** | 分钟～小时 | 取决于 Agent 是否遵守；协议经工具描述与 `moshi://protocol/ann-v1` 下发 | 开 |
| **S2 大模型归纳**（兜底） | 扫描器对**没有埋点**的会话调用大模型归纳事实与边 | 小时级 | **最全** | 开（限流，只进候选） |
| **S3 直写闸门** | Agent 主动调 `memory_annotate` | 秒级 | 只覆盖模型"愿意主动说"的部分 | **关**（见 §3.1.3） |

**为什么以 S1 为主**：Agent 在动作发生时知道"我因为什么改了哪里"，这份意图在扫会话时已经退化成文本；让它当场按固定格式写下，比事后用大模型猜准得多，且解析成本为零。**S2 不是为了替代 S1，而是为了兜住"客户 Agent 不配合"的情形**——覆盖率换精度。

**失败即退回**：埋点块缺失、版本未知、校验失败时，该段内容**不丢**，而是降级交给 S2；S2 也不可用时只落 `episode`，不入图（宁可少一条事实，不留一条垃圾）。

#### 3.1.1 内容类型（不是来源）

同一份对话数据里包含四种内容，它们的**来源相同**，只是**客观性不同**：

| 内容类型 | 例 | 客观性 | 处理 |
| --- | --- | --- | --- |
| LLM 陈述 | "这个项目用 pnpm"、"别动 legacy/" | 低（模型自述） | 全部收，置信按机制打折（§3.6.3） |
| 工具调用与返回 | `lsof -i:8080` → 输出 | **高**（客观输出） | 走解析器（§3.2），可作校准依据 |
| 用户输入 | 确认、纠正、偏好 | **最高**（金标签） | 直接抬升，并写 `feedback` |
| 会话元信息 | cwd、时间、模型 | 客观 | 用于时间锚定与 scope 判定（§3.6.4） |

> **关键**：客观性是**内容类型的属性**，在**置信赋值**环节才生效；它不改变"来源唯一"这个事实。所以 §3.1 的通道表**不再有"优先级"列**。

#### 3.1.2 已否决的通道

| 通道 | 状态 | 原因 |
| --- | --- | --- |
| ~~把标注块写进 Agent 系统提示词~~ | **否决** | 侵入客户 Agent 的系统提示词，违反综述 §17 外置原则 |
| ~~"确定性优先"的通道分级~~ | **否决** | 范畴错误：确定性是内容属性，不是通道属性 |
| ~~人工整理后批量导入~~ | **否决** | 不构成产品路径：客户不会替我们整理数据 |

> S1 与"写进系统提示词"不是一回事：S1 只经 **MCP 工具描述 + `moshi://protocol/ann-v1`** 下发格式，客户 Agent 的系统提示词一个字都不改；Agent 不读、不遵守，就自动退回 S2。

#### 3.1.3 直写闸门（S3 的四条约束）

`memory_annotate` 直接入图是最短路径，也最容易写坏库，因此**默认关闭**，开启后仍受四条约束：

1. **类型白名单**：只允许新事实与 `co_occur` / `derived_from` 边；`depends_on` / `supersedes` / `mutually_exclusive` 必须走审核——这三类会改变答案，不能让调用方单方面写入；
2. **量级约束**：单批条数上限 + 每分钟速率上限，超限直接拒绝并返回明确降级码；
3. **可撤销**：写入全部带 `origin='mcp_direct'`、`session_id`、`turn`，支持按批次整批撤销；
4. **不绕过校验**：生命周期过滤、写白名单（`tools/check-writes.ts`）、脱敏与实体消解一律照常执行。

### 3.2 解析器设计

- **插件式**：每个工具一个 parser，注册表驱动。首批覆盖：
  - 包管理（`npm/pip/cargo install` → 依赖树、版本）
  - 版本控制（`git status/log/diff` → 工作区状态、变更集）
  - 进程与端口（`ps/lsof/netstat` → 占用关系）
  - 文件系统（`ls/stat` → 存在性与时间戳）
  - 构建与测试（`make/pytest/npm test` → 结果、失败项）
- **未识别工具不强行抽取**：只落 `episode` 摘要，不入图。宁可少一条事实，不要多一条垃圾。
- **解析器只是"内容类型 → 结构化"的转换器**，不是数据源。它读的是对话里已有的工具返回，不额外执行任何命令。

### 3.3 标注缓冲与 harvest

- `memory_annotate` 只写 `annotation` 表（缓冲），**不即时入图**。理由：入图要过冲突检测与归一，同步做会拖慢 Agent 调用。
- 每日 03:00 harvest：
  1. **实体消解** → 生成 `canonical_key`（见 §3.6），同一身份的事实归并到同一 key
  2. **幂等判定**：`(canonical_key, scope, value_hash)` 已存在且未失效 → 只刷新置信与观测时间，**不新建行**
  3. **边生成**：先用轨迹（同 session 的工具序列、`procedure.steps`）与身份关系（同实体共现、时间序取代）产出边候选，再做关系归一（同义边类型合并、自环丢弃）。**边由数据产生，不由调用方直接指定**（S3 白名单除外）
  4. 冲突检测（互斥对、时序矛盾）→ 触发**追加式失效**（§3.6.3）
  5. 写 `fact` / `edge`，更新 `degree`、`community_id`
  6. 给受影响主题打 `dirty`（供归档增量更新用，见 §9.5）
- **幂等**：重复 harvest 不产生重复节点（`(canonical_key, scope, value_hash)` 唯一索引）；重复扫描同一条会话不产生重复事实与重复边（幂等键见详设 §5.12）。
- **边与事实同批产出**：每批结束核对"每 10 条新事实 ≥ 3 条新边"；低于该比例说明采集或抽取断了，不是"数据还少"。
- **harvest 只做"结构"，不做"判断"**：它把对话数据加工成结构化事实，**置信怎么给由 §3.6.3 的机制决定，具体数值待详设**。

### 3.4 隔离区与回滚

- 低于置信阈值、超长（> 2KB）、异常字符密度高的条目 → 写 `quarantine`，**不参与 GAT 与默认渲染**，UI 里单独一栏可见可批。
- **阈值待详设**：具体数值取决于置信体系定稿后的实际分布，本文不预设。
- 支持**按来源批量回滚**（某次 harvest 或某个 episode 产生的全部事实），对应综述 §14.7 的对抗防御。

### 3.5 脱敏

- 写入前过规则：API key / token / 私钥 / 带用户名的绝对路径 → 占位符（`<REDACTED:API_KEY>`）。
- 原文不入 `fact.content`，只存 `episode` 的哈希与本地路径。
- 脱敏规则可配置，**默认开启**。

### 3.6 写入语义：实体消解、内容固化与置信重估（v0.4 重写）

> **为什么必须有这一节**：v0.1 的 `dedup_key = hash(content + episode_id)` 只能去掉"字面完全重复"。`node` / `Node.js` / `nodejs` / `v22.9.0` 会变成四个节点——而 `mutually_exclusive` 边、时态冲突消解、社区聚合**全部建立在"同一主体"之上**。身份不消解，图就是一堆互不相认的孤岛，K1 的推理在噪声上跑。
>
> **借鉴来源与边界（v0.4 修正）**：借 Mem0 的**操作分类**（ADD / UPDATE / DELETE / NOOP）与 Graphiti 的**实体消解 + "失效而非删除"**。但有两样**明确不借**：
>
> 1. **不借它的决策权归属**——不让 LLM 决定合并/删除（综述 §10.2 已规避）；
> 2. **不借它的"静默覆盖"**——Mem0 的 UPDATE 是原地替换，且它**没有独立置信字段**（只有 metadata 与检索期相似度分）。所以"置信怎么给、怎么改"这件事，**在 Mem0 那里无从借鉴，必须自建**（§3.6.3）。

#### 3.6.1 三级消解（先规则，后向量，最后人工）

| 级 | 手段 | 覆盖 | 置信 | 何时可用 |
| --- | --- | --- | --- | --- |
| 1 | **规则规范化** | 端口、路径、包名、版本号、进程名——各有专用规范化函数（`Node.js@22.9.0` → `node:22.9`） | 1.0，直接合并 | Phase 0 |
| 2 | **向量近邻候选** | 规范化后仍不等的，取 embedding 近邻 top-3，相似度超阈值且同类型 → 建候选 alias | 待定，**只建 alias 不改主体** | Phase 1 |
| 3 | **人工确认队列** | 中间区间进 UI 队列，批一次即长期生效（写入 `alias.source='human'`） | 1.0 | Phase 1 |

**关键约束**：向量级只允许**新增别名**，不允许**合并节点**。合并是不可逆操作，交给人。

> **待详设**：规范化函数的具体清单、谓词受控词表（建议从"状态 / 版本 / 依赖 / 配置 / 约束"五类起步，随 `attrs` 观察扩张）、向量阈值——**都等字段确定后再定**，本文不预设。

#### 3.6.2 事实身份键（`canonical_key`）

```
canonical_key = hash(scope ‖ subject_entity_id ‖ predicate)
```

- 同一 `canonical_key` 下可以有多条**不同取值**的事实（`node:22.9` vs `node:18.20`），它们自动成为互斥对；
- 同一 `canonical_key` + 同一 `value_hash` 的重复投递 → **只刷新**，不新建（这是幂等的真正来源）；
- `scope` 进 key，是为了未来启用作用域时**不用改 key 格式**（Phase 0 恒为 `global`，见 §3.6.4）。

> **待详设**：`subject` / `predicate` / `value` 三要素是否成立、要不要拆成更多维度——取决于字段设计。本节只定"**必须有一个稳定的身份键**"这个要求，不定它的具体构成。

#### 3.6.3 内容 append-only，置信必须可重估（v0.4 核心修正）

**这是两件完全不同的事，v0.3 把它们混成了"只增不改"，是错的。**

| 对象 | 规则 | 为什么 |
| --- | --- | --- |
| **`content` 及事实结构** | **append-only，永不改写** | 历史内容是审计证据，改一个字就等于伪造历史 |
| **`confidence`** | **可重估、可覆盖**，但每次覆盖必须留痕 | 初始置信是客户大模型自评的产物，**它本来就不是真相，只是当前最优猜测**；不允许覆盖等于让错误的猜测永久留存 |

##### 内容侧：更新 = 追加失效，不是改写行

```
新观测到 端口8080 = nginx（原记录 = node）
  ① 写新 fact 行（valid_at = 观测时刻，valid_to = NULL）
  ② 旧 fact 行：valid_to = 观测时刻，epistemic_status = 'invalidated'
  ③ 建边 old --supersedes--> new（etype = supersedes）
  ④ 原 content 一个字都不改
```

四条硬规则：

1. **永不 `UPDATE fact.content`**——历史事实的内容是审计证据；
2. **失效靠 `valid_to` 收口**，不靠删除行；`epistemic_status` 只是 `valid_to` 的语义标签；
3. **`supersedes` 边必须建**——它是"为什么这条失效了"的唯一可追溯证据，也是归档「冲突与裁决」小节的直接数据源；
4. **回滚 = 撤销失效**：把 `valid_to` 清回 `NULL` 即可，不需要重建事实。

##### 置信侧：四件套 + 三条硬规则

置信不能是一个裸数字，必须是四件东西（**字段名与枚举值待详设确认，机制先定**）：

| 件 | 作用 | 现状 |
| --- | --- | --- |
| **值** | 当前最优估计，可被覆盖 | 必做 |
| **来源** | 这个值从哪来（LLM 陈述 / 工具输出 / 用户确认 / GAT 修正 / 人工）——枚举值待详设补全 | 必做 |
| **历史** | 每次变更的 before / after / 依据，进 `audit` | 必做 |
| **先验** | 新事实的起点值，按"来源 × 内容类型"查表 | **待详设**（字段未定，先验表无法成立） |

三条现在就能定的硬规则：

1. **任何置信变更必须写 `confidence_source`**——不允许出现"来源不明的新数值"；
2. **任何置信变更必须可回滚**——历史可查，能回答"这个 0.82 是谁给的、什么时候给的、凭什么"；
3. **GAT 的 δ 允许覆盖，但不得静默**——δ 覆盖后 `confidence_source` 必须标为 `gat_delta`，且保留被覆盖前的值。这修正了综述 §12.1 的"禁止直接覆盖符号原始分数"：**禁止的是静默覆盖，不是覆盖本身**。

> **为什么必须允许覆盖**：初始置信全部来自客户大模型的自评。LLM 系统性过度自信（几乎总给 0.8–0.95），不同模型/提示/上下文的分数**没有共同标尺**。如果 δ 不能覆盖，一条幻觉出来的高置信事实会永久污染这张图，而且 GAT 越训练越放大它。
>
> **待详设**：先验表的具体数值、校准规则、δ 的上限——等字段确定、拿到真实数据分布之后再定。**本文只保证"机制允许覆盖且可追溯"，不预设任何数值。**

#### 3.6.4 作用域：方案预留，v1.1 启用（v0.4 调整）

> 第一阶段先把功能跑通，**scope 不实现**，但方案与 schema 位置先留好。

| 项 | Phase 0 | v1.1 |
| --- | --- | --- |
| `scope` 列 | **保留**，默认 `'global'`，恒为常量 | 启用三值：`global` / `project:<id>` / `session:<sid>` |
| `canonical_key` | 含 scope 前缀（恒为 global） | 不变，无需迁移 |
| 写入判定 | 全部落 `global` | 按 cwd 判定项目 |
| 查询继承 | 不做 | 项目优先、全局兜底 |
| UI 切换 | 不做 | 全局/单项目视图 |

**设计要点（先写下来，实现时照做）**：

- 写入时按**对话上下文**判定：工具调用发生在哪个 cwd → 落哪个 project；纯用户偏好 → `global`；
- 查询时**项目优先、全局兜底**：先取 `project` 命中，不足再补 `global`，`session` 只在同会话内可见；
- **跨 scope 不算冲突**：`project:A` 的 pnpm 与 `global` 的 npm 是两个世界的真话，不建 mutex 边。

**Phase 0 的风险与兜底**：没有 scope，项目 A 的 pnpm 和项目 B 的 npm 会被判为互斥冲突。但 §4.3 第 2 条规定**互斥冲突不自动裁决**，落败者只标 `disputed` 但仍返回给 Agent 判断——所以表现是"冲突标记偏多"，而不是"错误地删掉一条真话"。**可以接受，这也是 scope 能安全搁置的前提。**

## 4 读取通路

### 4.1 `memory_query` 流程（v0.3 增补三路召回与全局分流）

```
query
  │
  ├─ ⓪ 意图分流（v0.3 新增）
  │     ├─ 局部型（"8080 被谁占了"）→ 走 ①–⑦
  │     └─ 全局型（"这台机器有哪些风险"）→ 走 ⑧ 社区摘要路径
  │
  ├─ ① 解析：实体识别（查 alias 表，§3.6）+ 意图分类
  ├─ ② 三路召回（v0.3 由两路扩为三路，见 §4.5）
  │     ├─ a. 向量 top-k（FAISS/HNSW）
  │     ├─ b. BM25 关键词（SQLite FTS5，零额外依赖）
  │     └─ c. 图扩散（以 a 的 top-3 为种子做 2 跳 PPR）
  ├─ ③ 子图预算：节点 ≤ 64、边 ≤ 192（可配）
  ├─ ④ GAT 打分（启用时）→ 排序
  ├─ ⑤ 符号兜底：时态过滤 + 冲突消解 + 依赖链检查
  ├─ ⑥ 预算装箱（v0.3 新增，见 §4.6）：token ≤ 1500，双池 7:3
  └─ ⑦ 组装证据包 JSON（综述 §14.2 schema）
        └─ ⑧ 全局路径：读 community_summary，直接返回主题级摘要 + 下钻指针
```

**为什么把全局问题单独分流**：v0.1 的召回本质是**局部检索**——它永远只能回答"某个实体周围发生了什么"，回答不了"整体是什么样"。这不是调参能解决的，是路径缺失。借鉴 GraphRAG 的社区摘要理念，但**摘要只做入口、不做内容**：摘要节点不进子图、不参与 GAT 消息传递（守 K1/K2），只负责"告诉 Agent 去哪一片看"。

### 4.2 延迟预算（P95）

| 阶段 | 预算 | 说明 |
| --- | --- | --- |
| ⓪ 意图分流 | 3 ms | 规则 + 关键词，命中不了默认走局部 |
| ① 解析（含 alias 反查） | 5 ms | |
| ② 三路召回 + 两信号 | 20 ms | 向量 7 + BM25 4 + PPR 7（PPR 只在种子 2 跳内，不全局迭代）+ **实体/时序重排各 <1ms（v0.6）** |
| ③ 子图构建 | 10 ms | |
| ④ GAT 前向（CPU，64 节点） | 25 ms | |
| ⑤ 符号兜底 | 10 ms | |
| ⑥⑦ 装箱 + 序列化 | 7 ms | |
| **总计** | **< 80 ms** | 全局路径（⑧）目标 **< 30 ms**（不跑 GAT） |

超预算即降级，不允许"慢但完整"。**三路召回任何一路超时即丢弃该路**，不拖累整体——三路是"锦上添花"，不是"缺一不可"。

### 4.3 符号兜底裁决顺序（定稿）

之前是开放问题，这里定为硬顺序：

1. **时态失效**：当前时刻不在 `[valid_at, valid_to)` 区间内 → 直接排除（v0.3：`valid_to` 补上后这条才真正可实现）
2. **互斥冲突**：按置信 × 强度裁决，落败者标记 `disputed` 但仍返回（让 Agent 自己判断）
3. **置信阈值**：低于阈值的不进证据包，但计数上报
4. **依赖链断裂**：依赖的前置事实已失效 → 返回时附 `stale_dependency` 告警
5. **身份未定**：`canonical_key` 为空（消解未完成）→ 附 `identity: "unresolved"`，置信打折后返回（v0.3）

**兜底永远返回"可用但降级"的结果，不返回空**。空结果对 Agent 是最坏的信息。

> **但"不返回空"不等于"编造"**：当全部候选都低于阈值时，返回 `evidence: []` + `confidence_summary: "none"` + `advice: "无可靠记忆，请勿臆断"`——这仍然是"可用但降级"，而不是拿噪声充数（对应 §10.3 的拒答题）。

### 4.4 降级路径

| 条件 | 行为 |
| --- | --- |
| 推理子进程不在 / 模型未训练 | 纯符号 + 向量排序，`degraded: "no_model"` |
| GAT 前向超时（> 25ms） | 用符号排序，`degraded: "timeout"` |
| 子图超预算 | 按 importance 截断，`truncated: true` |
| **BM25 索引未建 / FTS5 不可用** | 退两路召回，`degraded: "no_bm25"`（v0.3） |
| **PPR 扩散超 7ms** | 丢弃图扩散这一路，只留向量 + BM25（v0.3） |
| **无社区摘要 / 摘要过期** | 全局问题退回局部路径并附 `coverage: "partial"`（v0.3） |
| **实体消解未完成（新实体堆积）** | 该实体按独立主体处理，并标 `identity: "unresolved"`（v0.3） |

### 4.5 三路召回：为什么是三路，不是"全都上"（v0.3 新增，借鉴 A3）

> **借鉴来源与边界**：GraphRAG 的社区摘要、HippoRAG 的 Personalized PageRank、Zep 的混合检索（向量 + BM25 + 图）。**我们只借"召回入口"，不借"内容生成"**——摘要和图扩散都只负责"把候选找出来"，判断仍然全部交给子图 GAT + 符号兜底。

| 路 | 解决什么 | 为什么非它不可 | 成本 |
| --- | --- | --- | --- |
| 向量 | 语义近似 | 基线 | 7 ms |
| **BM25** | **精确标识符**：端口号、错误码、文件名、包名 | 向量对 `8080` / `EADDRINUSE` / `pnpm-lock.yaml` 这类**无语义标识符**几乎无能 | 4 ms，SQLite FTS5 内置，零依赖 |
| **PPR 图扩散** | **多跳关联**：A 依赖 B、B 依赖 C，问 A 时 C 也该出现 | 1–2 跳邻域只能"沿边走"，PPR 能按重要性加权扩散，避免邻居爆炸 | 7 ms，限制种子 2 跳内 |

**融合方式**：RRF（Reciprocal Rank Fusion），三路各取 top-20，按 `1/(60+rank)` 累加。**不做分数归一化**——三路分数量纲不可比，归一化是伪科学。

#### 4.5.1 两个重排信号（v0.6 新增）

> **借鉴与边界**：Mem0 的检索是**四信号融合**——semantic / keyword / **entity** / **temporal**。它和我们的对象一样是**同构事实**，所以它的做法比 Zep 的"按对象类型拆 search 方法"更适合我们（Zep 的对象是异构的：node / edge / episode / summary，才需要拆工具）。
>
> **所以不加新工具，只在 RRF 之后加两个打分项。** 这也是我们比 Mem0 少的那两个信号。

| 信号 | 触发条件 | 打分 | 成本 |
| --- | --- | --- | --- |
| **实体精确匹配** | query 里识别出实体（查 `alias` 表）→ 提升 `subject_entity_id` 命中的事实 | `+0.25 × entity_confidence` | < 1ms（走 `alias(alias)` 索引） |
| **时序意图** | query 含时间词（"现在" / "上次" / "上个月" / 具体日期）→ 按 `valid_at` / `valid_to` 相对当前时刻的距离打分 | `+0.20 × recency_score`，且**已失效事实降权而非排除** | < 1ms（走 `fact(valid_at, valid_to)` 索引） |

**三条约束**：

1. **只是重排，不改变召回集合**——两个信号只对已召回的候选加分，不引入新候选（守 K1：召回入口仍是三路，判断仍归子图）；
2. **时序信号必须能表达"已失效"**——"8080 现在被谁占"与"8080 以前被谁占"是同一句话的两种意图，把失效事实直接排除会让后者永远答不出来；
3. **权重是占位**（0.25 / 0.20），与 §5.5.1 的衰减参数同等待遇：**形态定、数值待标定，改必须过 golden set**。

> **为什么不加 `memory_lookup` 这类结构化工具**：我们的所有对象都是同一种（fact），不像 Zep 有 node / edge / episode 之分。为一个同构集合拆三个工具，只会让 Agent 在三个相似描述之间选错。**把意图差异做进信号，比做进工具面更省、更准。**

**硬约束（守 K1/K2）**：
- PPR **只在候选子图内跑**，不碰全图；
- 社区摘要**只作为路由入口**，摘要文本进证据包的 `topic_hint` 字段，**不进子图、不进 GAT 特征**；
- 三路召回的结果**必须过同一套符号兜底**（§4.3），没有"某一路结果可豁免"的特权。

### 4.6 预算装箱与渐进披露（v0.3 新增，借鉴 A2/B3）

> **借鉴来源与边界**：Letta 的 core memory 固定 token 预算与 memory pressure、MCP resources 的渐进披露。**我们不做物理分层**（守 K5），而是把"分层"实现为**同一份数据的三种读取粒度**。

#### 4.6.1 token 预算装箱

**决策（概设级，不可轻易改）**：证据包总预算 **1500 token**、双池 **7 : 3**（保底池每查询至少 2 条）、单条事实上限 **80 token**、装箱用 `score × pool_weight` 贪心（**不用背包 DP**，收益不抵复杂度）。

**可配范围、参数标定方法与实测分布** → **详设 §4.1**。这四个数字是 §0 边界铁律要求可验收的那一类，**改动必须过 golden set**（§10.3）。

#### 4.6.2 三级披露（同一份数据，三种粒度）

| 级 | 内容 | 典型 token | 谁触发 |
| --- | --- | --- | --- |
| **L0 索引** | 社区/主题标题 + 事实计数 + 新鲜度 | ~200 | 全局问题、或 Agent 主动读 MCP resource |
| **L1 要点** | 事实 `content` 一行 + 置信 + 时间 + 编号 `[M1]` | ~30/条 | `memory_query` 默认返回 |
| **L2 原文** | `source_ref` 指向的本地片段 | 不出境 | 仅本地排障，用户确认后 |

**渐进披露是外置形态下的必需品**：不能"推"就只能"分层给"，让 Agent 先用 200 token 判断值不值得深挖，而不是一次塞 1500 token 赌它用得上。

#### 4.6.3 引用锚定（可评测的前提）

- 每条证据带稳定编号 `[M1]`…`[Mn]`，编号在**同一次 query 内**唯一；
- 证据包同时返回 `json`（机器用）与 `numbered_list`（LLM 用）两种视图——**JSON 给程序，编号列表给模型**，这是对综述 §16.1「离散 JSON 更接近被证明有害的 KAPING」的最小缓解手段；
- 约定 Agent 在回复中引用 `[M1]`，`memory_feedback` 按编号回填 → **"记忆有没有被真正用上"从此可测**（否则综述 §15.9 #4 永远无法验证）。

#### 4.6.4 会话内证据缓存（v0.3，B3 的落地）

- 同一 `session` 内，相似 query（embedding 相似度 > 0.95）在 **5 分钟**内复用上次证据包，附 `cached: true`；
- **失效条件**：该 scope 下任一事实写入 / 失效 / `strength` 跨过分层阈值 → 立即失效；
- 目的：连续多轮围绕同一话题时，避免反复付 80ms 与 token；**不是**为了"少查"，是为了"查得起"。

### 4.7 失败语义与错误码

§4.4 有 7 条降级路径，但**没有统一的对外表达**。Agent 必须能从证据包里区分"**没查到**"和"**没查成**"——这两件事对它的决策完全不同。

| 情形 | 字段 | 值 | Agent 应如何理解 |
| --- | --- | --- | --- |
| 正常 | `status` | `ok` | 结果完整 |
| 某一路召回失败 | `degraded[]` | `no_bm25` / `no_ppr` / `no_vector` | 结果可能不全，但可用 |
| 推理不可用 | `degraded[]` | `no_model` / `timeout` | 排序是符号结果，置信仅供参考 |
| 子图被截断 | `truncated` | `true` | 命中可能被截掉，可缩小查询重试 |
| 全局路径降级 | `coverage` | `partial` | 摘要不完整，建议下钻 |
| 全部低于阈值 | `evidence` / `confidence_summary` | `[]` / `none` | **无可靠记忆，请勿臆断**（不是"不存在"） |
| 身份未定 | `identity` | `unresolved` | 该实体可能与其他事实同源 |
| 服务不可用 | MCP 层错误 | `-32603` + `retry_after` | 静默重试一次，再失败就放弃（外置纪律：不打扰宿主） |

**两条铁律**：

1. `status: ok` 与 `evidence: []` **可以同时出现**（查到了、但没有可靠证据）；
2. **绝不能把"查失败"报成 `ok` + 空**——那会让 Agent 把系统故障误读成"世界上没有这件事"，是最坏的一种误导（比报错更坏，因为报错至少能被发现）。

## 5 推理支路工程化

### 5.1 模型形态

- **独立 Python 子进程**（sidecar），通过本地 socket 提供两个端点：
  - `POST /encode`（入：文本数组；出：384 维向量数组）——embedding 编码，三路召回的向量路依赖它；
  - `POST /score`（入：子图 JSON；出：节点分数数组）——GAT 前向。
- 模型规模 1–6M 参数（综述 §14.3），单机 CPU 小批量可训。
- **懒启动 + 空闲卸载**：daemon 启动不拉 sidecar；无推理请求 5 分钟卸权重、30 分钟退进程。**三档内存预算与验收方式见 §11.5**——这一条是"选了 Python sidecar"之后必须守的预算纪律。
- **v1 不导出 ONNX**：GAT 结构在实验期会反复变，导出成本高于收益。ONNX 是 **v2 收敛目标**（可把 Python 从客户机彻底去掉），理由见 §11.4。

### 5.2 特征管道（正交化红线在此落地）

> 具体特征集（哪些列进模型、几维、怎么归一化）→ **详设 §5.1**。本节只定**红线**——这是概设级约束，换任何模型都必须成立。

**红线（v0.3 修正）**：`strength`、`pool`、`access_count`、`last_access_at`、`archive_meta.*` 等**生命周期/治理字段一律不入特征**。

> **v0.1 的错误已修**：原表把 `strength` 放进特征（标为"认知状态量"），同时把 `epistemic_status` 列进红线——**一进一出正好反了**，直接违反 K2。按综述 §4.3/§15.4：**强度、访问、归档、溯源属生命周期；认知状态属真值**。现在的划分与红线互为补集，`assert_no_lifecycle_features()` 因此有了可执行的白名单定义：

```
生命周期字段（禁入特征）：strength, pool, access_count, last_access_at,
                        archive_meta.*, layout.*, community_summary.derived_at
推理字段（允许入特征）：embedding, ftype, confidence, importance,
                      epistemic_status, degree, etype, weight
```

**这条检查必须做成"白名单穷举"而非"黑名单排除"**——黑名单永远会漏，白名单漏了会直接报错。单测覆盖：给每个字段喂一次，断言生命周期字段必抛异常。

### 5.3 训练

- **影子模式先行**：GAT 打分只记录不生效，累积对照样本。
- 样本来源：`feedback` 表 + 执行结果（**仅状态事实**，综述 §16.2 已限定）。
- 触发条件：已确认样本 ≥ 500 条 → 首次训练；之后每周增量。
- 训练在低优先级线程 + CPU 亲和性限制，不抢 UI 与查询。

### 5.4 灰度与回退

- 三档开关：`off` / `shadow` / `on`，存 `config.toml`。
- `on` 状态下自动熔断：P95 超 80ms 或打分方差异常（连续 100 次标准差 < 0.01，说明塌缩）→ 自动回 `shadow` 并写告警日志。

### 5.5 生命周期层：从"有字段"到"可执行"（v0.3 新增，借鉴 A4）

> **v0.1 的问题**：`strength` 有字段、有 UI 编码（Y 轴），但**没有方程、没有任务、没有调度**——这一层在代码里根本写不出来。借鉴 Generative Agents 的 recency 衰减 + reflection、Letta 的 sleep-time compute、Cognee 的 cognify 流水线，补成可执行的三件事。
>
> **边界**：这一层**完全在 GAT 之外**（K2）。它只做两件事——召回前筛选加权、后台维护；不参与注意力、不回传梯度、不改变任何一条事实的 content。

#### 5.5.1 强度更新方程（形态定稿，参数待校准）

```
每次被采纳：  s ← s + α × (1 − s)          // 饱和增量，永不越界
每次被否决：  s ← s × β                     // 乘性惩罚，比加法更稳
时间衰减：    s ← s × exp(−λ·Δt),  λ = ln2 / H   // H = 半衰期
独立验证：    s ← max(s, floor)             // ≥3 次独立观测一致 → 设下限，防"重要但低频"事实沉底
裁剪：        s ← clamp(s, 0, 1)
```

**方程形态现在定，四个参数（α / β / H / floor）等真实数据再标定**。参考初值：α=0.15、β=0.70、H=14 天、floor=0.60——**这是占位，不是承诺**，与 §0"边界铁律"里可验收的数字（延迟、帧率）不是一回事。参数变更必须过 golden set（§10.3）。

**三个必须写死的细节**：

1. **衰减是惰性计算**，不是定时扫全表——读时按 `last_decay_at` 补算，避免每日 O(N) 写放大；
2. **`valid_to` 非空（已失效）的事实衰减到 0**，但**永不物理删除**——它们是"当时是什么样"的唯一证据（§9.4 保留「已失效」小节的前提）；
3. **淘汰 = `epistemic_status='pruned'` 软删**，物理删除只能由用户在 UI 显式触发，且写 audit。

#### 5.5.2 巩固任务（后台四件，借鉴 reflection / sleep-time / cognify）

| 任务 | 输入 | 输出 | 为什么需要 |
| --- | --- | --- | --- |
| **情景→语义提炼** | 同一 `canonical_key` 下 ≥3 条 episodic 观测 | 1 条 semantic 要点 + 只读溯源边 | 没有它，图会被重复观测灌满，且永远没有"结论" |
| **过程提炼（v0.6）** | 同一 `cwd` 下重复 ≥3 次的工具调用序列 | 1 条 `procedure:<name>` 事实 + `attrs.steps[]`（§5.6） | 代码 Agent 最需要的是"怎么做"，而它只能从序列里长出来 |
| **社区摘要重建** | 该社区的活跃事实集 | `community_summary` 一行 | 全局问题（§4.5）的唯一入口 |
| **衰减重算 + 淘汰候选** | 全图（增量） | `strength` 更新 + 候选清单（**进 UI 待确认，不自动删**） | 让"衰退"看得见、可控 |

#### 5.5.3 调度与幂等

- 触发：每日 03:00 harvest **之后**串行跑，低优先级队列，限速；
- **可重入**：巩固产出带 `derived_from`（源事实 id 集合的指纹），重复跑不产生重复要点；
- **全量 vs 增量**：日常增量（只处理 `dirty` 社区）；用户点"重建"才全量，目标 10k 事实 < 60s。

#### 5.5.4 红线（与 K2 / 只增不改 的交界）

| 允许 | 禁止 |
| --- | --- |
| 新增 semantic 要点、新增溯源边、更新 `strength`、写 `community_summary` | 改写任何 `fact.content`；删除任何事实行 |
| 把事实标为 `pruned` / `invalidated` | 用巩固结果覆盖原始观测 |
| 巩固结果参与**召回筛选** | 巩固结果进入 GAT 特征或损失 |

### 5.6 过程记忆：取结构，不取标签（v0.6 新增）

> **为什么需要**：代码 Agent 最常需要记的不是"是什么"，而是"**怎么做**"——"这个项目的构建步骤是 A→B→C""遇到 `EADDRINUSE` 要先 kill 再 restart"。这类东西既不是状态事实，也不是一次情景。
>
> **借鉴与边界**：MIRIX 的六类记忆里有 `Procedural`；Letta 把记忆当作可被 Agent 修改的结构化块。**但 Mem0 没有这套分类**（单层 fact + metadata），**Zep 的 context types 也没有** procedural——它是学术分类（MIRIX / CoALA），不是产品共识。
>
> **所以我们取"结构"，不取"标签"**：价值在有序步骤，不在那个类型名。

**设计：结构化谓词，不动 `ftype`**

- 谓词约定 `procedure:<name>`（如 `procedure:build`、`procedure:port-conflict`），`attrs.steps[]` **必填**；
- 每条 step 三个字段：`action`（做什么）/ `expect`（成功长什么样）/ `on_fail`（失败先看哪）；
- **`ftype` 不扩**（仍是 `semantic | episodic | conditional`），因此 **GAT 特征维度不变**，也顺手绕开了 ftype / mem_type 那个悬而未决的冲突。

```json
{"predicate": "procedure:build",
 "steps": [
   {"action": "pnpm install", "expect": "node_modules 生成", "on_fail": "检查 registry"},
   {"action": "pnpm build",   "expect": "dist/ 生成",        "on_fail": "检查 node 版本"},
   {"action": "pnpm test",    "expect": "exit 0",            "on_fail": "见 f_1207"}
 ]}
```

**四条配套规则**：

| 项 | 规则 |
| --- | --- |
| **生成路径** | **靠序列模式，不靠 LLM**：同一 `cwd` 下，工具调用序列重复出现同一模式 **≥3 次** → 提炼为一条 procedure。属 §5.5.2 巩固任务的第四项（确定性聚合） |
| **召回** | 不加新工具。query 里出现动作词（"怎么构建"）时，BM25 命中 `procedure:build` 谓词 + §4.5.1 的实体信号加成即可召回 |
| **冲突** | **不建 mutex**。同一 `procedure:<name>` 下 `steps` 的 action 序列不同 → 视为两个版本，按 `valid_at` 新旧裁决（`supersedes`） |
| **生命周期** | 衰减半衰期比观测型事实长（procedure 不该因为一个月没构建就沉底）；**成功执行一次算一次"独立验证"**，复用 §5.5.1 的 `floor` 保底 |

> **什么时候提升为 `ftype`**：如果步骤冲突规则复杂到"同一 name 下多种合法流程"（例如 dev / prod 两套构建），或者 procedure 需要独立的召回通道，v1.1 再提升为正式类型。**现在不提升，是因为加一个 one-hot 维度会改 GAT 特征集，代价远大于收益。**

## 6 可读性三层架构

### 6.1 三层定义

| 层 | 载体 | 读者 | 用途 | 可写性 |
| --- | --- | --- | --- | --- |
| **L0 机器层** | SQLite 图 + 证据包 JSON | Agent | 推理、召回 | **唯一可写** |
| **L1 空间层** | 3D 点线图 | 人（**扫视**） | 发现结构：找团簇、找孤岛、看衰退 | 只读 |
| **L2 文档层** | Markdown | 人（**精读**） | 归档、分享、培训、客户资产 | 只读 |

三层不是三种存储，是**同一份数据的三种投影**。

### 6.2 一致性契约

1. **单向派生**：L0 → L1、L0 → L2。v1 **禁止任何回写**。
2. **可重建**：删除 `archive/` 与 `cache/layout/`，能完全重建，不丢信息。
3. **新鲜度可判**：L1/L2 的每份产物都带 `derived_at` 与 `source_rev`（L0 的全局版本号，单调递增）。UI 上"过期"是可以被显示出来的状态，而不是靠人猜。
4. **派生不阻塞主链路**：导出与布局计算都在低优先级队列，永不进入查询路径。

### 6.3 为什么不把存储改得"更好读"

如果为了让数据可读去改存储结构（比如把事实摊平成表格、加大量冗余字段），会同时破坏两件事：GAT 的特征分布、以及推理通路与生命周期的正交边界。

**可读性是投影问题，不是存储问题。** 这条要写死在概设里，防止后来的人"顺手优化"。

### 7.3 我们的差异点

- 别人的记忆是**对话记忆**（偏好、历史），我们是**环境/工具状态 + 因果依赖**；
- 别人以文本为中心，我们以图为中心——所以**可视化是核心竞争力，不是附属装饰**；
- 别人靠 LLM 抽取，我们以确定性工具观测为主通道——精度与可审计性更强。
- **别人是内置，我们是外置（v0.2）**：平台内置记忆（`CLAUDE.md`、Cursor Memories）占据系统提示词、绑定单一 Agent、用户不可审计；moshi 一条都不占——**不写提示词、不改内核、可随时拔掉**。代价是调用率不可控，收益是**同一份记忆能同时服务 Claude Code / Dsh / 任何 MCP 客户端**，且平台改版不会让它失效。这条是内置方案**结构上做不到**的，不是靠做得更好就能追上的（综述 §17.1）。

> **一句话**：A1 决定"能不能用"，B3/A2 决定"有没有人用"，A4/B4 决定"能撑多久"。

> **B1（作用域）不在前三件里**：Phase 0 单机单项目场景下它不是瓶颈，方案已预留（§3.6.4），v1.1 追加即可。它推迟的**前提**是 §4.3 第 2 条"互斥冲突不自动裁决"——没有这条兜底，无 scope 会误删真话。

## 8 UI 设计：操作面与图谱视图

> **本章分两层，不要混为一谈**：
> - **图谱视图**（§8.5–§8.8）回答"**看**"——3 秒内看出哪些主题活跃、哪些在衰退、Agent 刚用了哪块记忆；
> - **操作面**（§8.1–§8.4）回答"**改**"——查一条、纠一条、批一批、看一个队列。
>
> **一条贯穿全章的红线**：**看图不改，改在列表与检查器。** 3D 只负责"发现"，任何写操作都必须落到可预览、可撤销的面板里——3D 里的点选精度天生不足以承担写操作。

### 8.1 信息架构与页面清单

**一级页面（左侧导航 5 项）**：

| # | 页面 | 职责 | 主视图 | 关键动作 |
| --- | --- | --- | --- | --- |
| 1 | **图谱** | 发现结构、看衰退、看查询命中 | 3D / 2D / 表格三视图切换（§8.7） | 框选 → 跳 §8.3 批量 |
| 2 | **记忆** | 查与改：列表 + 筛选 + 检查器 | 表格 | 纠正、失效、合并、导出主题 |
| 3 | **待办** | 所有需要人决策的队列 | 队列列表（§8.3） | 消解确认、低置信裁决、淘汰候选 |
| 4 | **归档** | 主题文档台账、预览、重建 | 文档列表 + MD 预览 | 导出、重建、处理 `.proposed.md` |
| 5 | **设置与诊断** | 配置、隐私总览、自检（§10.5） | 表单 + 指标卡 | 改配置、清库、导出全库、跑 golden set |

**路由**：`/ui/graph`（默认）、`/ui/memories`、`/ui/inbox`、`/ui/archive`、`/ui/settings`。
**深链**：`/ui/memories?fact=<id>`、`/ui/graph?focus=<id>`、`/ui/memories?canonical_key=<k>`——归档文档与日志里的任何 id 都必须能一键跳回详情。

**全局常驻元素**：
- 顶部搜索（`/` 唤起）：跨实体与事实，输入即查 alias 表 + FTS5；
- 右下角"待办 N"角标：队列不为空时显示，点进 `/ui/inbox`；
- 连接状态指示：`daemon` / `sidecar` / `模型` 三个灯——**外置形态下用户必须能一眼看出"现在有没有推理能力"**。

**筛选器（跨图谱与记忆页共享同一份状态）**：`scope` × `ftype` × `epistemic_status` × `strength` 分层 × 时间区间 × `pool`。筛选状态写进 URL，可分享、可回退。

### 8.2 检查器：单条事实的详情

右侧抽屉（默认 420px，可拖宽）。三档密度，默认只展开前两档：

| 档 | 内容 | 默认 |
| --- | --- | --- |
| **摘要** | `content` 一行 + 置信 + 强度 + `ftype` + 时间区间 | 常显 |
| **结构** | 主体 / 谓词 / 取值（`attrs.frozen`）、`scope`、`canonical_key` 短哈希、`pool` | 常显 |
| **溯源** | `source_episode` 跳转 + span、`supersedes` 链、依赖链（上下游各 3 跳）、冲突对、审计历史 | 折叠 |

**只读与可写的边界（这条必须写死）**：

| 字段 | 可写？ | 理由 |
| --- | --- | --- |
| `content`、`attrs.frozen` | **只读** | 改它等于伪造历史（§3.6.3） |
| `confidence` | 可写 | 走四件套，必须填 `confidence_source` |
| `strength` / `importance` | 可写 | 人工校准，写 `audit` |
| `epistemic_status` | 可写 | 只能通过"追加式失效"改（写 `valid_to`），不能直接置值 |
| `attrs.ext` | 可写 | 扩展槽，不属于事实内容 |

每个可写项旁边**必须显示"上次是谁、什么时候改的"**——没有这一行，置信就还是黑箱。

**`attrs` 里未定字段的呈现**：按值猜控件（数字 / 布尔 / 文本 / 时间），猜不出就 KV 表格原样展示。**不做自定义表单**——字段还没定（§2.1），做表单是纯浪费。

### 8.3 队列与批量操作

三个队列统一收在 `/ui/inbox`，**一个页面处理完所有需要人决策的事**：

| 队列 | 来源 | 单条决策 | 批量 |
| --- | --- | --- | --- |
| **实体消解确认** | `alias.source='vector'`，相似度 0.6–0.92（§3.6.1） | 确认合并 / 拒绝 / 建新实体 | 按相似度区间批 |
| **低置信裁决** | 置信低于阈值但 `importance` 高（§3.4） | 抬升 / 失效 / 隔离 | 按来源批 |
| **淘汰候选** | 巩固任务产出（§5.5.2） | 归档 / 剪枝 / 保留 | 按主题批 |

**批量的两条硬规矩**：

1. **影响面预览必达**：任何批量操作先显示"将影响 N 条事实、M 条边、K 个主题"，确认后才执行。不显示影响面的批量按钮，等于让人盲签。
2. **30 秒可撤销**：执行后浮出 undo；超时才落盘。落盘本身仍是 append-only，撤销 = 清 `valid_to`（§3.6.3 第 4 条）。

**合并必须给 diff 视图**：左旧右新，列出会变的 `canonical_key`、会新增 / 消失的互斥对、会被触发幂等冲突的事实对。**不给人看 diff 的合并按钮，一定会点错**——而合并是这套系统里唯一不可逆的操作（§13）。

### 8.4 首次运行、空状态与引导

§11 说"安装成功率"是关键，那第一屏就得设计。五种状态：

| 状态 | 表现 | 引导 |
| --- | --- | --- |
| **首次打开（0 事实）** | 空图谱 + 三步卡片 | ① 复制 MCP 配置到宿主 → ② 等首次 harvest（显示"下次 03:00"）或点"立即扫描" → ③ 观察第一批事实出现 |
| **MCP 未连接** | 顶部黄条"Agent 尚未连接" | 一键复制的 `mcp.json` 片段 + 各宿主配置文件路径 |
| **sidecar 未就绪** | 顶部灰条"推理未启用，当前为纯符号模式" | 一键安装 Python 组件；**不装也完整可用**（§11.5） |
| **查了但无命中** | 列表空态 | 措辞必须是"**该实体尚未观测到**"，不能是"没有"——前者是记录边界，后者是事实断言（对应 §4.3 的拒答纪律） |
| **归档目录未配置** | 归档页空态 | 选目录（默认 `~/Documents/默识归档`），提示"这里会成为你可分享的记忆资产" |

**`moshi init` 脚本**（首次运行）：建 `~/.moshi/` → 写默认 `config.toml` → 建库 → 跑 schema 迁移 → 打印 MCP 配置片段 → 拉起 UI。**装完不用读文档就能跑通**，是这一节的验收标准。

### 8.5 图谱视图（3D）

#### 8.5.1 设计目标与反目标

**目标**：让人在 3 秒内看出三件事——哪些主题在活跃、哪些在衰退、Agent 刚才用了哪块记忆。

**反目标**（明确不做）：
- 不做"漂亮但读不出信息"的粒子动画；
- 不做每次打开都不同的随机布局（会摧毁用户的空间记忆）；
- 不把 3D 当唯一视图（精确操作必须能回到 2D/表格）。

#### 8.5.2 视觉通道预算：先分配，再画

3D 场景只有 3 个位置通道，加上尺寸/色相/亮度/动效等，**总共约 8 个可区分通道**。记忆里有 10 个以上元数据维度，全塞进去必然不可读。所以第一件事是**分配**，第二件事是**明确哪些维度不上画布**。

**通道分配表：**

| 视觉通道 | 编码维度 | 理由 |
| --- | --- | --- |
| **Y 轴（垂直）** | **记忆强度 `strength`**（活跃↑ / 沉积↓） | 位置是最强视觉通道；上下=生命力隐喻；衰退可做成"缓慢下沉"的动效 |
| **XZ 平面** | **主题社区 `community`** | 空间聚类已表达归属，不必再用颜色重复编码 |
| 节点大小 | 重要度 `importance`（或度数） | 尺寸适合连续量 |
| 节点色相 | 事实类型 `ftype`（semantic / episodic / conditional） | 类型是读者第一需求 |
| 节点亮度·不透明度 | `strength`（与 Y 冗余） | 这里的冗余是好事：强化"强弱"感知 |
| 边色相 | 边类型 `etype`（depends_on / logic / mutex / co-occur） | 关系语义 |
| 边宽 | 边置信 `confidence` | |
| 边流动点速度 | 该路径近期访问活跃度 | 动效通道，只承载弱信息 |
| **脉冲高亮** | **当前查询命中的子图** | 把"Agent 正在想什么"直接可视化 |
| 半透明包络球 | 主题社区边界 | 既科幻又实用（簇边界一目了然） |
| 标签 | 仅 `strength` 高 + 近距离显示 | 避免文字糊屏 |

**不上画布的维度**（放检查器与筛选器，因为它们是"查"不是"看"）：
`fact_id`、精确 `valid_at`、`access_count`、`pool`、`source_ref`、审计历史、`layout_version`。

#### 8.5.3 Y 轴：强度分层（采纳垂直编码，并加固）

垂直轴编码记忆强度，分四层而非连续映射：

| 层 | strength | 视觉 |
| --- | --- | --- |
| **活跃层** | ≥ 0.7 | 高亮、有光晕、显示标签、基准半径 |
| **衰减层** | 0.3 – 0.7 | 中等亮度、无标签（hover 显示） |
| **沉积层** | < 0.3 | 灰暗、缩小、半透明、无标签 |
| **幽灵层** | 已失效 / 已剪枝 | 极淡虚影，**默认关闭**，可开"显示历史" |

三个加固点，缺一个这个设计就会失效：

1. **分段映射而非线性**：强度分布是长尾的，线性映射会把绝大多数节点压在底部糊成一团。分段后每层内部再做归一化。
2. **参考平面锚定**：每层加半透明水平网格平面。3D 透视下 Y 方向的绝对距离不可比（同样 100 单位，远处看起来小得多），没有参考面，人读不出"高低"。
3. **下沉动画 2–3 秒缓动**：强度变化时节点缓慢下沉，不瞬移。这个动效本身就是信息——用户能"看见"记忆在衰退。

**被否决的备选方案**（记录以免反复讨论）：

| 备选 | 否决理由 |
| --- | --- |
| Z 轴编码时间 | 深度是最弱的视觉通道（靠透视/遮挡判断，误差大）。时间改用**时间轴切片**表达 |
| 颜色编码社区 | 空间位置已经表达了聚类，颜色再编一遍是冗余，浪费掉一个宝贵通道 |
| 线性 Y 映射强度 | 长尾挤压，底部不可读 |
| 用 3D 粒子云表示一切 | 好看但零信息量，违反反目标 |

#### 8.5.4 渲染管线 → 详设 §6.1

具体实现（`InstancedMesh` / `LineSegments` + shader / billboard 光晕 / 菲涅尔包络 / 参考平面）移交 **详设 §6.1**。概设只保留一条**硬约束与一条性能目标**：

- **不用 postprocessing bloom**——开销大、集显吃不消（这是选型约束，不是实现细节）；
- **性能目标：10k 节点 / 30k 边，集显 30fps；超过 20k 自动切点云模式。**

技术选型统一收在 **§11.2**（React 18 + TypeScript + Vite / Three.js / sigma.js / ECharts / zustand / Tailwind），本节只定**性能与交互纪律**。

- 构建产物放进 daemon 静态目录，`/ui` 直接访问，纯 SPA 无 SSR。

**页面级性能预算**（§8.5.4 只给了 3D 的 30fps，其余页面同样要有数字）：

| 页面 / 组件 | 预算 | 手段 |
| --- | --- | --- |
| 图谱 10k 节点 | 30fps（集显） | `InstancedMesh` 单 draw call + 点云降级（§8.8） |
| 记忆列表 10k 行 | 首屏 < 500ms，滚动 60fps | 虚拟滚动（`tanstack-virtual`）；**禁止一次拉全量**，走游标分页 |
| 检查器 | < 50ms | 详情按需请求，不随列表下发 |
| 归档 MD 预览 | < 300ms | 懒加载 + 只渲染可见段 |
| 搜索（`/`） | < 80ms 出首屏结果 | alias 反查 + FTS5 走同一后端接口，前端不做本地过滤 |

**三条交互纪律**：

1. **前端不做任何图计算**——力导向、社区划分、布局全部后台算好落库（§8.5.5、§6.2 第 4 条）。前端只渲染与交互。
2. **深色优先，跟随系统**；同时提供手动切换（本地 UI 常在长时间盯屏场景使用）。
3. **窄屏（< 1100px）**：3D 与检查器互斥显示，检查器改浮层抽屉；表格视图在窄屏下退化为卡片列表。

**键盘可达（不用鼠标也能完成一次纠正）**：`/` 搜索 · `j`/`k` 列表上下 · `Enter` 打开检查器 · `Tab` 在可写字段间移动 · `Cmd/Ctrl+Enter` 提交 · `Esc` 关闭 · `g` `m` 跳记忆页 · `g` `i` 跳待办。

## 9 归档沉淀：Markdown 导出与增量更新

### 9.1 定位

归档是 **L2 投影**：只读、可重建、不回写。目标是**分享、培训、客户自有记忆资产**。

相比 SQLite，纯文本有四个天然优势，这是归档存在的根本理由：

1. **可进 git**：客户自己的记忆就有了版本历史，能 diff、能回滚、能协作；
2. **可脱离 moshi 独立存在**：不依赖任何 ID 解析，任何编辑器都能开；
3. **可被其他工具消费**：RAG、笔记软件、静态站点生成器；
4. **可被人学习**：这是"培训"场景的前提。

### 9.2 导出单元是"主题"，不是"事实"

一条事实再重要，孤立无援也讲不成故事；一组事实即使单条不重要，只要有完整依赖链、冲突裁决、时间演化，就很有价值。所以：

- **主题 = 图上的社区**（Louvain 社区发现），`topic_id` 稳定，slug 由 `topic_id` 派生（**不随标题变**，否则文件会反复改名）；
- **价值门槛**：满足 `事实数 ≥ 8` 且（`依赖链完整度 ≥ 0.5` 或 `存在冲突裁决记录`）才导出；
- 低价值主题**不导出**——归档一旦什么都收，就变成垃圾场，没人会读。

### 9.3 目录结构 → 详设 §7.1

目录树（`index.md` / `topics/<slug>/` / `_history/` / `.moshi-archive.json` 台账）移交 **详设 §7.1**。概设只保留一条约束：**`archive/` 必须支持配置到任意目录**（§1.2），因为它要脱离 moshi 独立存在。

### 9.4 文档模板 → 详设 §7.2–§7.3

正文分节与完整 frontmatter 模板移交 **详设 §7.2 / §7.3**。概设只保留两条**不可改的取舍**：

- **保留「已失效」小节**，不直接删。归档的价值之一就是"当时是什么样"，这对应双时态的文档化。
- **「本次更新」小节**自动生成，列出新增 N 条 / 失效 M 条 / 置信变化 K 条（含前后值）。人既看到最新状态，也看到"变了什么"。

### 9.5 增量更新机制（核心）

**变更检测**：每个主题算 `content_hash`（基于事实集合 + 关键字段的规范化摘要）。三路触发：

| 触发 | 条件 | 说明 |
| --- | --- | --- |
| 定时 | 默认每日 04:00 | 可配为每周 |
| 脏标记 | 该主题下变更事实 ≥ 3 条，或置信变化 > 0.15 | 由写入通路打 `dirty`（§3.3 第 5 步） |
| 手动 | UI 单主题导出 / 全局重建 | |

**更新策略**：

- 默认**整篇重写**——幂等、简单、不会累积补丁噪声；
- `revision` 自增，`_history/` 留最近 5 版，更早交给 git；
- **内容未变则不写盘**：保留 mtime，避免 git 产生无意义 diff、避免同步盘反复上传。

**人工编辑保护（关键，必须有）**：

导出时记录 `content_hash`；下次导出前比对磁盘文件的实际 hash。

- 若文件**未被改动** → 正常重写；
- 若文件**被人工改过** → **不覆盖**，改写 `<slug>.proposed.md`，在 `archive_meta.human_edited` 置位，UI 提示"有 N 个主题存在人工修改待合并"。

这条防的是最伤信任的一种事故：自动更新把人写的东西吃掉了。

**主题分裂与合并**：社区发现重算后可能出现主题拆分/合并。处理规则：

- 合并：slug 取存活时间更长的那个，另一个写一份"已并入 X"的跳转文档，不直接删；
- 分裂：新主题新建 slug，原主题文档保留并标注"已拆分为 A / B"。

### 9.6 脱敏与边界

- 走与写入**同一套**脱敏规则（§3.5）；
- 默认**不含** `source_ref` 原文片段，只留 `episode_id + span` 引用；
- 可配置开启原文，但开启时 UI 必须警告：`archive/` 很可能被同步到网盘、发到群里、提交到公开仓库——这是"原文不出境"边界最容易破的后门。

### 9.7 调度与性能

- 低优先级队列，限速每秒 1 篇，不抢查询与 UI；
- 全量重建目标：10k 事实约 200 个主题，**< 60s**；
- 单主题导出 < 300ms。

### 9.8 反模式（红线）

| 禁止 | 原因 |
| --- | --- |
| ❌ 导出器读 MD 回灌图 | MD 会变成第二个真相源，正交化直接崩 |
| ❌ 整段原文写进 MD | 违反"原文不出境"，且 MD 容易被同步/分享 |
| ❌ 每次导出新建目录 | 无法 diff，历史变成噪音 |
| ❌ 覆盖人工修改 | 信任崩塌，一次就够 |
| ❌ 导出阻塞查询路径 | 归档是后台事，不能影响 Agent |
| ❌ 导出全部事实（含低价值） | 归档失焦，没人读 |

### 9.9 v2 预留扩展

- **静态站点导出**：分享/培训场景，主题合集 → 可浏览的 HTML 站点；
- **学习路径**：按依赖链拓扑序生成"先读什么、后读什么"；
- **新人 onboarding 包**：从归档里抽"本机开发环境"这类高频主题，打包给新同事。

## 10 可观测性与评测埋点

### 10.1 日志

- 结构化 JSONL，分级（error / warn / info / debug），滚动 7 天。
- 关键事件必须记：harvest 起止与条数、导出起止、GAT 灰度切换、熔断触发、schema 迁移。

### 10.2 指标

| 指标 | 用途 |
| --- | --- |
| 查询延迟 P50/P95/P99 | 是否守住 80ms |
| **Agent 自发调用率 / 空调用率** | **外置形态下唯一的采纳信号**——不调用不是故障，但长期为零说明工具描述没写清或场景不匹配 |
| **`[M#]` 引用率** | 证据包里有多少条被 Agent 真正引用——**这是"记忆有没有被用上"的直接证据**，也是综述 §15.9 #4 的唯一可测形式 |
| **unplug-safe 通过率** | 停掉 daemon 后 Agent 是否无感（外置承诺的可验收形式） |
| harvest 入图/隔离比 | 抽取质量 |
| **实体消解待办量 / 消解失败率** | 身份层健康度；待办持续上涨说明规则覆盖不足（A1） |
| 事实总量、边总量、主题数 | 成长曲线 |
| GAT 打分分布（均值/方差） | 检测塌缩 |
| 归档耗时、待合并主题数 | 归档健康度 |
| UI FPS 采样（客户端上报） | 性能回归 |

#### 10.2.1 图质量指标（v0.3 新增，借鉴 B4）

> 综述 §2.4 指出"图结构质量指标在领域内稀缺"——这是我们可以贡献的点，也是**系统悄悄变烂的唯一可观测信号**。延迟和崩溃率都发现不了"图变垃圾"。

| 指标 | 定义 | 告警阈值（初值） |
| --- | --- | --- |
| **孤立节点比** | `degree = 0` 的事实占比 | > 15% → 抽取或消解出问题 |
| **社区模块度** | Louvain 划分的 modularity | < 0.3 → 社区结构瓦解 |
| **`stale` 依赖链数** | 依赖前置已失效、自身仍 active 的事实数 | > 总量 5% → 失效传播没跑 |
| **近似重复比** | 同 `canonical_key` 下语义相似度 > 0.95 的不同事实占比 | > 10% → 消解阈值太松 |
| **关键实体覆盖率** | 高频实体（top 50）中至少有 1 条 active 事实的比例 | < 80% → 召回会大面积落空 |
| **跨 scope 泄漏数** | `project:*` 事实被 `global` 查询命中的次数 | > 0 → scope 继承逻辑有 bug |

### 10.3 离线回归集（v0.3 新增，借鉴 B4）

> 只有在线埋点等于**盲改**：改一次检索权重、换一次 embedding，没有任何东西告诉你"变好了还是变坏了"。

**golden set 的构成**（建议 60–120 条，人工标注，随版本演进）：

| 题型 | 例 | 考什么 | 为什么必须有 |
| --- | --- | --- | --- |
| 单跳 | "8080 被谁占了" | 基础召回 | 回归底线 |
| 多跳 | "哪个进程依赖了会超时的镜像源" | 依赖链传导 | K1 的核心价值 |
| **时态更新** | "现在用的是 Node 几"（历史上有 18） | 旧答案**必须失效** | 双时态 + `supersedes` 的直接验收 |
| **拒答** | "这台机器装过 Redis 吗"（实际没观测过） | 该说"没有记录" | 防幻觉；**兜底返回降级结果不等于编造** |

**四条使用纪律**：

1. 每次改检索 / 改消解 / 换 embedding / 重训 GAT，**必须跑一遍**，结果进版本记录；
2. **不追求高分，追求不退化**——记忆系统的指标是纵向的，横向比没意义；
3. 时态更新与拒答题**任何一条回归即为阻断**（这两类直接对应产品承诺）；
4. 回归集**不进 CI 的 PR 门禁**（太慢），但进发布门禁。

### 10.4 评测埋点（对应综述 §16.4「立项即埋」）

- 每次 query 记录：`query_id`、三路召回各自贡献的 `fact_ids`、最终入包集合、`[M#]` 是否被引用、是否被 `feedback` 采纳；
- 支持 A/B 分组：关/开 GAT、关/开 global self-attention、关/开 cross-attention、**关/开三路召回中的任一路**（v0.3 新增）；
- 纵向曲线：命中率 vs 事实总量，用于验证"随使用成长"是否真实存在。

**这些开关必须从 Phase 0 就存在于代码里**，不能等到要评测时再补——补出来的开关一定不干净。

### 10.5 自检页

`/ui/diagnostics`：DB 完整性检查、索引状态（含 FTS5）、布局新鲜度、模型版本、归档台账一致性、**实体消解待办量、图质量六项指标、golden set 最近一次结果**。

## 11 技术选型、打包与升级

> 本章回答"**用什么写**"。选型只看三个硬约束：**客户电脑上跑得动**（§1.3 的内存与冷启动）、**装得上**（安装成功率）、**改得动**（GAT 结构会反复调）。

### 11.1 选型结论

**主进程 Node 22+（`engines.node` = `>=22.18.0`）+ TypeScript，推理侧 Python sidecar，二者通过本地 socket 通信。**

| 职责 | 承担者 | 说明 |
| --- | --- | --- |
| daemon、HTTP/MCP、存储、检索、UI、调度 | **Node 22+ + TypeScript** | 与 MCP 官方 SDK 同栈；查询路径无 CPU 密集段，事件循环够用 |
| embedding 编码、GAT 前向、训练 | **Python sidecar** | PyTorch + PyTorch Geometric；**可缺席**，缺了退纯符号模式 |
| 训练（离线） | 开发者机器上的 Python | **永不发生在客户机**，客户机只加载权重 |

### 11.2 子选型（定稿）

| 层 | 选定 | 理由 | 明确不用 |
| --- | --- | --- | --- |
| 运行时 | **Node 22+ LTS + TypeScript**（下限 22.18.0，已在 24.19.0 验证） | 与 `@modelcontextprotocol/sdk` 同栈，MCP 一等公民 | Deno / Bun 作运行时（生态与 native 模块支持未稳） |
| HTTP | **Fastify** | 内置 JSON Schema 校验，正好当接口契约；比 Express 快 2–3× | Express（无 schema 校验）、Koa |
| SQLite 驱动 | **better-sqlite3** | 同步 API（省掉 async 噪音）、prebuild 覆盖三平台、支持 `loadExtension` | `node:sqlite`（22 内建仍 experimental，API 会变） |
| 向量索引 | **sqlite-vec** | 向量与事实同库、支持 KNN + 元数据过滤、零额外服务、可随库备份 | **FAISS**（Python 侧，且 10k 规模用不到）、**hnswlib-node**（native 编译风险高，v1 无必要） |
| Embedding 模型 | **bge-small-zh-v1.5（384 维）** | 中文环境事实足够；单条编码 ~10ms | bge-m3（1024 维，v1.1 再评估，需走 §E4 的重嵌入迁移） |
| Embedding 运行时 | **sidecar 内 sentence-transformers** | 与 GAT 同一进程，**避免在客户机上维护第二套推理栈** | `onnxruntime-node`（会与 Python 形成双推理栈） |
| GAT | **PyTorch + PyTorch Geometric** | 结构改起来最快，消融实验不用两套代码 | 手写算子 / DGL（生态更小） |
| MCP | **`@modelcontextprotocol/sdk`**（Streamable HTTP） | 官方实现，协议演进跟得上 | 自实现 JSON-RPC |
| 前端 | **React 18 + TypeScript + Vite** | §8 的三视图与检查器都是组件密集界面 | SSR 框架（本地 UI 不需要） |
| 3D | **Three.js**（`InstancedMesh` + `LineSegments`） | 渲染实现见详设 §6.1 | Babylon.js（包体大、收益不明显） |
| 2D 图谱 | **sigma.js** | 自带 WebGL 渲染，省掉手搓 canvas | 手搓 `d3-force`（要自己做拾取与缩放） |
| 图表 | **ECharts** | 统计面板与成长曲线 | — |
| 状态 / 样式 | **zustand / Tailwind** | 轻量，无 boilerplate | Redux（过重） |
| 日志 | **pino**（JSONL） | 低开销，直接落 §10.1 的格式 | winston |

> **一条实现约束**：`sqlite-vec` 需要 `better-sqlite3` 的 `loadExtension`，而扩展是平台相关的 `.dylib/.so/.dll`——**必须随包分发三平台二进制**，不能指望客户机编译。这是 §11.6 打包的硬要求。

### 11.3 为什么是「Node + Python sidecar」

选它，是因为它把**改模型的成本**压到最低：

- PyG / DGL / sentence-transformers 生态完整，GAT 改结构、加层、换损失都是改几十行；
- 训练与推理**同一套代码**，消融实验（综述 §15.9 五项）不用维护两份实现；
- 换 embedding 模型（bge-small → bge-m3）只需换一行加载。

**必须同时接受的三个代价**（不写下来就会在实现时打架）：

| 代价 | 后果 | 应对 |
| --- | --- | --- |
| **§1.3 的"空闲 < 150MB"单档不成立** | Python + torch 常驻 250–350MB | 改成**三档内存预算**（§11.5），并加空闲卸载 |
| **两个安装器** | 安装成功率下降，而这是外置形态的生死线 | Python 组件**默认可选**，缺了纯符号模式完整可用（§11.6） |
| **跨进程调用 +1~2ms** | 查询 P95 预算从 80ms 里扣 | 仍在预算内（§4.2 三路召回 18ms + GAT 25ms 已含余量）；socket 用 unix domain / named pipe，不走 TCP |

### 11.4 被否决的备选（记录以免反复讨论）

| 方案 | 优点 | 否决理由 |
| --- | --- | --- |
| **全 Node + ONNX Runtime** | 单运行时单安装器；空闲 ~90MB、冷启动 < 400ms，**§1.3 两条预算都达标** | GAT 在实验期结构反复变，每次都要重导出 ONNX（需固定 shape `(1,64,F)` + attention mask 层）；消融迭代成本高于收益。**保留为 v2 收敛目标**：GAT 结构稳定后迁 ONNX，可把 Python 从客户机彻底去掉 |
| **Rust 主进程 + candle/ort** | 单二进制、空闲 ~40MB、冷启动 < 150ms | MCP Rust 生态弱、GAT 需手写、前端仍是 JS（两套语言）；开发时间预计 2–3 倍，与"快速落地"目标冲突 |
| **全 Python（FastAPI + PyG）** | AI 生态最顺，一套语言 | 分发地狱（PyInstaller 包体 100MB+、跨平台坑多）、内存最高、MCP Python SDK 非一等公民 |

### 11.5 Python sidecar 的生命周期与内存预算

**这是"选了 B 之后必须补的一节"**——否则 §1.3 的预算就是假的。

**生命周期**：

| 事件 | 行为 |
| --- | --- |
| daemon 启动 | **不拉起 sidecar**。冷启动 < 1s 靠的就是这一条 |
| 首次需要向量 / GAT | 异步拉起 sidecar，**本次查询立即降级** `degraded: "no_model"` 返回，不阻塞 |
| sidecar 就绪 | 写 `~/.moshi/sidecar.ready`（含 pid、模型版本、端口）；后续查询走 socket |
| 空闲 5 分钟 | 卸载权重（torch 模块置 `None` + `gc`），**进程保留**——省掉 2–4s 的冷启动 |
| 空闲 30 分钟 | 退出进程，回到纯符号模式 |
| 崩溃 | 1 小时内最多重启 3 次；超过则停在纯符号模式并写告警（**不弹窗、不打扰宿主**，§1.5 纪律 2） |
| 训练 | **客户机永不训练**，只加载权重；训练在开发者机器离线做 |

**三档内存预算（替代原单档"< 150MB"）**：

| 档 | 常驻集 | 目标（10k 事实） |
| --- | --- | --- |
| **纯符号**（sidecar 未起 / 已退出） | Node + SQLite + sqlite-vec + 静态前端 | **< 150MB**（原目标保留在此档） |
| **推理空闲**（进程在、权重已卸） | + torch 运行时 | < 220MB |
| **推理就绪**（权重驻留） | + bge-small + GAT | < 400MB |

**冷启动预算（拆分）**：

| 阶段 | 目标 |
| --- | --- |
| daemon 冷启动 | **< 1s** |
| 首查可用（纯符号） | < 100ms |
| sidecar 首次就绪 | < 5s（后台异步，**不阻塞任何查询**） |

> **验收方式**：三档各写一条 CI 断言（RSS 采样），"纯符号 < 150MB"这条必须在 Phase 0 就绿——它是外置形态"轻"的承诺，也是没装 Python 的用户唯一能感知到的形态。

### 11.6 打包与分发

| 项 | 方案 |
| --- | --- |
| 形态 | **内嵌 Node 22+ 运行时 + 应用目录**（安装包约 60MB）；v1 用浏览器打开 `/ui`，不做桌面壳 |
| 为什么不是单文件 | `better-sqlite3` 与 `sqlite-vec` 都是平台相关 native 模块，单文件打包（`bun build --compile` / `pkg`）需把它们标 external 并携带 `.node`/`.so`，三平台各测一遍才敢用。**v1 选稳的**；v1.1 再试 Node SEA |
| Python 组件 | **可选、单独下载**：`uv` 管理独立 venv，随包分发预编译 wheel（**避免客户机联网装 torch**）。torch CPU 版约 200MB——不塞进主安装包 |
| native 依赖清单 | `better-sqlite3.node`、`sqlite-vec` 三平台二进制、`onnxruntime`（仅当 v1.1 迁 ONNX 时需要） |
| 安装器 | Windows MSI / macOS pkg / Linux tar.gz + `install.sh` |
| 登录项 | LaunchAgent / 计划任务 / `systemd --user`（§1.3） |
| 首次运行 | `moshi init`：建目录 → 写 `config.toml` → 建库 → 迁移 → 打印 MCP 片段 → 拉起 UI（§8.4） |
| 自动更新 | 检查 manifest → 下载 → 原子替换（先写 `.new` 再 rename）→ 重启；**数据迁移必须向后兼容**（§2.3 单向升级） |
| 卸载 | 保留数据目录，打印归档路径提示 |

> **"Python 可选"这条是全章最重要的设计**：它把"装不上 torch"从**致命失败**降级为**功能缺失**。装不上的用户仍得到一套完整可用的符号记忆系统——这直接决定安装成功率，而安装成功率决定外置形态能不能活。

## 13 工程风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 布局漂移 | 用户失去空间记忆，3D 沦为装饰 | 增量稳定 + `layout_version` 锁定 + 过渡动画 |
| 归档吃掉人工修改 | 信任崩塌 | hash 检测 + `.proposed.md` + UI 提示 |
| 3D 性能不达标 | UI 不可用 | 点云降级 + 2D 兜底 + 规模分档 |
| 抽取质量差 | 垃圾入图，GAT 学坏 | 确定性优先 + 隔离区 + 未识别工具不入图 |
| 主题切分不稳定 | 归档文件反复改名，链接失效 | slug 由 `topic_id` 派生 + 合并/分裂规则 |
| Python 依赖装不上 | 安装失败率高 | 纯符号模式可跑，推理为可选组件 |
| 归档目录被同步到公开处 | 隐私泄露 | 默认不含原文 + 导出前警告 + 可选敏感词扫描 |
| **被"顺手优化"成提示词注入** | 越过外置边界，失去跨 Agent 通用性，与平台零和冲突 | §1.5 的写盘白名单 + description lint + unplug-safe 测试，三条都是**构建期/CI 强制**，不靠自觉 |
| **实体误合并**（v0.3） | 把两个不同实体并成一个 → 事实串味，且**不可逆** | 向量级只建 alias 不合并；合并只能人工确认；合并写 audit 且可拆分（`alias` 行级回退） |
| **消解待办堆积**（v0.3） | 新实体长期不消解，图重新碎成孤岛 | 待办量进 `/ui/diagnostics` 与图质量面板；> 50 条告警 |
| **三路召回拖慢查询**（v0.3） | P95 破 80ms | 每路独立超时即丢弃（§4.4）；PPR 限制种子 2 跳；RRF 不做归一化 |
| **衰减参数拍错**（v0.3） | 重要事实沉底（半衰期太短）或图永不过期（太长） | 14 天为初值；「独立验证设 0.60 下限」保底；参数变更必须过 golden set |
| **巩固产生"伪结论"**（v0.3） | 从噪声观测里提炼出一条看似权威的 semantic 要点 | 巩固只允许在 ≥3 条**已验证**观测上发生；产出带 `derived_from` 溯源；置信不高于源事实均值 |
