# 默识工程落地任务台账

> **这份文档是给执行者（Agent 或人）读和写的。**
> 代码怎么写看 `详设`；为什么这么做看 `概设` / `综述`。这里只回答三件事：**现在做到哪了、下一步做什么、怎么算做完了。**

---

## 0 使用协议（每次开工必读）

### 0.1 三份文档的分工

| 文档 | 回答 | 什么时候看 |
| --- | --- | --- |
| `综述.md` | 该不该做、有没有证据 | **几乎不看**。只在质疑某个方向时查 |
| `概设.md` | 做成什么样、为什么这么定 | 需要判断"这个设计能不能改"时看对应章节 |
| `详设.md` | 具体怎么写：字段、算法、接口、参数 | **每次写代码前看对应小节** |
| **本文** | 现在做到哪、下一步做什么 | **每次开工第一件事** |

**规则：本文不复制详设的内容。** 任务详情只给"做什么 + 看哪一节 + 怎么验收"。想改实现细节，去改详设；本文只记进度。

### 0.2 状态机

**状态值**（§3 状态列只能填以下值）：

```
TODO ──开始──> WIP ──验收通过──> DONE           （机器无关）
                 │                 └─ 机器相关节点：DONE.m<id>（见 §9）
                 ├──部分验收通过──> WIP.m<id> ──剩余项通过──> DONE.m<id>
                 ├──卡住──> BLOCKED ──问题解决──> WIP
                 └──不再需要──> DROPPED（必须在 §5 写原因）
```

| 状态 | 含义 | 允许的下一步 |
| --- | --- | --- |
| `TODO` | 未开始 | 依赖满足后可开工 |
| `WIP` | 正在做，**同一时间只允许一个** | 完成或阻塞 |
| `WIP.m<id>` | 机器相关节点在该机上只完成部分验收（DoD 未满足）；缺项写进 §9.3 | 剩余项通过后改 `DONE.m<id>`；代码再改退回 `WIP` |
| `BLOCKED` | 缺信息/缺决策/外部故障 | 等 §5 的问题有结论 |
| `DONE` | 验收命令跑过、输出记进度日志（`任务台账/进度日志-2026-11.md`）；**机器无关** | 不可再改，除非 §5 有决策记录 |
| `DONE.m<id>` | 同上，且已在机器 m<id> 上验收通过；**机器相关节点必须带后缀** | 可在更多机器上追加后缀 |
| `DROPPED` | 主动放弃 | 必须在 §5 写明原因与替代方案 |

**机器后缀规则**（机器清单与登记办法见 §9.1）：

- **R1** 机器无关节点完成后写裸 `DONE`；机器相关节点（§9.2）完成后写 `DONE.m<当前机>`。
- **R2** `<id>` = §9.1 的机器序号；每台机器第一次接入时自己登记，取 `max(已有 id)+1`，**id 不复用、不跳号**。
- **R3** 同一节点在更多机器上验收通过时追加后缀，按 id 升序：`DONE.m1.m2`。正文可写 `DONE.mx` 简写，**状态列不许写 `mx`**。
- **R4** 带后缀的节点只要代码/数据面再改，退回 `WIP` 并清空后缀，按当前机器重验后重标。
- **R5** 机器无关的 `WIP` 写裸 `WIP`；机器相关节点在某台机器上只完成部分验收时写 `WIP.m<id>`（缺项记 §9.3），该机不得写裸 `DONE`。`BLOCKED` 不带机器后缀。
- **R6** 阶段出口（§2）= 该阶段全部节点在 §9.1 中 `required=是` 的机器上都有证据。
- **R7** 状态列可 grep：`(DONE|WIP)(\.m[0-9]+)*`（并列写法见 R8：先按 `，` 切分再逐段匹配）。
- **R8** 同一节点在不同机器结论不一致时，单元格内并列写两个状态，逗号分隔、按 id 升序：`DONE.m1，WIP.m2`（含义：m1 已通过、m2 未通过）。未通过的机器不得写进 `DONE`；只有该节点在全部 `required=是` 机器都通过时，才拼接成 `DONE.m1.m2`。

### 0.3 一次工作循环（严格按此顺序）

```
1. 读 §1 进度快照（30 秒）
2. 读进度日志最后 5 条（`docs/任务台账/进度日志-2026-11.md`）（知道上次做到哪、有没有半成品）
3. 若 §1 有 WIP → 接着做那个；否则按 §3 顺序取第一个"依赖全 DONE 的 TODO"
4. 读该任务的详述卡（`docs/任务台账/任务详述.md`） + 它引用的详设小节
5. 跑一次该任务的验收命令，确认当前真实状态（不要相信台账，相信代码）
6. 改状态为 WIP，在 §1 记开始时间
7. 写代码
8. 跑验收命令，把关键输出抄进进度日志（`docs/任务台账/进度日志-2026-11.md`）
9. 改状态为 DONE，更新 §1 快照
```

**第 5 步不能省。** 台账可能滞后于代码（上一次会话可能改完代码没来得及改台账）。**代码是事实，台账是记录**——两者冲突时以代码为准，并立即修正台账。

### 0.4 上下文恢复协议（压缩/新会话后）

新会话开始时，你可能什么都不记得。按这个顺序恢复，**不要试图读全部文档**：

```
① 本文 §1（进度快照）                    → 30 秒，知道全局位置
② 进度日志最后 5 条（`docs/任务台账/进度日志-2026-11.md`）                  → 1 分钟，知道最近发生了什么
③ 本文 §3 中 WIP/WIP.m<id>/BLOCKED、或已 DONE 但缺本机后缀的行（对照 §9.2）→ 30 秒
④ 对应任务的详述卡（`docs/任务台账/任务详述.md`）                     → 2 分钟
⑤ `git status` + `git log --oneline -5`  → 确认代码真实状态
⑥ 跑该任务的验收命令                     → 确认是否其实已经做完
```

**⑤⑥ 是关键**：上一次会话可能在"代码写完但没标 DONE"的状态结束。不验证就重做，会浪费一整轮。

**在新机器上恢复时**：先按 §9.1 登记本机拿到 id，再按 §9.2 找出缺本机后缀的节点——那些是必须在本机重验的；机器差异与适配动作记进 §9.3。

### 0.5 完成定义（DoD）

一个任务只有同时满足以下七条，才能标 `DONE`（机器相关节点还要带机器后缀，见第 7 条）：

1. **代码已落盘**，`pnpm build` 通过；
2. **验收命令跑过**，关键输出已抄进进度日志（不是"应该能过"，是"跑过并且过了"）；
3. **该模块的关键分支有单测**（详设 §12.1 列了必测项）；
4. **新增代码里没有未记录的 `TODO` / `FIXME`**（有就记进 §5）；
5. **三处已更新**：§1 快照、§3 状态、进度日志；
6. **生产调用点/接线点存在**：模块被真实进程调用（daemon / CLI / MCP），不是只有测试在调。验收命令必须能证明这一点——只跑单测不算。"模块写好了但没人调"等于没做，P1-08/P1-14 就是这样被误标 DONE 的。
7. **机器相关节点有本机证据**（仅 §9.2 列出的节点）：在 §9.3 的本机行记命令、读数、日期、commit，并在 §3 标 `DONE.m<本机id>`；缺本机行不能标 `DONE.m<id>`。只完成部分验收的，标 `WIP.m<本机id>`，缺项写进 §9.3。

缺任何一条都不算 DONE。**宁可标 WIP，不要虚标 DONE**——虚标会让后续任务建立在不存在的地基上，返工成本是十倍。

### 0.6 遇到不确定时怎么办

| 情况 | 做法 |
| --- | --- |
| 详设写清楚了 | 照做 |
| 详设没写，但概设有原则 | 按原则选一个最简单的实现，**记进决策记录（`docs/任务台账/决策记录.md`）**，继续 |
| 详设和概设冲突 | **以概设为准**，改详设，记 §5 |
| 两者都没写 | 选最保守的方案（不做额外功能、不猜业务规则），记 §5，继续 |
| 需要外部信息（平台格式、库 API） | 先用 `--probe` 类命令实测，把实测结果记进 §5，再实现 |
| 真的做不下去 | 标 `BLOCKED`，§5 写清"试过什么、卡在哪、需要谁决定"，**然后去做下一个任务**——不要停在原地 |

**最重要的一条：不要为了"等一个答案"而停工。** 80 个任务里绝大多数互不阻塞，卡住一个就换一个。

### 0.7 禁止事项

| 禁止 | 原因 |
| --- | --- |
| 改概设的方向性决策 | 那是月级文档，改了会与综述脱节。有异议写 §5 |
| 跳过验收命令标 DONE | 见 §0.5 |
| 一次改多个任务状态（一次性状态模型迁移除外，须在进度日志记一条全项目迁移日志） | 状态机失效后无法判断真实进度 |
| 删除进度日志的历史条目 | 它是唯一的执行轨迹，只能追加 |
| 在任务里"顺手"加功能 | 范围蔓延是长周期任务失败的第一原因。想到的加进 `docs/任务台账/想法池.md` |
| 用 `rm` 清理 `~/.moshi` | 那是用户数据。测试用临时目录 |

### 0.8 日志格式（进度日志追加用）
日志文件（`docs/任务台账/进度日志-YYYY-MM.md`）是 Markdown 表格，一行一条，列固定，便于 grep 与排序：

| 时间 | 任务 | 状态 | 说明 | 证据 | 机器 |
| --- | --- | --- | --- | --- | --- |

- **时间**：`YYYY-MM-DD HH:mm`；历史条目只有日期时只写日期。
- **任务**：卡片 ID（`P0-05` / `P2-19-A` / `P3-A2`）或 `全项目`。
- **状态**：§0.2 的值，含 `DONE.m<id>` / `WIP.m<id>`。
- **说明** / **证据**：一句话结果 / 验收命令输出摘要。单元格内不得换行；出现 `|` 一律写成 `\|`，否则表格会从该处被切断。
- **机器**：本次验收所在机器（`m1` / `m2`…，见 §9.1）；与机器无关或历史未记录写 `-`。

例：

| 时间 | 任务 | 状态 | 说明 | 证据 | 机器 |
| --- | --- | --- | --- | --- | --- |
| 2026-11-02 14:32 | P0-05 | DONE | DDL 建成，user_version=1 | migrate ok, 14 tables, 0.8s | - |
| 2026-11-02 16:10 | P0-06 | BLOCKED | 触发器 json_extract 比较在 SQLite 3.40 上行为不同 | need version pin | - |

## 2 里程碑与验收

> 退出条件原文见 **概设 §12**。这里只给可执行命令。

| Phase | 验收命令 | 通过标准 |
| --- | --- | --- |
| **P0** | `moshi init && moshi import --since 2025-01-01 && moshi doctor` | 事实 ≥ 100；`node`/`nodejs` 同实体；I1–I10 全绿；停 daemon 后 Agent 无感 |
| **P1** | `moshi eval run --golden v1 && pnpm bench`（默认在临时副本上跑；`--vector` 才建向量、跑三路召回） | 时态题 + 拒答题全过；P95 < 80ms；能导出 ≥ 1 篇主题文档 |

| **P4** | `moshi eval report` | 七项消融 + 六项质量基线 |
| **v1.1** | 两仓库并行 + 三平台安装包 | 事实不串味；安装成功率可测 |
