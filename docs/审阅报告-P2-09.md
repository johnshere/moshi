## 一、现在要处理

### M2（阻断）派生要点没有墓碑，也没有反向对账

派生点的身份是"源 id 集合指纹"。系统只查**当前活跃的派生点**，从不检查"当前源集合是否还支撑这条结论"，也不记录"人已经否决过它"。

**复现 1：用户失效派生点 → 下一轮被原样重建**（`temp/review-p2-09/probe.ts`）

```
[1] first  { groups: 1, created: 1, skipped: 0, superseded: 0 }
[1] after user invalidate active points = 0
[1] second run { groups: 1, created: 1, skipped: 0, superseded: 0 } active points = 1 resurrected= true
```

原因：`src/core/lifecycle/consolidate.ts:198-202` 只检查 `listActiveDerivedFacts`（`src/infra/sqlite/consolidationRepo.ts:47-55`，条件带 `valid_to IS NULL`）。被人工失效的要点不在活跃集，源组仍 ≥3，于是重建一条新行。

**这不是边角场景**：派生点 confidence 取源均值，低于 0.45 会进低置信队列；strength 0.5 衰减后会进淘汰候选队列。用户从 `/ui/inbox` 批量失效它（`src/app/http/routes/batch.ts:140` → `inboxRepo.invalidateMany`），下一次任意 `memory_annotate` 触发 harvest，就会把它复活。**用户永远删不掉一条错误结论。**

**复现 2：源观测失效、组跌破阈值 → 旧结论继续活跃**

```
[2] after source invalidated: run { groups: 0, created: 0, skipped: 0 }
    active points = 1  [ 'node 的 runtime_state 为 a、b、c（由 3 次观测归纳）' ]
```

3 条源失效 1 条后只剩 2 条，`listEpisodicGroups` 不再返回该组，巩固直接跳过；旧结论仍 `active`，其 `derived_from` 边指向已失效源。读取侧 `adjudicate` / `evidence` 的 stale 判定只看 `depends_on`（`src/core/read/adjudicate.ts:123-129`、`src/core/read/evidence.ts:132-141`），`derived_from` 不参与，所以**基于已撤回证据的结论不会被标 stale**。

**为什么对账不能只挂在每轮 `consolidate` 上**

`src/app/harvestRunner.ts:88-101` 只在 harvest 之后串行跑巩固，而兜底轮询也只在 `countPending > 0` 时触发。用户从 UI 失效源事实不会产生 annotation；如果没有新写入，`consolidate` 根本不会跑，旧结论会一直活跃。补丁需要二选一：

- 在失效入口（批量失效、单条 PATCH、冲突策略收口兄弟）后主动触发一次受影响 key 的对账；或
- 读取侧把 `derived_from` 纳入 stale 判定（源全部失效 → 结论标 stale），作为兜底。

**墓碑语义要先定义清楚，否则会修出第二个 bug**

现状上有两个可用信号：

- 人工失效（批量 / 单条 PATCH）走 `factRepo.invalidate` 时不传 `supersededBy`，所以 `superseded_by IS NULL`；
- 巩固自动收口旧要点时传 `supersededBy = 新点 id`（`consolidate.ts:231`），所以非空。

但：

- 单条 PATCH 失效（`src/app/http/routes/facts.ts:326-327`）**没有写 audit**，不能只靠 audit 的 `source` 判断人工来源；
- 反向对账如果也用 `supersededBy = NULL` 失效旧要点，就会和"人否决过"混为一谈，导致源集合恢复后**永远无法再产出结论**。

建议补丁里明确：**墓碑只认"人工否决"**（批量失效已有 `ui_batch_invalidate` audit；单条 PATCH 补一条 audit），反向对账写独立来源（如 `rule:consolidate_reconcile`）且不算墓碑；或者给派生行加显式标记。查询"同 `canonical_key` + 同指纹 + 人工失效"的历史行，命中则跳过并计数。

**修法范围**

1. 产出前查墓碑：同 `canonical_key`、同 `attrs.ext.derived_from` 指纹、被人工否决过的派生行存在 → 跳过。
2. 反向对账：每轮（或失效触发时）对"有活跃派生点但当前活跃源 < `minObservations`"的 key 收口旧要点；源集合变化、但仍 ≥ 阈值的，沿用现有 supersede。
3. 让"源撤回"能被读到：失效入口触发对账，或读取侧把 `derived_from` 纳入 stale 判定（至少"源全部失效"这一档）。
4. 单测：失效后不复活；源撤回后结论收口；批量撤销（30s undo）后允许重新产出；反向对账产生的失效不被误判为墓碑。

### M1-min（硬规格）`disputed` 源被洗成 `active`；`N` 的计数口径错误

**证据**

- `src/infra/sqlite/consolidationRepo.ts:32` 的组查询：`ftype='episodic' AND epistemic_status IN ('active','disputed')`；
- 产出固定 `epistemicStatus: 'active'`（`src/core/lifecycle/consolidate.ts:134`）；
- 单测 `disputed 观测参与提炼` 断言 `created: 1`，把这个行为锁死；
- 概设风险表（`docs/概设.md:1423`）写的是："巩固只允许在 ≥3 条**已验证**观测上发生；产出带 `derived_from` 溯源；置信不高于源事实均值"。

**这是文档冲突，不是纯代码失误**：详设 §8.3.1 的 SQL（`docs/详设.md:2552`）确实带 `disputed`，代码照抄了详设；但概设的风险表是更高层的防伪结论约束。`disputed` 的语义是"互斥落败但未失效，仍返回并带 flag"（`src/domain/enums.ts:20-23`），把它当证据提炼成一条 `active` 结论，恰好是风险表要防的"从噪声观测里提炼出看似权威的 semantic 要点"。

**建议（最小修法）**

- 组查询改为只取 `active`；`disputed` 源不参与提炼。同步把详设 §8.3.1 的 SQL 改成一致口径（或反过来在概设里明确允许 disputed 并承担风险——但按当前文档，应以概设为上）。
- 单测改为断言"仅 disputed 的组不提炼"；如果产品确实想把 disputed 作为证据，结论至少应为 `disputed` 而不是 `active`，且要改概设，不是改一行代码。
- 正文把 `由 {n} 次观测归纳` 改成 `由 {n} 个不同取值归纳`（或"n 条观测记录"）。`n` 是组内行数，而同值重复观测已被 harvest 折叠（`src/core/write/harvest.ts:171-173`），所以 `n` 是**不同取值数**，不是观测次数。这是 I-25，但正文正在对用户陈述错误计数，应并入本次补丁。
- 不要再用 `runtime_state` 举例"互斥状态并列"：单值谓词每次新值都会让冲突策略收口旧行（`src/core/write/conflict.ts:100-101`），活跃行凑不到 3 条；能进巩固的真实组主要是 `set` / `series` 的"≥3 个共存取值"。这是语义形态问题（D-107 的后续），本次不裁决。

> 初版建议的 A（按基数性分流）/ B（只归纳同值观测）/ C（降级为摘要）里：B 不可行（同值观测已被折叠）；A 需要补 `cardinalityOf` 查询，属设计取舍；C 是备选。都不阻塞本次补丁。

### M5（硬规格）派生 `content` 绕过 2 KB 上限

- 详设 §5.3（`docs/详设.md:1645`）规定 `content` 上限 2 KB（`max_fact_bytes`），超了截断；harvest / 直写都通过 `clipContent` 执行（`src/core/write/quarantine.ts:91`），**`renderConsolidatedContent` 没有任何截断**，`consolidate` 也拿不到该配置。
- 实测（`temp/review-p2-09/probe3.ts`，3 个 1 KB 取值）：`derived content bytes = 3060 limit=2048`。
- 取值由 Agent 提供，长度不可控；`content` 不可变，一旦落库无法再截。检索入包会按 80 token 截断，但 DB / UI / 归档仍存全量。
- 建议：产出前复用 `clipContent`（配置注入或常量 2048），用截断后的文本落库；`attrs.frozen.value` 保持聚合结构不受影响。补一条超长取值的单测。
