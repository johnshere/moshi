## 1 审视基准

### 1.1 不变的核心方向（审视红线，以下设计不挑战）

1. **外置系统**：不写提示词、不改内核、不注入、不接管工具循环（综述 §17，概设 §1.5）；
2. **单一来源**：一切初始数据只来自 Agent↔LLM 对话产生的数据，moshi 不自采（概设 §3.0）；
3. **单图 + 标签**：单张全局事实图 + `scope`/`mem_type` 标签，拒绝多图物理隔离（K5）；
4. **记忆侧不跑 LLM**：只有 GAT + 查询交叉注意力 + FFN + 冻结 Embedding + 检索（K6）；
5. **GAT 主链路 + K2 正交**：推理特征通路与生命周期元数据通路严格隔离；
6. **要点出境、原文不出境**（综述 §15.5）；
7. **内容 append-only、置信可重估**（概设 §3.6.3）。

## 3 硬伤级（H1–H5）

### H1 谓词基数性缺失：「同 key 多 value 自动互斥」会互斥爆炸

- **位置**：§3.6.2「同一 canonical_key 下可以有多条不同取值的事实，它们自动成为互斥对」；附录 C。
- **问题**：`canonical_key = hash(scope‖subject_entity_id‖predicate)`，同一 key 下多条不同 value 被"自动成为互斥对"。但**这只对单值状态型谓词成立**（version/status/owner）；观测序列型谓词（磁盘用量、构建次数、端口列表）每次观测都是新 value，全部自动互斥。
- **后果**：互斥冲突爆炸，冲突检测退化为噪声；§10.2.1「近似重复比」指标同步被观测序列污染。
- **第三方佐证**：Mem0 社区被报告最多的"同一事实反复入库"即源于此；Graphiti 时态图膨胀也含"观测 vs 状态"未区分。
- **建议**：谓词词表增加**基数性维度**（single-valued / series / set）：仅 single-valued 的多 value 建 `mutex`；series 走时间线（新观测不互斥旧观测）；set 走成员/co-occur 关系。**详设字段时必定**。

### H2 三路召回依赖失效链未定义：向量路超时则 PPR 必死

- **位置**：§4.1 ②「c. 图扩散（以 a 的 top-3 为种子做 2 跳 PPR）」；§4.2「三路召回任何一路超时即丢弃该路」。
- **问题**：a（向量）超时被丢弃 → c（PPR）无种子 → 级联丢弃；"独立超时丢弃"不成立。§4.4 降级表只处理了"c 自己超时"，没处理"a 超时导致 c 无种子"。
- **后果**：向量路一慢，图扩散路同步失效，三路变一路。
- **建议**：定义种子回退链（a→b→a+b），或 PPR 独立用查询实体作种子；§4.4 补一行降级规则。

### H3 被动观测源零工程定义：v1 主通路的数据入口没有落地

- **位置**：§3.1 R2（"每日 03:00 harvest 会话记录"，标注为 **v1 主通路**）；§1.1 拓扑「C1 被动观测，只读尾随」。
- **问题**：主通路没有工程定义——读什么文件（Claude Code `~/.claude/projects/*.jsonl`？Dsh 什么格式？）、格式解析、增量游标存哪、断点续读、文件权限（macOS TCC）、日志轮转、Agent 未运行时的行为。
- **后果**：这是整个系统 80% 数据入口。Graphiti 实践表明 ingestion 层是最重的部分；moshi 无 LLM，观测解析就是全部写入来源，其可靠性直接决定系统生死。§12 Phase 0 只有"解析器（3 个工具）"，没有"会话记录读取器"。
- **建议**：§3.1 补「观测源适配层」：每 Agent 一个适配器 + 增量游标（存元表）+ 格式探测 + 失败静默降级（扫不到则跳过并记日志）。

### H4 巩固「情景→语义提炼」在"记忆侧不跑 LLM"约束下无算法形态

- **位置**：§5.5.2 任务一；§13 风险表「巩固产生伪结论」。
- **问题**：不跑 LLM（继承约束②）前提下，"提炼语义要点"只有两种可能：规则取众数/属性并集（产物 ≈ 冗余事实），或做不到语义概括（"8080 常在 nginx 与 node 之间切换"这类跨观测结论，规则写不出来）。
- **后果**：Cognee 的 cognify、A-MEM 动态建链、Generative Agents 的 reflection **全部依赖 LLM**——这条路线被外置约束结构性堵死。§13 把它当"可缓解"，实际是"做不到"。
- **建议**：Phase 0/1 明确「提炼 = 确定性聚合」（同 key 下已验证观测的属性并集 + 最高置信 content 作要点 + `derived_from`）；**语义概括类结论显式标为不做**（或列为 v2 可选 LLM 支路，届时过外置裁决）。

### H5 value 侧无规范化：幂等键脆弱

- **位置**：§3.6.1 三级消解只覆盖主体实体；§3.6.2 幂等键含 `value_hash`；附录 C `alias` 表只有 entity 别名。
- **问题**：value 存在 `attrs` 自由 JSON，无规范化管道——`22.9.0` / `v22.9` / `22.9` 算三个 value_hash → 同一事实反复入库（幂等失效）→ 又触发 H1 的互斥爆炸。
- **第三方佐证**：Mem0 社区最常见 bug 即同一事实反复入库。
- **建议**：value 走与 subject **共用规范化器**；`attrs` 的 value 字段 schema 化（至少 `value_type: version/port/path/…`），`value_hash` 用规范化后指纹。

## 4 承接遗漏（C1–C5）

### C1 MCP 工具面缺 `memory_correct`

- **位置**：§1.5「三个 MCP tool 全部可缺席」；§12「MCP stub」。
- **问题**：综述 §17.4 明确 `memory_correct` 从"锦上添花"升为**必需工具**（外置形态下 Agent 无法靠提示词自动纠正记忆）；概设 MCP 工具面只有 query/annotate/feedback 三个，漏接。
- **影响**：写错后只能人开 UI 修正；与 E1 叠加，程序化纠错通路整个缺失。
- **建议**：工具面补第 4 个 `memory_correct(fact_id, patch)`；"三工具可缺席"改"四工具"，unplug-safe 与零调用测试同步。

### C2 `ftype` 静默替换了综述的 `mem_type` 分层

- **位置**：§5.2 特征表、附录 C `fact.ftype`（semantic/episodic/conditional）；综述 §5.1 / §14.4（working/episodic/semantic/procedural）。
- **问题**：两套分类轴冲突且概设无说明——procedural（过程记忆）无处安放；working（会话级记忆）无实现路径（§4.6.4 是查询缓存，不是记忆）；conditional 是概设新增轴，与 mem_type 的关系未定义。
- **影响**：实现者会混用两套枚举；GAT 特征 one-hot 与生命周期标签打架；记忆分层能力消失。
- **建议**：定死两轴——`ftype` = 事实性质（GAT 特征用），`mem_type` = 记忆层次（生命周期标签，需补列）；或显式声明"working/procedural 本版砍掉"并说明理由。

### C3 多模态预留接口未承接

- **位置**：§0 继承约束清单。
- **问题**：综述 §1.2-4 明确"多模态预留配置入口，运行期不加载"；概设继承约束与里程碑均未提。
- **影响**：未来加多模态时 schema 无准备（低优先，但属方向漏接）。
- **建议**：§0 补一条"多模态留口、不实现"。

### C4 「空闲 <150MB」验收口径模糊

- **位置**：§1.3「冷启动不加载模型；GAT 权重与 embedding 懒加载」+「空闲内存 < 150MB」。
- **问题**：首次查询后 embedding（约 70MB）+ GAT（约 24MB）+ FAISS 常驻；"空闲"是"从未查询过"还是"查询后空闲"？若模型驻留则不达标。
- **影响**：违反 §0 边界铁律（每个数字必须有验收方式）。
- **建议**：定义"空闲 = 无查询 5 分钟后的常驻集"，或加模型卸载策略，并补验收测试。

### C5 golden set 缺意图分流/全局问题题型

- **位置**：§10.3 四题型（单跳/多跳/时态更新/拒答）。
- **问题**：§4.1 ⓪ 意图分流是查询第一环、全局路径 ⑧ 是 v0.3 新增核心路径，却无任何回归保护。
- **影响**：意图分流误判率没有评测项，全局路径正确性盲飞。
- **建议**：golden set 补「意图分流正确率」「全局摘要下钻可用性」两类题型。

## 5 工程坑（E1–E10）

| # | 位置 | 问题 | 建议 |
| --- | --- | --- | --- |
| **E1** | §3.1.1 / §5.5.1 / §3.6.3 | **feedback 闭环缺失**：adopt/correct/reject 只定义了强度侧（且只有采纳/否决）；verdict→置信映射、Agent 的 correct/reject 是否等同金标签（综述 §5.5「人类纠正=金标签」）未定义。**reject 不联动置信 → 高置信错误事实因置信阈值过滤不掉而永久被召回** | 定义 feedback 消费时点 + 三 verdict 的置信/强度联动表；Agent 显式 reject → 置信打折 + 写 audit |

| **E8** | §9.5 人工编辑保护 | **`.proposed.md` 死胡同**：生成后无合并路径/生命周期——用户无视提示则主文档永久旧版、每次导出覆盖 .proposed.md | 定义三选一动作（采纳建议 / 保留人工版 / 人工版转正）+ UI 必达 + 冲突合并规则 |
| **E9** | §4.6.4 会话内缓存 | **失效条件「任一事实写入即失效」过宽** → 缓存命中率≈0，机制形同虚设 | 失效改为「命中子图相关社区的 `source_rev` 变化」；缓存键 = query 嵌入 + 相关社区版本号 |
