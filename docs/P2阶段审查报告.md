### Z-1 【P1 主要】daemon 的 /mcp HTTP 传输 body 被 Fastify 消费，HTTP 版 MCP 客户端失败（已登记 I-38，未修复）

- 节点：P2-25 / P2-26（既有问题，收口未修；台账 I-38 已登记）
- 位置：`src/app/http/server.ts:156-163`；`src/app/mcp/server.ts:131 createMcpHttpHandler`
- 问题：`app.post('/mcp')` 直接把 `req.raw` 交给 `createMcpHttpHandler`。Fastify 对 `application/json` 会先解析 body，进入 handler 时 `req.raw` 数据流已被读空 → MCP handler 读到空流 → `Parse error: Invalid JSON`。P2-25 施工记录坑 5、P2-26 施工记录均明确记录该问题「影响所有 HTTP MCP 客户端」，建议 Lead 单开卡修；台账 I-38 已登记（「属独立小任务，建议单开卡」），但最终收口 commit（80a0b08）代码形态未变，未见 contentTypeParser / 原始流修复。
- 证据：P2-25 progress「真 daemon 的 POST /mcp 经 Fastify 时 body 已被 Fastify 解析，createMcpHttpHandler 读 req.raw 得到空流 → Parse error: Invalid JSON（既有问题，不在本任务 scope）」；P2-26 progress「真 daemon 的 /mcp body 被 Fastify 消费的问题仍在（P2-25 坑 5），建议 Lead 单开卡修」。
- **实测（2026-11-04，真实 HTTP 端口）**：`buildHttpApp` + `server.listen(0)`，`fetch POST /mcp` 带 `accept: application/json, text/event-stream` → **HTTP 400 `{"code":-32700,"message":"Parse error: Invalid JSON"}`**（`temp/check-mcp-body.ts` 复现）。对照组：`app.inject` 模式下 body 未丢（返回 406 Not Acceptable 而非 parse error）——正因 accept-p2 验收链全部用 inject，此缺陷未被自动化捕获。
- 影响：通过 HTTP 传输的 MCP 客户端无法完成任何 JSON-RPC 调用（stdio MCP 与进程内直连可用，故非全挂）；MCP 是默识对外集成主通道，HTTP 形态在生产 daemon 上不可用。P2-25/26 的 UI 验收因此被迫改用临时 harness 绕过，收口时缺陷仍在。
- 建议：单开修复卡——用 Fastify `addContentTypeParser` 保留原始 body，或让 `/mcp` 走原始 Node listener（不经 Fastify body 解析），并补一条真实 HTTP POST /mcp 的集成测试（不能用 inject 代替，实测两者行为不同）。
