# 后待办

> 定位：本工程台账任务结束之后再启动的工作。以下为三个想法的记录。

## 想法一：采集本机所有 Agent 的会话信息与记忆库，梳理重要的「事实元数据」

- 本工程完成开发之后去做这件事：采集本机上所有 Agent 的会话信息、记忆库（cc、doubao、qoder、dsh、workbuddy 等），梳理重要的「事实元数据」。
- 这是个开发环节，用于采集验证的功能。

## 想法二：适配器改为做在本机网关上

- 原先的适配器方案：给所有矮件做适配器。
- 新想法：给本机网关做一个适配器，比如 Magpie 或 CC Switch —— 这类工具有代理本机所有 Agent 网关的功能，也有接入所有流量的入口。
- 给它们写个插件，就能获取到所有实时会话信息，从中获取一些可用的事实数据和元数据，用来记录下来。
- 这样每天空闲的时候训练本工程记忆库的数据，就会更加真实。

## 想法三：冷启动期注入总开关 + 开启门槛提示

- 背景：系统存在**双向冷启动** —— 语料冷（有效事实少）、监督冷（裁决/反馈标签少）。此时 Hook 侧主动注入属 push：错了无法撤回，还会被模型复述、被采集回灌，形成「注入 → 复述 → 再抽取 → 置信上升 → 下次更靠前」的污染环。冷启动期系统应只是被动记忆库：插入 / 查询 / 反馈，由 Agent 经 MCP 等接口主动调用。
- 开关：给客户一个可自行开/关的「允许 Hook 注入」总开关，**默认关闭**；关闭时 hook 只采集、注入恒不发（注入与否不再由 `hook.inject_existing` 单一布尔决定，而由档位决定）。
- 开关背后是档位，不是一个布尔：
  - **S0 记忆库（默认）**：只采集 + 查询/插入/反馈，不注入。
  - **S1 受信注入**：只注入用户自己写下的事实（`source=user_statement`、`scope=project`、置信 1.0），每轮 ≤2 条、≤400B。不依赖任何模型，污染风险接近零。
  - **S2 模型辅助**：GAT 打开 + 受限注入（仅 `tool_obs` / `user_confirm` 来源、置信 ≥0.75、每轮 ≤3 条、≤800B、同一事实 7 天内不重复）。
- 手动强开必须拦截提示：客户可在 S0 强行打开，但需二次确认，并当场告知当前数据状态与预期效果（示例口径："当前 project 活跃事实 X 条、平均子图 4.4 节点、反馈 0 对，未达门槛；此时注入内容大概率是噪声，且可能污染会话"）。强开决定写入 audit（谁、在什么数据状态下开的）。
- 判定提醒（**由系统算，不让客户自评**）：界面上，开关下方常驻显示「距可开启还差 …」，达到门槛后主动提示「现在可以开启了」。阈值初版口径（可调）：

  | 目标档 | 门槛                                                                                                          |
  | ------ | ------------------------------------------------------------------------------------------------------------- |
  | S1     | project scope 活跃事实 ≥ 150 条                                                                               |
  | S2     | `training_sample` ≥ 500 且覆盖 ≥ 3 种裁决规则；`feedback` ≥ 2000 对；平均子图节点 ≥ 20；δ 不饱和（非贴 ±cap） |

- 实现约束：阈值必须与 `core/ops/gate.ts` 同源，禁止两套口径；不提供「直接跳到 S2」的入口，只能先 `shadow` 观察再 `on`；当前档位与缺口在 UI 可见。
