## 0 结论摘要

**设计就位、执行缺位**。

## 2 问题清单

严重度定义：
`P0` = 核心承诺失效或静默给出错误结果；`P1` = 数据丢失 / 安全 / 明显功能缺陷；`P2` = 健壮性与一致性问题。

### 2.1【P0】Agent 写记忆的闭环是断的

**证据**
- `memory_annotate` 只入队：[`src/app/mcp/annotate.ts:109`](../src/app/mcp/annotate.ts) 调用 `annotationRepo.insert` 后即返回 `accepted`。
- `harvest()` 全仓只有一个调用点：[`src/app/cli/commands/import.ts:189`](../src/app/cli/commands/import.ts)。
- `src/app/main.ts` 的 daemon 只做了一次 `syncMissingFts` 与一次 `syncFactVectors`，**没有定时器、没有 R2 扫描、没有 R3 尾随监听**。
- 配置项 `ingest.harvest_cron`（[`src/app/config.ts:44`](../src/app/config.ts)）没有任何消费者。
- 真实库 `annotation` 表 0 行。

**影响**
Agent 通过 MCP 说“记住 X”，工具返回 `accepted`，但事实永远不进图。整个产品的核心承诺在当前构建里不生效；
`import` 之外的所有写入通道（R1 实时、R2 定时、R3 尾随）都只有一个“队列入口”，没有“出口”。

**性质**
与 P1-19 发现的“读取管道无入口”是同一类病：单测覆盖了每个零件，没人检查零件是否接上。
现有 `tests/unit/mcp.test.ts` 对 `memory_annotate` 只断言 `accepted.length`，不断言事实出现——所以测试是绿的。

**建议**
1. daemon 内加 harvest 消费者（定时 + 写后触发二选一，建议“入队即唤醒 + 兜底定时”）；
2. 增加端到端验收用例：`annotate → harvest → fact 存在`，并写进 Phase 0 验收门槛。

### 2.2【P0】BM25 遇到含冒号的 token 整条查询静默失败

**证据**
- `tokenizeForFts` 的分隔符是 `/[./_\- \t]+/`，**不切冒号**（[`src/core/parse/tokenize.ts`](../src/core/parse/tokenize.ts)），因此 `pkg:node`、`报错: EADDRINUSE`、`12:30` 都会产出带 `:` 的 token。
- `orQuery` 把这些 token 原样用 ` OR ` 拼接。
- [`src/infra/sqlite/ftsRepo.ts:33`](../src/infra/sqlite/ftsRepo.ts) 直接把它们送进 `MATCH`，并且 `catch { return [] }`。

**实测（内存 FTS5 表，`unicode61`）**

```
"pkg:node OR node"      => ERROR: no such column: pkg
"\"pkg:node\" OR node"  => 命中 2 条
"node"                  => 命中 2 条
```

**影响**
1. 任何含冒号的查询，BM25 一路直接归零——而 `pkg:node` 正是本系统最常见的实体书写形式；
2. 失败被 `catch` 伪装成“没有结果”，上层无法标出 `bm25_error`，违反详设“不得把失败报成 ok+空”的原则。

**建议**
`orQuery` 给每个 token 加双引号（FTS5 短语语法），并在 `bm25Search` 里把异常上抛或返回判别值，让 recall 层能标降级。

### 2.3【P0】证据缓存失效不完整：纠正置信后仍返回旧值

**证据**
- `migrations/001_init.sql` 里 `schema_rev` 只有一个触发器，且只挂 `AFTER INSERT ON fact`（注释写的是“任何写入 +1”）。
- `UPDATE confidence`、`invalidate()`（改 `valid_to` / `epistemic_status`）、建边、社区摘要**都不推高 rev**。
- `EvidenceCache` 以 `schemaRev` 为失效键（P1-20 编排器注入了 `buildEvidenceCache`）。

**影响**
用户 `memory_correct` 把置信 0.9 改成 0.3 → 在 TTL（默认 5 分钟）内同一问题仍返回 0.9。
这是“静默错误”，比报错更难发现；审计表里留着正确的历史，证据包里给的却是旧值。

**建议**
补迁移：`AFTER UPDATE OF confidence, epistemic_status, valid_to ON fact` 与 `edge` 表的 rev 触发器；
把“任何写入 +1”的注释与实现对齐，或直接改为覆盖 `fact`/`edge`/`community_summary` 三张表的统一计数。

### 2.4【P0】版本类事实永不失效（真实库 100% 命中）

**证据**
- `DEFAULT_SINGLE_VALUED` 白名单只有 `installed_version` / `runtime_version` / `package_manager` / `occupied_by` / `git_branch` / `git_head` / `env_var` / `build_result` / `test_result`（[`src/core/write/conflict.ts:22`](../src/core/write/conflict.ts)）。
- **`version` 不在名单里**，而兜底解析器 `ver.generic` 产出的谓词正是 `version`（[`src/core/parse/parsers/pkg.ts:196`](../src/core/parse/parsers/pkg.ts)）。
- 真实库 60/60 条事实的谓词都是 `version`。

**影响**
`git version 2.43`（半年前）与 `git version 2.44`（今天）同时 active 并存，读取侧两条都给。
`running`（ps）、`port_conflict` 同类：不在白名单且没有 TTL。
**这直接打掉 moshi 相对 Mem0 的主打差异点——时态正确性。**

**建议**
1. 短期：把 `version`、`running`、`port_conflict` 纳入单值（或按“带时间窗口的 series”）策略；
2. 中期：谓词基数不应由代码硬编码白名单决定，应优先读 `ontology` 表（该表已在 schema 里但无人写入），白名单只作兜底；
3. 补一条验收：同一主体先后两次不同版本观测 → 只返回最新一条。

### 2.5【P1】增量读取时 tool_use ↔ tool_result 跨批次配不上

**证据**
`pending` 缓冲在每次 `readEpisode` 内部新建（[`src/core/adapters/claude-code.ts:275`](../src/core/adapters/claude-code.ts)），
而真实会话是“先落 `tool_use` 行，若干秒后落 `tool_result` 行”。

**影响**
若两次 `import`/轮询正好切在中间：第二次读到的 `tool_result` 配不到名字 →
`toToolTurns` 把它归成 `unknown` → 所有解析器的 `tools: ['bash']` 都不匹配 →
**该工具回合的事实永久丢失**，且没有任何计数或告警。

`readLines` 对“半行”的处理是正确的，但“半条对话”这个维度没有处理。

**建议**
pending 按 `sessionId` 持久化到游标文件旁；或 `tool_result` 无配对时回退一行重读。

### 2.6【P1】向量索引只在进程启动时补一次，且真实环境全程关闭

**证据**
- [`src/app/main.ts:97`](../src/app/main.ts) 的 `syncFactVectors` 是启动时跑一次的 IIFE。
- `import` 是独立进程；它写入的事实 daemon 侧不会再补向量。
- 真实库 `meta.vector_disabled = '1'`，即 sqlite-vec 未能加载，`knn()` 一路返回 `[]`。

**影响**
1. 长驻进程内，新事实对 KNN 永久不可见（直到重启）；
2. P1-02 的向量路在当前安装里**完全没有跑**，而这一点在 UI 状态条之外没有任何告警；
3. 后续 golden set 与 P95 基准都会在“没有向量路”的前提下测量。

**建议**
写入后异步补向量（或 harvest 结束钩子触发增量 sync）；把 `vector_disabled` 提升为显式红灯（现为 `meta` 里一行数据）。

### 2.7【P1】失败即丢弃，没有重放入口

**证据**
`markError` 同时写入 `harvested_at`（[`src/infra/sqlite/annotationRepo.ts:96`](../src/infra/sqlite/annotationRepo.ts)）——注释说明这是为了防止毒数据堵队列，方向正确，但**没有配套的重放能力**。

**触发面不小**
`normalizePredicate` 会剥掉所有非 ASCII 字符（[`src/core/parse/normalizers.ts:110`](../src/core/parse/normalizers.ts)）。
模型只要提交一个中文谓词（如 `已安装版本`）→ 返回 `null` → `buildIdentity` 抛 `E_INPUT` → 整条 annotation 永久标记 error。

**影响**
对一个中文产品，这是一条系统性的静默丢失路径：数据丢了，UI 上看不到，只能翻 `annotation.error` 字段。

**建议**
1. 提供 `moshi queue retry [--all|--id]`；
2. 谓词规范化失败时降级为 `unnormalized:<hash>` 而不是抛错，或至少在 MCP schema 层限制谓词字符集并给出可读报错。

### 2.8【P1】脱敏只覆盖事实表，原文永久落盘

**证据**
- `annotate` 通道在入队前脱敏（正确）：[`src/app/mcp/annotate.ts:53`](../src/app/mcp/annotate.ts)。
- **`tool_parse` 通道没有**：`ingestEvent` 把 `cmd` + `output` 原文 `canonicalJson` 进 `annotation.payload_json`（[`src/core/write/ingest.ts:112`](../src/core/write/ingest.ts)）。
- 该表无删除、无保留期；`quarantine.payload_json` 同理。
- `episode` 只存 `summary` + `raw_path`，原文存档依赖 Agent 自己的会话文件（可能被轮转删除）。

**影响**
`export GITHUB_TOKEN=ghp_xxx` 这类命令的明文会长期躺在 `~/.moshi/moshi.db` 里，而事实表是干净的——
比“完全没脱敏”更容易被误判为“已脱敏”。

**建议**
入队时统一脱敏；`harvested_at` 落定后清空 payload（保留 hash + 摘要即可）；
`quarantine` 增加保留期/上限。

### 2.9【P1】`/mcp` 无鉴权，`/ui` 无鉴权下发 token

**证据**
鉴权 hook 只匹配 `/api/*`（[`src/app/http/server.ts:42`](../src/app/http/server.ts)），`POST /mcp` 直接透传给 MCP handler；
`GET /ui` 不校验任何凭据，却把 `token` 拼进 HTML。

**影响**
虽然只绑回环，但**本机任意进程**都能调 `memory_correct`——四个工具里唯一的 `destructiveHint: true`。
`/ui` 则等于“给任何能访问回环的客户端发钥匙”。

**建议**
`/mcp` 复用同一 token（或独立的 MCP token）；`/ui` 至少校验 `Host` / `Origin` headers，token 改为一次性换取。

### 2.11【P2】Windows 路径大小写不折叠

`normalizePath` 只把盘符小写（[`src/core/parse/normalizers.ts:64`](../src/core/parse/normalizers.ts)），
`C:/Users/John/App` 与 `c:/users/john/app` 会生成两个实体、两组身份键。
目标平台是 Windows，这类重复会持续污染实体表与幂等索引。

另：`normalizeVersion` 会丢掉预发布后缀（`1.0.0-rc1` → `1.0.0`），两个不同的预发布版本会被判为同一取值。

### 2.12【P2】`ps` 是事实放大器，图结构没有长出来

**证据**
`proc.ps` 对输出每一行产一条 `running` 事实（[`src/core/parse/parsers/proc.ts:93`](../src/core/parse/parsers/proc.ts)），一次 `ps aux` 就是 100+ 条；
基数 `set` 且无 TTL → 永不失效、永不合并。真实库当前 `edges = 0`、全部节点 `degree = 0`。

**影响**
一旦接上 R2/R3 扫描，图会立刻开始膨胀；而 PPR 需要边走，现在无路可走。

**建议**
`proc.ps` 改为“只记录与当前项目相关的进程”（按 cwd / 端口 / 已知包名过滤），或降级为 episodic 且带短 TTL。

### 2.13 其他（记录，不单独立项）

- `confidence.ts` 的 `DEFAULT_PRIORS.derivedCap = 0.9`，而 `config.ts` 的 `prior_derived = 0.7`——两处默认值不一致。
- `SidecarClient.status().rssMb` 恒为 `null`（从未从 `health()` 回填）。
- `SidecarClient.encode` 把**超时**也计入崩溃次数，慢机器上 3 次超时会让 sidecar 停用一小时。

- `entity` 合并（`merged_into`）后，事实的 `canonical_key` 仍指向旧实体，**合并不会合并事实的幂等键** —— 合并功能上线时需要一并处理。

## 3 与同类系统的横向对比

| 维度 | moshi 现状 | 同类做法 | 差距评估 |
|---|---|---|---|
| 矛盾消解 | 仅 9 个白名单谓词做失效，其余永久并存 | Mem0：LLM 判 ADD / UPDATE / DELETE / NOOP；Zep·Graphiti：按 episode 做 edge invalidate | **最大差距**，且直接打掉“时态正确”卖点 |
| 图结构 | 真实库 0 条边 | Graphiti 每 episode 抽实体+关系；Cognee 用图谱做管线 | 图只在 schema 里有，数据里没有 |
| 遗忘 / 衰减 | `lifecycle` 配置齐全，**无执行代码**（P2） | MemoryOS 热度分层晋级；A-MEM 动态重连 | 事实只增不减，越用越脏 |
| 冲突可追溯 | `audit` + `adjudication` 两张表，设计比多数开源项目细 | Mem0 多数只留 history | **这是优势**，但要先有失效动作才用得上 |
| 双时态 | `valid_at` / `valid_to` / `recorded_at` 齐全 | Graphiti 同样支持 | 设计领先，实现没跟上 |
| 命名空间隔离 | `scope` 硬锁 `global` | Mem0 / Zep 按 user / agent 隔离 | 已知的 Phase 0 限制，v1.1 前置 |
| 敏感信息 | 事实层脱敏，原文层不脱敏 | 主流实现多在入库前统一过滤 | 需要补齐 |
| 写入闭环 | annotation 无消费者 | 主流都是“写 → 抽取 → 合并”同步或异步闭环 | 当前最致命的一条 |

**一句话**：与 Mem0 / Zep 的核心差距不在架构，而在“写入闭环有没有人消费”这一件事上；
设计上 moshi 已经领先（双时态 + 审计 + 裁决 + 隔离区），实现上落后在“动作落地”。
