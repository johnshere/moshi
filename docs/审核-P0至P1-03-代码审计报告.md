## 2 问题清单

严重度定义：
`P0` = 核心承诺失效或静默给出错误结果；`P1` = 数据丢失 / 安全 / 明显功能缺陷；`P2` = 健壮性与一致性问题。

### 2.1【P0｜复核未修复】Agent 写记忆的闭环是断的

**证据**
- `memory_annotate` 只入队：[`src/app/mcp/annotate.ts:109`](../src/app/mcp/annotate.ts) 调用 `annotationRepo.insert` 后即返回 `accepted`。
- `harvest()` 全仓只有一个调用点：[`src/app/cli/commands/import.ts:189`](../src/app/cli/commands/import.ts)。
- `src/app/main.ts` 的 daemon 只做了一次 `syncMissingFts` 与一次 `syncFactVectors`，**没有定时器、没有 R2 扫描、没有 R3 尾随监听**。
- 配置项 `ingest.harvest_cron`（[`src/app/config.ts:44`](../src/app/config.ts)）没有任何消费者。
- 真实库 `annotation` 表 0 行。

**影响**
Agent 通过 MCP 说“记住 X”，工具返回 `accepted`，但事实永远不进图。整个产品的核心承诺在当前构建里不生效；
`import` 之外的所有写入通道（R1 实时、R2 定时、R3 尾随）都只有一个“队列入口”，没有“出口”。

**建议**
daemon 内加 harvest 消费者（“入队即唤醒 + 兜底定时”）；增加端到端验收 `annotate → harvest → fact 存在`。

---

### 2.2【P0｜复核未修复】BM25 遇到含冒号的 token 整条查询静默失败

**证据**
- `tokenizeForFts` 的分隔符是 `/[./_\- \t]+/`，**不切冒号**（[`src/core/parse/tokenize.ts:21`](../src/core/parse/tokenize.ts)），因此 `pkg:node`、`报错: EADDRINUSE`、`12:30` 都会产出带 `:` 的 token。
- `orQuery` 把这些 token 原样用 ` OR ` 拼接（[`src/core/parse/tokenize.ts:91`](../src/core/parse/tokenize.ts)）。
- [`src/infra/sqlite/ftsRepo.ts:33`](../src/infra/sqlite/ftsRepo.ts) 直接送进 `MATCH`，并 `catch { return [] }`。

**实测（内存 FTS5 表，`unicode61`）**

```
"pkg:node OR node"      => ERROR: no such column: pkg
"\"pkg:node\" OR node"  => 命中 2 条
"node"                  => 命中 2 条
```

**影响**
1. 任何含冒号的查询，BM25 一路直接归零——而 `pkg:node` 正是本系统最常见的实体书写形式；
2. 失败被 `catch` 伪装成“没有结果”，`recallBm25` 返回空数组、`search.ts` 的 `try/catch` 也抓不到，**整个证据包仍报 `status:'ok'`**，违反详设 §6.13“查失败绝不报 ok + 空”。

**建议**
`orQuery` 给每个 token 加双引号（FTS5 短语语法）；`bm25Search` 把异常上抛或返回判别值，让 recall 层能标 `bm25_error`。

---

### 2.3【P0｜复核未修复】证据缓存失效不完整：纠正置信后仍返回旧值

**证据**
- `migrations/001_init.sql` 里 `schema_rev` 只有一个触发器，且只挂 `AFTER INSERT ON fact`（注释写的是“任何写入 +1”）。
- `UPDATE confidence`、`invalidate()`（改 `valid_to` / `epistemic_status`）、建边、社区摘要**都不推高 rev**。
- `EvidenceCache` 以 `schemaRev` 为失效键（[`src/app/mcp/deps.ts:26`](../src/app/mcp/deps.ts)）。

**影响**
用户 `memory_correct` 把置信 0.9 改成 0.3 → 在 TTL（默认 5 分钟）内同一问题仍返回 0.9。
这是“静默错误”，比报错更难发现；审计表里留着正确的历史，证据包里给的却是旧值。

**建议**
补迁移：`AFTER UPDATE OF confidence, epistemic_status, valid_to ON fact` 与 `edge` 表的 rev 触发器。

---

### 2.4【P0｜复核未修复】版本类事实永不失效（真实库 100% 命中）

**证据**
- `DEFAULT_SINGLE_VALUED` 白名单只有 9 个谓词，**`version` 不在名单里**（[`src/core/write/conflict.ts:22`](../src/core/write/conflict.ts)）。
- 兜底解析器 `ver.generic` 产出的谓词正是 `version`（[`src/core/parse/parsers/pkg.ts:196`](../src/core/parse/parsers/pkg.ts)）。
- 真实库 60/60 条事实的谓词都是 `version`。

**影响**
`git version 2.43`（半年前）与 `git version 2.44`（今天）同时 active 并存，读取侧两条都给。
**这直接打掉 moshi 相对 Mem0 的主打差异点——时态正确性。**

**建议**
短期把 `version`、`running`、`port_conflict` 纳入单值/带时间窗的 series；中期谓词基数以 `ontology` 为准（但见 §2.15：它现在根本没人写）。

### 2.5【P1】增量读取时 tool_use ↔ tool_result 跨批次配不上

`pending` 缓冲在每次 `readEpisode` 内部新建（[`src/core/adapters/claude-code.ts:275`](../src/core/adapters/claude-code.ts)）。
若两次 `import` 正好切在 `tool_use` 与 `tool_result` 之间：第二次读到的 `tool_result` 配不到名字 → 归成 `unknown` → 所有解析器的 `tools:['bash']` 都不匹配 → **该回合事实永久丢失**，且无计数无告警。

**建议**
pending 按 `sessionId` 持久化到游标文件旁，或 `tool_result` 无配对时回退一行重读。

### 2.6【P1｜复核未修复】向量索引只在进程启动时补一次

[`src/app/main.ts:97`](../src/app/main.ts) 的 `syncFactVectors` 是启动时跑一次的 IIFE。`import` 是独立进程，它写入的事实 daemon 侧不会再补向量；长驻进程内新事实对 KNN 永久不可见（直到重启）。
真实库 `vector_disabled='1'`，即 sqlite-vec 未能加载，向量路全程关闭；P1-02 的 KNN 在当前安装里**完全没有跑**，而这只在 UI 状态条里体现。

**建议**
写入后异步补向量（harvest 结束钩子）；`vector_disabled` 升级为显式红灯。

### 2.7【P1】失败即丢弃，没有重放入口

`markError` 同时写入 `harvested_at`（[`src/infra/sqlite/annotationRepo.ts:96`](../src/infra/sqlite/annotationRepo.ts)）——方向正确，但**没有配套重放**。
`normalizePredicate` 会剥掉所有非 ASCII 字符（[`src/core/parse/normalizers.ts:110`](../src/core/parse/normalizers.ts)）：模型提交中文谓词（如 `已安装版本`）→ 返回 `null` → `buildIdentity` 抛 `E_INPUT` → 整条 annotation 永久 error。

**建议**
提供 `moshi queue retry`；谓词规范化失败降级为 `unnormalized:<hash>`，或在 MCP schema 层限制字符集并给可读报错。

**建议**

## 3 P1 读取通路问题（P1-04 ~ P1-21）

### 3.1【P0】finalScore 丢掉融合分：证据排序与查询相关性脱钩

**证据**
- 详设 §6.7 原文（[`docs/详设-默识记忆系统.md:2071`](详设-默识记忆系统.md)）：
  ```
  base       = fusedScore(f)                  // §6.5 的融合分
  neural     = scored ? (f.confidence + δ_f) : f.confidence
  finalScore = 0.55 * base + 0.30 * neural + 0.15 * strength
  ```
- 实现（[`src/core/read/adjudicate.ts:143`](../src/core/read/adjudicate.ts)）：
  ```ts
  finalScore: 0.55 * f.confidence + 0.3 * neuralScore + 0.15 * f.strength
  ```
  两处偏差叠加：`base` 被换成了 `confidence`；`neural` 在 P1 由 `opts.neural ?? new Map()` 恒为 0（[`adjudicate.ts:66`](../src/core/read/adjudicate.ts)），而 `search.ts` 调用时根本没有传 `neural`。
- `fuseRank` 算出来的 `FusedItem.final`（RRF + 实体 + 时序）在 `search.ts` 里**只用于决定谁进子图和前 8 个种子**，从未进入打分（[`search.ts:406`](../src/core/read/search.ts) 之后无任何 `fused` 引用）。
- 单测把偏差固化成了断言：[`tests/unit/adjudicate.test.ts:142`](../tests/unit/adjudicate.test.ts) 期望 `0.55*0.8 + 0.3*0.6 + 0.15*0.4`，注释却写“base”。

**影响**
1. 证据包排序实际 = `0.55×confidence + 0.15×strength`，**与查询文本、实体命中、时序窗口全部无关**。一个高置信的无关邻居会压过 BM25/向量第一名的直命中。
2. `fuse` 段（P1-06）的所有信号只影响“能否进入候选集”，不影响顺序——这使 RRF 融合在最终输出上是空转的。
3. 装箱先装 floor 池再装 util 池，`slice(0, topK)` 又在装箱之后（[`search.ts:441`](../src/core/read/search.ts)），所以直命中还可能被 floor 池挤出 `top_k`。这就是台账 B-3 观察到的现象；但 **B-3 把原因归给“详设权重如此”，实际是 base 传错了参数**。
4. GAT 接入（P3）后，`neural` 的 30% 权重也是从零长出来的，届时排序还会再变一次——等于现在建立的排序基线不可用。

**建议**
1. `adjudicate` 增加 `baseScores: ReadonlyMap<string, number>`（来自 `fused`），按详设公式取 `base`；
2. 无 GAT 时 `neural` 回落为 `confidence`（详设原文如此），而不是 0；
3. 修正单测，并补一条“融合分第一的直命中必须排在无关高置信邻居之前”的回归用例；
4. `top_k` 截断放在装箱前或按融合序优先，避免 floor 池挤掉相关命中。

### 3.2【P0】互斥判定在生产上不可达

**证据**
- `runSchemaInfer`（[`src/core/lifecycle/schema-infer.ts:40`](../src/core/lifecycle/schema-infer.ts)）全仓**没有任何调用点**：没有 CLI 子命令、没有 daemon 定时器、没有 harvest 钩子。

- 结果是真实库 `adjudication=0 行`；`conflicts` 恒空、`disputed` 恒无。

**影响**
P1-08“符号兜底五步”里最核心的一步在生产环境**从未执行过**。单测之所以绿，是因为测试自己先往 `ontology` 里写了 cardinality。

**建议**
1. 给 `runSchemaInfer` 一个执行点（daemon 每次 harvest 后 / `moshi doctor --fix` / 启动时一次）；
2. 验收用例必须从“空 ontology 库”起步，禁止测试手工预置 cardinality 以外还断言生产可达；
3. 台账把 P1-14 的 DONE 改为“代码完成、接线待补”更诚实。

### 3.3【P0】缓存键漏掉过滤参数

**证据**
- 键只由 `tokens(normalizedQuery) + scope + JSON.stringify(flags)` 组成（[`src/core/read/cache.ts:51`](../src/core/read/cache.ts)）；`flags` 只含 `gat/self_attn/cross_attn/vector/bm25/ppr`（[`search.ts:289`](../src/core/read/search.ts)）。
- `top_k`、`include_history`、`ftype`、`time_range` **均未进键**，而它们直接改变证据集。
- 实测 C（内存库，6 条事实、有缓存）：
  ```
  first packed 6 cached false
  second(topK=1) packed 6 cached true
  third(includeHistory) cached true
  ```

**影响**
同一会话内先宽后窄、先窄后宽、先历史后当前，都会拿到**另一次查询的证据包**。`[M#]` 编号与 `query_id` 虽重新生成，但对应的事实集是错的——Agent 会引用“这次没查过”的事实。这是静默错误，且只在有缓存（daemon/MCP 主路径）时出现。

**建议**
键里加入 `{top_k, include_history, ftype, time_range}` 的规范化 JSON；或对“过滤参数不同的同一 query”直接跳过缓存。

### 3.4【P0】意图分流的 `'all'` 是子串匹配

**证据**
- [`src/core/read/route.ts:23`](../src/core/read/route.ts) 的 `GLOBAL_WORDS` 包含 `'all'`，匹配方式是 `query.toLowerCase().includes(w)`（[:29](../src/core/read/route.ts)）。
- 实测 C（内存库）：
  ```
  route "how to install a package" {"route":"global","globalWord":true,"hasEntity":false}
  route "整体情况如何"              {"route":"global","globalWord":true,"hasEntity":false}
  route "small note"               {"route":"global","globalWord":true,"hasEntity":false}
  ```
  `install`、`small`、`allocation` 都含 `all`。
- 全局路径**不返回任何单条事实**（[`search.ts:166`](../src/core/read/search.ts) `buildGlobalPack`），只给主题摘要——而真实库 `community=0`、无摘要。

**影响**
英文查询只要含 `all` 子串且没有识别到实体（中文产品里实体表覆盖有限），就会走全局路径，得到“无摘要 + partial”的空包，并且 `status` 是 `degraded` 而不是报错——用户看到的是“没记住”，实际是“没查”。

**建议**
`'all'` 从全局词表移除，或改为**按词边界**匹配（`\ball\b`），并对中文词表保持 `includes`；分流单测补 `install` / `small` 反例。

### 3.5【P1】读取路径在数据库里写 adjudication

**证据**
- `adjudicate` 的 ② 步在每次查询中调用 `openAdjudicationOnce`（[`src/core/read/adjudicate.ts:107`](../src/core/read/adjudicate.ts)）——SELECT 后再 INSERT，**无事务**。
- `search.ts` 对 `adjudicate` 没有任何 `try/catch`（编排层其余各段都有）：只读连接（`readonly:true`）、库锁、磁盘满都会让整条查询抛异常。
- 表注释明说 adjudication 是“GAT 唯一的**非循环**标签来源”（[`src/infra/sqlite/adjudicationRepo.ts:3`](../src/infra/sqlite/adjudicationRepo.ts)）；而读取时的规则裁决是按当时候选集做的，随查询变化，把它当训练标签是自我蒸馏。

**影响**
1. 一旦 §3.2 接线完成，**每次查询都会写库**：读路径变成写路径，违反 §6.1“本层不碰写”的分层约定；
2. 并发查询下 `adjudication` 里会出现大量随查询漂移的 `mutex_win` 记录，`findMutexWin` 取 `ORDER BY decided_at DESC` 会拿到最新一次读取时的裁决，而不是写入时的稳定结论；
3. 归档里的“裁决胜者”也因此失去意义（见 §3.8）。

**建议**
读取路径只做**内存内判定**并输出 `disputed/conflicts`；adjudication 落库改由写入侧（harvest）或显式反馈（`memory_feedback` 采纳/推翻）触发。

### 3.6【P1】`stale_dependency` 在默认读取路径恒不触发

**证据**
- `passFilters` 默认只保留 `epistemic_status === 'active'`（[`search.ts:129`](../src/core/read/search.ts)），非 active 事实在 `adjudicate` 之前就被剔除。
- `adjudicate` ④ 的 `invalid` 集从**已过滤的 working 列表**里取（[`adjudicate.ts:120`](../src/core/read/adjudicate.ts)），因此默认路径恒为空，`stale_dependency` 永不标记。
- `evidence.ts` 的 `dependency_summary.stale` 只看 **packed** 事实的状态（[`evidence.ts:141`](../src/core/read/evidence.ts)）——失效前置不在包里，`stale` 恒 `false`。

**影响**
§6.7 ④ 与 §4.4 的 `stale` 语义在常规查询里是死代码；只有 `include_history=true` 时才可能生效。依赖失效是生命周期链条里的关键信号，现在等于没有。

**建议**
④ 的失效判定应基于**未过滤的完整子图**（或单独查前置状态），而不是过滤后的候选；`dependency_summary.stale` 同理改为查库判定。

### 3.7【P1】`RANGE_RE` 带 `/g` 却用 `.test()`，时序分类会抖

**证据**
`const RANGE_RE = /\d{4}-\d{2}(?:-\d{2})?/g`（[`fuse.ts:32`](../src/core/read/fuse.ts)），`detectTimeKind` 用 `RANGE_RE.test(query)`（[`fuse.ts:106`](../src/core/read/fuse.ts)）。带 `g` 的正则 `test` 会推进 `lastIndex`：第一次命中后，第二次对同样文本的 `test` 从上次位置继续，可能返回 `false` 并重置。

**影响**
同一会话里对同一条“2026-08 端口冲突”式查询，时序加成（`+0.20 × recencyScore`）会时有时无；表现为融合排序抖动，很难复现定位。

**建议**
改为无 `g` 的正则，或 `RANGE_RE.lastIndex = 0` 后再测（更稳妥的是拆成 `/\d{4}-\d{2}/` 检测 + 带 `g` 的匹配两个常量）。

### 3.8【P1】归档“冲突与裁决”把规则名当成事实内容

**证据**
`findMutexWin` 返回的是 `decided_by` 列（规则名 `'mutex_by_confidence@1'`），不是胜者 fact_id（[`adjudicationRepo.ts:112`](../src/infra/sqlite/adjudicationRepo.ts)）；`render.ts` 却用 `contentOf.get(adj.decidedBy)` 找胜者内容（[`render.ts:88`](../src/core/archive/render.ts)）。

**影响**
一旦有互斥边，归档会渲染成“互斥，裁决为 mutex_by_confidence@1”。要拿到胜者只能从 `fact_ids` 里减去败者，而当前 repo 没暴露这层语义。

**建议**
`findMutexWin` 返回 `{ winnerFactId, loserFactId, rule }`（按排序后的 `fact_ids` 与败者标记推导），渲染层只用 `winnerFactId`。

### 3.9【P1】识别器只认正斜杠路径；端口正则过宽

**证据**
- `PATH_RE = /(?:[A-Za-z]:)?(?:~|\.{1,2})?\/[\w./-]+/g`（[`recognize.ts:34`](../src/core/read/recognize.ts)）只匹配 `/`，**不匹配 Windows 反斜杠**；`C:\Users\john\...` 在目标平台上是常态。
- `PORT_RE = /\b:?(\d{2,5})\b/g`（[`recognize.ts:33`](../src/core/read/recognize.ts)）把任何 2~5 位数字当端口候选：`2026`、`21`、`80` 全部进 alias 查询。
- `LOCAL_HINTS`（[`route.ts:26`](../src/core/read/route.ts)）同样只认 `/`，反斜杠路径不构成“局部证据”。

**影响**
Windows 路径查询（本项目的主要使用场景）既可能被误判为全局，也拿不到路径实体 → 实体加成 `+0.25` 永远拿不到。端口候选膨胀则让每次查询多做几十次 alias 查询，吃掉 5ms 预算。

**建议**
路径正则同时接受 `\\`（转义后），并对盘符 + 反斜杠做规范化；端口候选限定 `:\d{2,5}\b` 或落在已知端口范围（或先查 alias 再决定）。

### 3.11【P2】其他（读取通路记录）

- **截断后 token 计数低估**：`pack.ts` 用 `Math.min(est, 80)` 计数，但 `truncateToFirstSentence` 保留到第一个句号，长句可能远超 80 token；实际预算被低估（[`pack.ts:86`](../src/core/read/pack.ts)）。
- **topic_hint 跨 scope**：`getLatestSummary` 不限定 scope（[`communityRepo.ts:144`](../src/infra/sqlite/communityRepo.ts)），不同 scope 的摘要可能串到证据包；P1 无社区时 `coverage` 恒 `partial`。
- **`isSeed` 语义偏差**：`buildSubgraph` 把所有 fused id 都标 `isSeed`（[`subgraph.ts:113`](../src/core/read/subgraph.ts)），而 §6.6 的种子是前 8；目前对排序无实质影响，但节点统计口径与“种子覆盖率”类指标会失真。
- **外部边保留**：边裁剪是 `inside.concat(outside).slice(0, maxEdges)`（[`subgraph.ts:89`](../src/core/read/subgraph.ts)），端点不在集合内的边仍会进 `subgraph.edges`，进而进 `adjudicate` ④ 与 `dependency_summary`。
- **邻居截断顺序**：`neighbors` 先按 `weight DESC` 截 400（[`edgeRepo.ts:89`](../src/infra/sqlite/edgeRepo.ts)），subgraph 再按 etype 优先级排序；高权重低优先级边可能占满窗口，把 `mutually_exclusive` 挤掉。
- **schema-infer 只做了一半**：`attr_keys` 恒返回 `[]`（[`schema-infer.ts:32`](../src/core/lifecycle/schema-infer.ts)），详设 §8.5 的属性键推断缺失。
- **归档 N+1**：`selectTopics` 每个社区再跑两次查询（[`topics.ts:29`](../src/core/archive/topics.ts)）；`archiveAll` 每次全量渲染，`content_hash` 只省写盘不省计算。
- **实体识别跑两遍**：`routeIntent` 与 `searchWithPipeline` 各调一次 `recognizeEntities`（[`search.ts:249`](../src/core/read/search.ts)、[:285](../src/core/read/search.ts)），alias 查询翻倍，3ms + 5ms 预算被拆成 8ms。
- **埋点同步写**：`logQuery` 在请求路径内同步写两张表且无事务（[`logRepo.ts:32`](../src/infra/sqlite/logRepo.ts)），并发下 `SQLITE_BUSY` 概率上升（失败只 warn，不致命）。
- **状态条 FTS 判据**：`/api/status` 用 `countFts() > 0` 判 on（[`server.ts:78`](../src/app/http/server.ts)），不比对 `fact` 行数，缺行时仍显示绿灯。
- **UI 无查询入口**：REST 只有 facts 的列表/详情/改置信（`routes/facts.ts`），证据包只能从 MCP 取；UI 状态条无法验证读取通路。

## 4 与同类系统的横向对比

| 维度 | moshi 现状 | 同类做法 | 差距评估 |
|---|---|---|---|
| 排序/相关性 | 融合分不进 finalScore，按 confidence×strength 排（§3.1） | Mem0 以向量相似度为主 + recency/importance；Zep 用 relevance + 时间衰减 | **新发现的最大差距**，直接决定“查得准不准” |
| 矛盾消解 | 读侧互斥不可达（§3.2）+ 写侧 9 个白名单谓词 | Mem0：LLM 判 ADD/UPDATE/DELETE/NOOP；Graphiti：按 episode 做 edge invalidate | **最大差距**，且直接打掉“时态正确”卖点 |
| 图结构 | 真实库 0 条边；PPR/子图无数据基础 | Graphiti 每 episode 抽实体+关系；Cognee 用图谱做管线 | 图只在 schema 里有，数据里没有 |
| 缓存一致性 | TTL + 余弦，但键漏过滤参数、rev 只在 INSERT 递增 | 多数系统按 query+filter 做键，写库即失效 | 静默错误风险高于同类 |
| 遗忘 / 衰减 | `lifecycle` 配置齐全，**无执行代码**（P2） | MemoryOS 热度分层晋级；A-MEM 动态重连 | 事实只增不减，越用越脏 |
| 冲突可追溯 | `audit` + `adjudication` + `query_log/evidence_log`，设计比多数开源项目细 | Mem0 多数只留 history | **这是优势**；但 adjudication 若由读取写，会污染标签 |
| 证据包契约 | `moshi-evidence/1` 字段完整、m_id 连续、降级枚举 8 种、query_id 不可跨查询复用 | 多数只返回 JSON blob | **明显领先**，P1 这部分做得好 |
| 降级诚实性 | 设计正确，但 BM25 异常被 repo 吞掉（§2.2）、依赖失效恒不触发（§3.6） | 主流实现常直接降级静默 | 设计领先、实现有漏洞 |
| 双时态 | `valid_at` / `valid_to` / `recorded_at` 齐全 | Graphiti 同样支持 | 设计领先，实现没跟上 |
| 命名空间隔离 | `scope` 硬锁 `global` | Mem0 / Zep 按 user / agent 隔离 | 已知的 Phase 0 限制，v1.1 前置 |
| 敏感信息 | 事实层脱敏，原文层不脱敏 | 主流实现多在入库前统一过滤 | 需要补齐 |
| 写入闭环 | annotation 无消费者 | 主流都是“写 → 抽取 → 合并”闭环 | 当前最致命的一条 |

**一句话**：与 Mem0 / Zep 的差距不在架构，而在三个“接上就生效”的地方——**写入有没有人消费、融合分有没有进排序、基数表有没有人填**。证据包契约与埋点可追溯性反而已经领先。
