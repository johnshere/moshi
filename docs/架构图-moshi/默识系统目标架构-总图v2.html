总架构：装配是门，能力是标准件

这一版只重画一张图，并且把注意力压在两个地方：装配层如何把五张不同的「嘴」压成同一个请求，机理层与基础设施如何切成 写 / 读 / 存储 / Sidecar 四块。上层的差异（信封、stdio、HTTP、argv、页面）全部止步于装配，能力层对外只有一个外形： execute(req, ctx) → Result。
01 · 唯一开门人

装配是门，不是翻译层

面只做协议归一；caps × 能力 × mode/budget 矩阵决定放行。矩阵外直接拒绝 —— 「默认允许」是这套架构最常见的退化方式。

02 · 统一信封

统一的是外形，不是字段

五个能力共用 execute(req, ctx) → Result：错误模型、降级码、trace/cost、副作用声明同一套；req 字段各自独立，编译期校验。

03 · 2×2 分块

L1 与 L0 各切两块

L1 = 写链路 / 读链路；L0 = 存储 / Sidecar。写块只写、读块只读，跨块只经存储；Sidecar 是唯一允许「缺席」的依赖。

为什么这么切三个决定，会影响后面所有代码归属

装配层做三件事，只做三件

  • 查矩阵：谁能调谁、给多少预算、用哪个 mode。数据表，不是 if 分支。
  • 注入 ctx：caller · scope · budget · trace。身份由这里给，面不再自己算。
  • 串步骤：≤3 步的组合（import = 扫描 + capture），有事务边界才算一条。

反例：装配开始读 req.topic、开始拼返回文案，就已经不是门，而是第二个 service 层。

L1 与 L0 的 2×2

  • 写链路（WR0→WR8）：唯一写入口 upsertFact，harvest 异步补边。
  • 读链路（RD1→RD9）：三路召回 + 裁决，证据包是终点。
  • 存储：WAL 单写者；归档是可重放的旁路，不是备份。
  • Sidecar：encode / score / 熔断，缺席只改降级码。

不变量：写块不读、读块不写、跨块只经存储；Sidecar 不进流水线内部。
