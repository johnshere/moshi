v4 是一张系统架构总图：纵向是八层依赖骨架（① 宿主 → ⑧ 进程外），横向是数据流转——WR0–WR8 写在 ④ 领域层，RD3–RD9 读也在 ④ 领域层，各自往下穿到 ⑦ 存储。运行日志（query_log / 审计 / 日志）不是系统数据，作为旁路虚线挂在存储旁边，不汇入主写链。布局仍由 Mermaid Flowchart（jsDelivr CDN）生成。

竖着读 · 层

箭头一律指向被依赖方，越往下越纯：上层认识下层，下层永远不知道上层。① 宿主 到 ⑧ 进程外，一共八段。

顺着读 · 流转

写入从 ② 进、在 ③ 收口、由 ④ 的 WR0–WR8 一步步行完，落到 ⑦；读取同样在 ④ 里走 RD3–RD9，再从 ② 注入回去。

虚线 = 不在主链

旁路：query_log / 审计 / 日志，只写不读。Sidecar：可缺席的判断支路，缺了就退化为纯符号。

02

三条硬红线与一条旁路

图上画不出的约束，写在这里
  • read ↛ write：两条正交支路，禁止互相 import；运行时都碰同一个 SQLite，那是数据交汇，不是代码耦合。
  • core ↛ app / http：领域层不认识接入与组装，只接收已归一化的调用。
  • domain ↛ infra：类型层不碰 IO；业务代码不拿到 SQL、一律经 infra 的专用方法。
  • 旁路不是主链：query_log（保留 3 天）、audit、log 由读写过程顺带写入，只写不读——它们不参与写入判定，也不会被检索；归档投影是 ⑧ 的产物，同样不回灌。
  • Sidecar 可缺席：它是唯一允许「不在」的依赖——缺席即 no_sidecar，读取退化为纯符号，不阻塞主链路。
